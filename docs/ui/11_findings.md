> 알기 전에 적는다. 번호만 연구 파트의 `F-n` 과 나눠 둔 것이다.

## UF-1. 팔레트를 **통째로 재는 것이 과잉 진단**이었다 — 그림이 실제로 쓰는 조합으로 재야 한다

| | |
|---|---|
| 상태 | **확정** (`scripts/make_slides.py` 의 `show` 세 줄에서 읽음) |
| 발견 | UD-1 1 단계에서 검증기를 되찾아 팔레트를 재던 중 |
| 영향 | UD-2 의 수정 범위, `docs/ui/01_system.md` 2 절의 판정, 앞으로의 검증 방식 |

### 발단

되찾은 검증기로 저장소의 팔레트를 재니 **넷 중 셋이 FAIL** 로 나왔다. 그중
보고서·카드의 7 색은 `M02` 보라 ↔ `M01` 파랑이 정상시야 ΔE **12.3** 이었고,
그 쌍을 고치는 것으로 보고했다.

### 먼저 의심한 것 — 그리고 그것이 틀린 지점

「**팔레트 사전에 있는 색은 전부 한 화면에 나올 수 있다**」고 보았다. 그래서
`--pairs all` 로 7 색을 한 번에 쟀다.

**틀렸다.** 코드를 열어 보니 팔레트 사전의 색이 전부 한 그림에 오는 일이 없었다.

### 결정적 측정 — 그림이 실제로 쓰는 조합 `[측정]`

`scripts/make_slides.py` 의 `show = [...]` 세 줄이 조합을 정한다. 그 셋을 각각
`scripts/validate_palette.py` 로 쟀다:

| 조합 | 어디 | 판정 |
|---|---|---|
| `M01`·`M04`·`M08` | 한 축에 겹쳐 그리고 범례를 단다 — **가장 엄격한 자리** | **ALL PASS** |
| `M_FE`·`M04`·`M08` | 방법마다 칸이 따로 (facet) | **FAIL** — `M_FE`↔`M04` 12.9 |
| `M_FE`·`M01`·`M04`·`M05`·`M08` | 막대 차트, x 축에 이름이 직접 붙는다 | **FAIL** — 위 + `M04`↔`M05` 13.7 |

**`M02` 와 `M06` 은 어느 그림에도 안 나온다** — 팔레트 사전에 정의만 있다.
즉 12.3 은 **존재하지 않는 그림의 실패**였다.

### 왜 이것이 중요한가 — 하마터면 노랑을 갈색으로 만들 뻔했다

7 색 전체를 통과시키려고 후보를 탐색했더니 **`M05` 노랑이 `#986800` 갈색(원래에서
ΔE 21.6)** 으로 밀려나는 답이 먼저 나왔다. 쓰이지 않는 조합을 만족시키려고
**쓰이는 그림의 색 정체성을 버리는** 수정이었다.

조합으로 다시 재니 실제 수정은 **두 색 × ΔE 2** 로 끝났다 (UD-2).

### 저장소가 이미 알고 있었다

실패 두 쌍 중 하나는 새 발견이 아니다. `docs/33_card_design_samples.md` 가
「**네 번째를 얹으면 정상시야 분리도가 무너진다**(`M_FE` magenta ↔ `M04` orange 가
ΔE 12.9 로 15 미만 FAIL)」라고 적고, 그래서 **카드에서는 `M_FE` 를 뺐다.**

**그런데 슬라이드에는 남아 있었다.** 문서가 경고를 적은 산출물에서는 지켜졌고,
다른 산출물로는 옮겨지지 않았다. 이것이 「**검증기가 저장소에 없었다**」의 두 번째
비용이다 — 자가 없으면 규칙이 한 파일 안에만 머문다.

### 놓쳤다면

**노랑이 갈색이 된 채로 보고서 그림 전체가 다시 그려졌을 것이다.** 그리고 그
수정은 「검증을 통과시키려고」 한 것이라 되돌릴 근거를 대기도 어려웠다 — 검사는
초록이고 그림만 이상해진다.

더 나쁜 쪽은 **자를 잘못 쓴 채로 다음 단계에 들어가는 것**이다. 시연 화면은 방법이
11 개까지 켜지므로 전체 팔레트를 한 번에 재면 **어떤 조합도 통과할 수 없고**,
그러면 「색으로는 안 되니 다른 부호를 쓰자」는 잘못된 결론으로 갔을 것이다.
실제로는 레인마다 두 색씩이라 여유가 있다.

### 규칙으로 남길 것

- **팔레트는 사전 단위가 아니라 「한 그림에 함께 나오는 색」 단위로 잰다.**
  `scripts/validate_palette.py --scope lane|legend` 가 그 두 자이고, 조합 목록은
  `tests/test_palette.py` 가 코드에서 읽는다.
- **시연 화면에도 그대로 적용된다.** 화면은 방법마다 레인이 따로라 한 레인 안에
  동시에 보이는 색은 [출력 1 + 참값 회색] 둘뿐이다. 여러 색이 나란히 오는 곳은
  범례뿐이다 (`docs/ui/01_system.md` 2.1).

### 남은 것

`M02`·`M06` 은 팔레트에 정의만 있고 안 쓰인다. 지금은 **그대로 둔다** — 쓰이지
않으므로 해롭지 않고, 나중에 그림에 넣게 되면 그때 그 조합으로 재면 된다.
**[미정]** 으로 남길지, 사전에서 뺄지는 팔레트 단일 원본을 만들 때 정한다.

## UF-2. **소스에 문자열이 있는지로 재면 안 된다** — U-14 가 과했고, 아무 일도 안 하는 줄이 검사를 통과했다

| | |
|---|---|
| 상태 | **확정** (브라우저로 실측) |
| 발견 | UD-1 2 단계에서 화면 검사를 처음 돌렸을 때 |
| 영향 | U-14 의 판정, 앞으로 화면 규약을 재는 방식 |

### 발단

U-14 를 이렇게 적었다 — 「`prefers-reduced-motion` 대응 없음: `index`·`live`·카드
3 안 **전부 0**, `mockup_expo` 만 1. 그런데 이들이 스윕·스크롤을 돌린다」.

`grep -c prefers-reduced-motion` 으로 센 것이었다.

### 먼저 의심한 것

「문자열이 없으면 대응이 없는 것이고, 대응이 없으면 애니메이션이 돈다」고 봤다.
**두 고리가 다 틀렸다.**

### 결정적 측정 — reduced-motion 을 켜고 캔버스 변화를 쟀다 `[측정]`

`tests/test_demo_screens.py` 가 `prefers-reduced-motion: reduce` 로 페이지를 열고
캔버스 픽셀 해시를 1.5 초 간격으로 두 번 떠서 비교한다.

| 화면 | 문자열 | **실제로 도는가** |
|---|---|---|
| `index.html` | 없음 | **안 돈다** — 재생 기본값이 `off` 다 |
| `cards/A_monitor.html` | 없음 | **안 돈다** — 「흐르게」 버튼을 눌러야 시작한다 |
| `live.html` | 없음 | 서버가 없으면 안 돈다. **데이터가 오면 스윕 커서가 매 프레임 돈다** |
| `mockup_expo.html` | **있음** | 재생 기본값이 「정지」라 안 돈다 |

**즉 자동으로 도는 것은 애초에 없었다.** 「스윕·스크롤을 돌린다」는 전제가 틀렸다 —
셋 다 **사람이 켜야** 돈다. 체크리스트가 요구하는 것은 「**자동** 회전 콘텐츠」이고,
사용자가 명시적으로 켠 것은 그 대상이 아니다.

### 반대편 — 문자열이 있는데 아무 일도 안 한다

`mockup_expo.html` 이 가진 한 줄은 이것이었다:

```css
@media (prefers-reduced-motion:reduce){canvas{animation:none}}
```

**캔버스는 CSS 애니메이션으로 그리지 않는다.** `requestAnimationFrame` 으로 그린다.
이 줄은 존재하지 않는 CSS 애니메이션을 끈다 — 아무 일도 하지 않는다. 그런데
**문자열 검사는 이것을 「대응 있음」으로 센다.**

### 조치

- 검사를 **실동작**으로 바꿨다 — 소스를 읽지 않고 브라우저에서 캔버스 변화를 잰다.
- U-14 를 정정했다 (`docs/ui/01_system.md` 1.1).
- 남은 실물 하나를 고쳤다 — `live.html` 의 스윕 커서는 데이터가 오면 매 프레임
  도는데, reduced-motion 이면 **데이터가 올 때만** 그리게 했다. 흐르는 것은 남고
  쉬지 않는 재도색만 빠진다.
- `mockup_expo.html` 의 무효한 줄은 실제로 전환·스크롤을 줄이는 것으로 바꿨다.

### 놓쳤다면

두 방향으로 틀렸을 것이다. **없는 결함을 고치느라** 세 화면에 쓸모없는 가드를
넣고, **있는 결함**(`mockup_expo` 의 빈 줄, `live` 의 커서)은 「문자열이 있으니
됐다」로 넘어갔을 것이다.

그리고 이 교훈은 이 항목 하나에 그치지 않는다 — **U-1~U-14 의 절반이 `grep` 으로
센 것**이다. 2 단계의 화면 검사가 그것들을 다시 재는 자리이기도 하다.

### 규칙으로 남길 것

> **화면 규약은 소스가 아니라 화면에서 잰다.** `grep` 은 「어디를 볼지」를 찾는
> 데는 좋지만 판정에는 쓰지 않는다. 브라우저로 열어 **동작을 재는** 검사가
> `tests/test_demo_screens.py` 다.

## UF-3. 구간 길이를 고정해서, **신호 속도가 화면 폭에 딸려 간다** — 같은 「10 s」가 화면마다 다른 속도다

| | |
|---|---|
| 상태 | **확정** (CSS px↔mm 환산, `docs/ui/02_benchmark.md` 1 절) |
| 발견 | 0 단계 R-A — 심전도 표시 규약을 우리 화면에 대 보면서 |
| 영향 | 3 단계 레이아웃, 구간 길이 칩의 의미, U-9 의 해석 |

### 발단

「우리 격자는 장식이다」까지는 알고 있었다(U-13 · 6.0). 표준을 확인하고
**우리 화면이 실제로 몇 mm/s 인지** 환산해 보다가 다른 것이 나왔다.

### 먼저 의심한 것

「구간 길이를 10 s 로 고정했으니 **속도도 고정**이고, 격자만 그 속도에 맞추면
된다」고 봤다. **틀렸다** — 고정된 것은 **시간**이지 속도가 아니다. 캔버스가 화면
폭에 맞춰지므로 **폭이 속도를 정한다.**

### 결정적 측정 `[측정]`

CSS 에서 1 mm = 96/25.4 = 3.7795 px.

| 화면 폭 | 구간 10 s | 구간 4 s | 구간 2 s |
|---|---|---|---|
| 1920 | **49.6 mm/s** | 124 | 248 |
| 1440 | **36.9 mm/s** | 92 | 185 |
| 1280 | **32.7 mm/s** | 82 | 164 |

임상 표준은 **25 mm/s**(소칸 0.04 s)와 빠른 기록 **50 mm/s** 둘뿐이다.
**표준과 맞는 칸은 표에서 하나 — 1920 에서 10 s 이고, 그것도 의도가 아니라 우연이다.**

### 왜 중요한가

1. **격자를 규약에 맞추려 해도 맞출 수가 없다.** 대칸이 0.2 s 를 뜻하게 하려면
   속도가 고정돼야 하는데 지금은 폭이 바뀌면 같이 움직인다.
2. **U-9 의 해석이 바뀐다.** 「반응형이 없다(`@media` 0 개)」는 레이아웃이 깨진다는
   말로 읽혔는데, 화면 검사에서 세 폭 모두 **넘침은 없었다**. 실제 문제는 레이아웃이
   아니라 **신호의 시간 척도가 조용히 바뀌는 것**이다. 깨지지 않기 때문에 더 위험하다.
3. 박람회에서 **다른 노트북을 쓰면** 파형이 다른 속도로 흐른다. 아무도 눈치채지 못한다.

### 조치 — 3 단계로 넘긴다

**구간 길이가 아니라 속도를 고정한다.** 칩을 「10 s · 4 s · 2 s」가 아니라
**「25 mm/s · 50 mm/s」**로 두고, 화면에 보이는 시간은 폭이 정하게 한다
(1920 → 19.9 s / 9.9 s · 1280 → 13.1 s / 6.5 s). 확대는 **한 박동 렌즈**가 맡는다
(`docs/31_demo_design_review.md` 1.2 가 이미 「빠진 것은 이것 하나」라고 지목했다).

### 놓쳤다면

격자를 「대칸 = 0.2 s」로 그려 놓고 **폭이 바뀌면 거짓말이 되는** 화면을 만들었을
것이다. 지금은 격자가 아무 말도 하지 않아서 **틀리지도 않는다** — 규약을 절반만
들여오는 것이 아무것도 안 하는 것보다 나쁘다.

## UF-4. **페이드는 처음부터 있었다 — 순서가 틀렸을 뿐이다.** 폭을 두 번 줄이는 동안 원인은 그대로였다

| | |
|---|---|
| 상태 | **확정** (브라우저에서 캔버스 픽셀로 실측) |
| 발견 | 3 단계 경로 B 에 스윕 잔광·페이드를 넣던 중, 「적용됐는지 확인해 달라」는 요청에서 |
| 영향 | 스윕 렌더링, 그리고 **「보이지 않는다」를 폭 문제로 읽는 습관** |

### 발단

커서 오른쪽(곧 덮어씌워질 지난 바퀴)을 딱 잘라 지우지 말고 커서에 가까워질수록
투명해지게 해 달라는 요청을 받았다. 구현하고 돌렸는데 **화면에는 여전히 딱 잘린
경계만 보였다.**

### 먼저 의심한 것 — 두 번 다 폭이라고 봤다

1. 「지우는 폭 50 % 안에 페이드 구간 16 % 가 통째로 묻혔다」 → **22 % 로 줄였다.**
   지난 바퀴가 오른쪽에 남기 시작했으므로 **고쳐진 줄 알았다.** 아니었다.
   경계는 그대로 딱 잘려 있었고, 단지 그 경계가 더 왼쪽으로 왔을 뿐이다.
2. 다시 폭을 의심하려던 참에 **그리는 순서**를 읽었다.

### 관측 — 코드의 순서 `[코드]`

한 프레임이 커서 앞에서 하던 일:

```
  [x1, x1+fade]        페이드 그라디언트 (destination-out)
  [x1+fade, x1+erase]  clearRect — 딱 잘라 지움
```

지움 막대가 페이드 **바깥쪽**에 있다. 커서는 왼쪽에서 오른쪽으로 가므로, 어떤
픽셀이든 **커서가 닿기 `erase-fade` 만큼 전에 이미 통째로 지워져 있다.** 페이드
구간에 들어올 때 그 자리는 이미 비어 있고, **페이드는 빈 칸을 페이드한다.**

폭을 어떻게 줄여도 이 관계는 변하지 않는다. `erase > fade` 인 한 지움이 항상 먼저다.

### 고친 방식

지움 막대를 **커서 바로 앞**(1.2 % ≈ 21 px)으로 좁혀 두 파형이 한 픽셀에서
겹치지 않게만 하고, 그 너머의 지난 바퀴는 **손대지 않는다.** 지우는 일은 페이드가
한다 — 같은 픽셀이 매 프레임 다시 칠해지고 커서가 가까워질수록 계수가 커지므로
곱이 지수로 떨어져, 커서가 닿을 때쯤 남는 것이 없다. 딱 잘라 지우는 것과 결과는
같고 **경계만 없다.**

### 실측 `[측정]`

두 바퀴째 커서 기준, 알파로 가중한 잉크량 (40 px 묶음):

| 커서로부터 | +0 | +40 | +80 | +120 | +160 | +200 | +240 | +280 |
|---|---|---|---|---|---|---|---|---|
| 잉크 | 0.8 | 0.5 | 1.1 | 0.6 | 1.7 | 13.8 | 155.9 | 98.4 |

계단이 아니라 경사다. 커서 뒤 잔광도 같은 탐침으로 잡힌다 — 바로 뒤 234 vs 먼 쪽 91.

### 탐침을 만들면서 한 번 더 속았다 `[측정]`

처음 쓴 탐침은 **RGB 만** 봤다. `destination-out` 은 **RGB 를 그대로 두고 알파만
깎으므로**, 완전히 지워진 픽셀이 `maxL=255`(순백)로 읽혔다. 「커서 앞에 흰 줄이
있다」는 있지도 않은 결함을 한참 쫓았다. **알파로 가중하지 않은 캔버스 측정은
측정이 아니다.**

### 남긴 것

`tests/test_demo_screens.py::test_sweep_fades_into_the_cursor_instead_of_cutting`
— **폭이 아니라 모양을 잰다.** 커서 앞이 비었는지, 멀리에 지난 바퀴가 남았는지,
그리고 그 사이가 계단이 아니라 경사인지(`near < mid < far`). 폭을 다시 건드려도,
순서를 다시 뒤집어도 이 검사가 잡는다.

### 놓쳤다면

「페이드를 넣었다」고 기록에 적힌 채 화면에는 딱 잘린 경계가 남았을 것이다.
`docs/33` 이 겪은 「문서가 코드보다 앞섰다」와 **같은 종류**다 — 이번에는 코드도
있었고 실행도 됐는데, **순서 때문에 아무 일도 하지 않았다.**

## UF-5. 다크를 **매체 질의에만** 적으면, 화면에서 다크를 고른 사람에게 두 테마가 섞인다

| | |
|---|---|
| 상태 | **확정** (OS 라이트 + `data-theme="dark"` 로 실측) |
| 발견 | 시안을 아티팩트로 올려 휴대폰에서 열어 보려고 테마 처리를 점검하다가 |
| 영향 | `demo/ui/layout_b.html`, 앞으로 만들 모든 화면 |

### 발단

아티팩트 뷰어는 보는 사람이 고른 테마를 루트에 `data-theme="dark"` 로 찍는다.
그래서 **OS 는 라이트인데 화면에서 다크를 고른** 조합이 실제로 생긴다.

### 먼저 의심한 것

**의심조차 안 했다.** `tokens.css` 가 두 벌(`@media` 와 `[data-theme]`)을 제대로
갖고 있는 것을 먼저 보고 **「이 프로젝트는 이미 이 함정을 알고 있구나」** 로
넘겼다. 토큰 파일이 맞으니 그 토큰을 쓰는 화면도 맞을 것이라고 본 것인데,
**두 파일은 각자 자기 토큰을 따로 갖고 있었다.**

### 관측 `[측정]`

`tokens.css` 는 두 벌을 갖고 있었다 — `@media (prefers-color-scheme:dark)` 와
`:root[data-theme="dark"]`. **`layout_b.html` 은 한 벌뿐이었다.** 그 결과 이 조합에서

* 방법 색(`tokens.css`) → 다크판으로 바뀐다
* 배경·잉크·격자(`layout_b.html`) → **라이트 그대로**

한 화면 안에서 두 테마가 섞인다. 자동 반전이 아니라 **선언이 반쪽**이었던 것이다.

JS 도 같은 곳이 틀어져 있었다. `isDark()` 가 `matchMedia` 로 직접 따지고 있어서,
이 조합에서 **잔광 톤업이 검정 쪽으로 섞였다** — 다크 배경 위에서 빛나야 할 것이
어두워진다.

### 고친 방식

CSS 에 `--dark: 0|1` 을 두고 세 블록(기본 · 매체 질의 · `[data-theme]`)이 정하게
한 다음, **JS 는 그 하나만 읽는다.** 네 조합을 JS 가 다시 재현할 일이 없어지므로
어긋날 자리가 사라진다.

### 남긴 것

`tests/test_demo_screens.py::test_explicit_dark_choice_darkens_the_page` —
**OS 라이트로 열고** `data-theme="dark"` 를 찍은 뒤 배경이 실제로 어두워지는지 본다.
매체 질의만 있는 화면은 여기서 걸린다.

### 놓쳤다면

노트북(OS 다크)에서는 멀쩡했을 것이다. **박람회 노트북이 라이트 OS 이고 관람객이
다크를 고르는 순간** 화면이 반쯤 뒤집힌 채로 서 있었을 것이다.
