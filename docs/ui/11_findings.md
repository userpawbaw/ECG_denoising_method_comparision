## UF-1. 팔레트를 **통째로 재는 것이 과잉 진단**이었다 — 그림이 실제로 쓰는 조합으로 재야 한다

| | |
|---|---|
| 상태 | **확정** (`scripts/make_slides.py` 의 `show` 세 줄에서 읽음) |
| 발견 | UD-1 1 단계에서 검증기를 되찾아 팔레트를 재던 중 |
| 영향 | UD-2 의 수정 범위, `docs/ui/01_system.md` 2 절의 판정, 앞으로의 검증 방식 |

### 발단

되찾은 검증기로 저장소의 팔레트를 재니 **넷 중 셋이 FAIL** 로 나왔다. 그중
보고서·카드의 7 색은 `M02` 보라 ↔ `M01` 파랑이 정상시야 ΔE **12.3** 이었고,
그 쌍을 고치는 것으로 보고했다.

### 먼저 의심한 것 — 그리고 그것이 틀린 지점

「**팔레트 사전에 있는 색은 전부 한 화면에 나올 수 있다**」고 보았다. 그래서
`--pairs all` 로 7 색을 한 번에 쟀다.

**틀렸다.** 코드를 열어 보니 팔레트 사전의 색이 전부 한 그림에 오는 일이 없었다.

### 결정적 측정 — 그림이 실제로 쓰는 조합 `[측정]`

`scripts/make_slides.py` 의 `show = [...]` 세 줄이 조합을 정한다. 그 셋을 각각
`scripts/validate_palette.py` 로 쟀다:

| 조합 | 어디 | 판정 |
|---|---|---|
| `M01`·`M04`·`M08` | 한 축에 겹쳐 그리고 범례를 단다 — **가장 엄격한 자리** | **ALL PASS** |
| `M_FE`·`M04`·`M08` | 방법마다 칸이 따로 (facet) | **FAIL** — `M_FE`↔`M04` 12.9 |
| `M_FE`·`M01`·`M04`·`M05`·`M08` | 막대 차트, x 축에 이름이 직접 붙는다 | **FAIL** — 위 + `M04`↔`M05` 13.7 |

**`M02` 와 `M06` 은 어느 그림에도 안 나온다** — 팔레트 사전에 정의만 있다.
즉 12.3 은 **존재하지 않는 그림의 실패**였다.

### 왜 이것이 중요한가 — 하마터면 노랑을 갈색으로 만들 뻔했다

7 색 전체를 통과시키려고 후보를 탐색했더니 **`M05` 노랑이 `#986800` 갈색(원래에서
ΔE 21.6)** 으로 밀려나는 답이 먼저 나왔다. 쓰이지 않는 조합을 만족시키려고
**쓰이는 그림의 색 정체성을 버리는** 수정이었다.

조합으로 다시 재니 실제 수정은 **두 색 × ΔE 2** 로 끝났다 (UD-2).

### 저장소가 이미 알고 있었다

실패 두 쌍 중 하나는 새 발견이 아니다. `docs/33_card_design_samples.md` 가
「**네 번째를 얹으면 정상시야 분리도가 무너진다**(`M_FE` magenta ↔ `M04` orange 가
ΔE 12.9 로 15 미만 FAIL)」라고 적고, 그래서 **카드에서는 `M_FE` 를 뺐다.**

**그런데 슬라이드에는 남아 있었다.** 문서가 경고를 적은 산출물에서는 지켜졌고,
다른 산출물로는 옮겨지지 않았다. 이것이 「**검증기가 저장소에 없었다**」의 두 번째
비용이다 — 자가 없으면 규칙이 한 파일 안에만 머문다.

### 놓쳤다면

**노랑이 갈색이 된 채로 보고서 그림 전체가 다시 그려졌을 것이다.** 그리고 그
수정은 「검증을 통과시키려고」 한 것이라 되돌릴 근거를 대기도 어려웠다 — 검사는
초록이고 그림만 이상해진다.

더 나쁜 쪽은 **자를 잘못 쓴 채로 다음 단계에 들어가는 것**이다. 시연 화면은 방법이
11 개까지 켜지므로 전체 팔레트를 한 번에 재면 **어떤 조합도 통과할 수 없고**,
그러면 「색으로는 안 되니 다른 부호를 쓰자」는 잘못된 결론으로 갔을 것이다.
실제로는 레인마다 두 색씩이라 여유가 있다.

### 규칙으로 남길 것

- **팔레트는 사전 단위가 아니라 「한 그림에 함께 나오는 색」 단위로 잰다.**
  `scripts/validate_palette.py --scope lane|legend` 가 그 두 자이고, 조합 목록은
  `tests/test_palette.py` 가 코드에서 읽는다.
- **시연 화면에도 그대로 적용된다.** 화면은 방법마다 레인이 따로라 한 레인 안에
  동시에 보이는 색은 [출력 1 + 참값 회색] 둘뿐이다. 여러 색이 나란히 오는 곳은
  범례뿐이다 (`docs/ui/01_system.md` 2.1).

### 남은 것

`M02`·`M06` 은 팔레트에 정의만 있고 안 쓰인다. 지금은 **그대로 둔다** — 쓰이지
않으므로 해롭지 않고, 나중에 그림에 넣게 되면 그때 그 조합으로 재면 된다.
**[미정]** 으로 남길지, 사전에서 뺄지는 팔레트 단일 원본을 만들 때 정한다.

## UF-2. **소스에 문자열이 있는지로 재면 안 된다** — U-14 가 과했고, 아무 일도 안 하는 줄이 검사를 통과했다

| | |
|---|---|
| 상태 | **확정** (브라우저로 실측) |
| 발견 | UD-1 2 단계에서 화면 검사를 처음 돌렸을 때 |
| 영향 | U-14 의 판정, 앞으로 화면 규약을 재는 방식 |

### 발단

U-14 를 이렇게 적었다 — 「`prefers-reduced-motion` 대응 없음: `index`·`live`·카드
3 안 **전부 0**, `mockup_expo` 만 1. 그런데 이들이 스윕·스크롤을 돌린다」.

`grep -c prefers-reduced-motion` 으로 센 것이었다.

### 먼저 의심한 것

「문자열이 없으면 대응이 없는 것이고, 대응이 없으면 애니메이션이 돈다」고 봤다.
**두 고리가 다 틀렸다.**

### 결정적 측정 — reduced-motion 을 켜고 캔버스 변화를 쟀다 `[측정]`

`tests/test_demo_screens.py` 가 `prefers-reduced-motion: reduce` 로 페이지를 열고
캔버스 픽셀 해시를 1.5 초 간격으로 두 번 떠서 비교한다.

| 화면 | 문자열 | **실제로 도는가** |
|---|---|---|
| `index.html` | 없음 | **안 돈다** — 재생 기본값이 `off` 다 |
| `cards/A_monitor.html` | 없음 | **안 돈다** — 「흐르게」 버튼을 눌러야 시작한다 |
| `live.html` | 없음 | 서버가 없으면 안 돈다. **데이터가 오면 스윕 커서가 매 프레임 돈다** |
| `mockup_expo.html` | **있음** | 재생 기본값이 「정지」라 안 돈다 |

**즉 자동으로 도는 것은 애초에 없었다.** 「스윕·스크롤을 돌린다」는 전제가 틀렸다 —
셋 다 **사람이 켜야** 돈다. 체크리스트가 요구하는 것은 「**자동** 회전 콘텐츠」이고,
사용자가 명시적으로 켠 것은 그 대상이 아니다.

### 반대편 — 문자열이 있는데 아무 일도 안 한다

`mockup_expo.html` 이 가진 한 줄은 이것이었다:

```css
@media (prefers-reduced-motion:reduce){canvas{animation:none}}
```

**캔버스는 CSS 애니메이션으로 그리지 않는다.** `requestAnimationFrame` 으로 그린다.
이 줄은 존재하지 않는 CSS 애니메이션을 끈다 — 아무 일도 하지 않는다. 그런데
**문자열 검사는 이것을 「대응 있음」으로 센다.**

### 조치

- 검사를 **실동작**으로 바꿨다 — 소스를 읽지 않고 브라우저에서 캔버스 변화를 잰다.
- U-14 를 정정했다 (`docs/ui/01_system.md` 1.1).
- 남은 실물 하나를 고쳤다 — `live.html` 의 스윕 커서는 데이터가 오면 매 프레임
  도는데, reduced-motion 이면 **데이터가 올 때만** 그리게 했다. 흐르는 것은 남고
  쉬지 않는 재도색만 빠진다.
- `mockup_expo.html` 의 무효한 줄은 실제로 전환·스크롤을 줄이는 것으로 바꿨다.

### 놓쳤다면

두 방향으로 틀렸을 것이다. **없는 결함을 고치느라** 세 화면에 쓸모없는 가드를
넣고, **있는 결함**(`mockup_expo` 의 빈 줄, `live` 의 커서)은 「문자열이 있으니
됐다」로 넘어갔을 것이다.

그리고 이 교훈은 이 항목 하나에 그치지 않는다 — **U-1~U-14 의 절반이 `grep` 으로
센 것**이다. 2 단계의 화면 검사가 그것들을 다시 재는 자리이기도 하다.

### 규칙으로 남길 것

> **화면 규약은 소스가 아니라 화면에서 잰다.** `grep` 은 「어디를 볼지」를 찾는
> 데는 좋지만 판정에는 쓰지 않는다. 브라우저로 열어 **동작을 재는** 검사가
> `tests/test_demo_screens.py` 다.

## UF-3. 구간 길이를 고정해서, **신호 속도가 화면 폭에 딸려 간다** — 같은 「10 s」가 화면마다 다른 속도다

| | |
|---|---|
| 상태 | **확정** (CSS px↔mm 환산, `docs/ui/02_benchmark.md` 1 절) |
| 발견 | 0 단계 R-A — 심전도 표시 규약을 우리 화면에 대 보면서 |
| 영향 | 3 단계 레이아웃, 구간 길이 칩의 의미, U-9 의 해석 |

### 발단

「우리 격자는 장식이다」까지는 알고 있었다(U-13 · 6.0). 표준을 확인하고
**우리 화면이 실제로 몇 mm/s 인지** 환산해 보다가 다른 것이 나왔다.

### 먼저 의심한 것

「구간 길이를 10 s 로 고정했으니 **속도도 고정**이고, 격자만 그 속도에 맞추면
된다」고 봤다. **틀렸다** — 고정된 것은 **시간**이지 속도가 아니다. 캔버스가 화면
폭에 맞춰지므로 **폭이 속도를 정한다.**

### 결정적 측정 `[측정]`

CSS 에서 1 mm = 96/25.4 = 3.7795 px.

| 화면 폭 | 구간 10 s | 구간 4 s | 구간 2 s |
|---|---|---|---|
| 1920 | **49.6 mm/s** | 124 | 248 |
| 1440 | **36.9 mm/s** | 92 | 185 |
| 1280 | **32.7 mm/s** | 82 | 164 |

임상 표준은 **25 mm/s**(소칸 0.04 s)와 빠른 기록 **50 mm/s** 둘뿐이다.
**표준과 맞는 칸은 표에서 하나 — 1920 에서 10 s 이고, 그것도 의도가 아니라 우연이다.**

### 왜 중요한가

1. **격자를 규약에 맞추려 해도 맞출 수가 없다.** 대칸이 0.2 s 를 뜻하게 하려면
   속도가 고정돼야 하는데 지금은 폭이 바뀌면 같이 움직인다.
2. **U-9 의 해석이 바뀐다.** 「반응형이 없다(`@media` 0 개)」는 레이아웃이 깨진다는
   말로 읽혔는데, 화면 검사에서 세 폭 모두 **넘침은 없었다**. 실제 문제는 레이아웃이
   아니라 **신호의 시간 척도가 조용히 바뀌는 것**이다. 깨지지 않기 때문에 더 위험하다.
3. 박람회에서 **다른 노트북을 쓰면** 파형이 다른 속도로 흐른다. 아무도 눈치채지 못한다.

### 조치 — 3 단계로 넘긴다

**구간 길이가 아니라 속도를 고정한다.** 칩을 「10 s · 4 s · 2 s」가 아니라
**「25 mm/s · 50 mm/s」**로 두고, 화면에 보이는 시간은 폭이 정하게 한다
(1920 → 19.9 s / 9.9 s · 1280 → 13.1 s / 6.5 s). 확대는 **한 박동 렌즈**가 맡는다
(`docs/31_demo_design_review.md` 1.2 가 이미 「빠진 것은 이것 하나」라고 지목했다).

### 놓쳤다면

격자를 「대칸 = 0.2 s」로 그려 놓고 **폭이 바뀌면 거짓말이 되는** 화면을 만들었을
것이다. 지금은 격자가 아무 말도 하지 않아서 **틀리지도 않는다** — 규약을 절반만
들여오는 것이 아무것도 안 하는 것보다 나쁘다.

## UF-4. **페이드는 처음부터 있었다 — 순서가 틀렸을 뿐이다.** 폭을 두 번 줄이는 동안 원인은 그대로였다

| | |
|---|---|
| 상태 | **확정** (브라우저에서 캔버스 픽셀로 실측) |
| 발견 | 3 단계 경로 B 에 스윕 잔광·페이드를 넣던 중, 「적용됐는지 확인해 달라」는 요청에서 |
| 영향 | 스윕 렌더링, 그리고 **「보이지 않는다」를 폭 문제로 읽는 습관** |

### 발단

커서 오른쪽(곧 덮어씌워질 지난 바퀴)을 딱 잘라 지우지 말고 커서에 가까워질수록
투명해지게 해 달라는 요청을 받았다. 구현하고 돌렸는데 **화면에는 여전히 딱 잘린
경계만 보였다.**

### 먼저 의심한 것 — 두 번 다 폭이라고 봤다

1. 「지우는 폭 50 % 안에 페이드 구간 16 % 가 통째로 묻혔다」 → **22 % 로 줄였다.**
   지난 바퀴가 오른쪽에 남기 시작했으므로 **고쳐진 줄 알았다.** 아니었다.
   경계는 그대로 딱 잘려 있었고, 단지 그 경계가 더 왼쪽으로 왔을 뿐이다.
2. 다시 폭을 의심하려던 참에 **그리는 순서**를 읽었다.

### 관측 — 코드의 순서 `[코드]`

한 프레임이 커서 앞에서 하던 일:

```
  [x1, x1+fade]        페이드 그라디언트 (destination-out)
  [x1+fade, x1+erase]  clearRect — 딱 잘라 지움
```

지움 막대가 페이드 **바깥쪽**에 있다. 커서는 왼쪽에서 오른쪽으로 가므로, 어떤
픽셀이든 **커서가 닿기 `erase-fade` 만큼 전에 이미 통째로 지워져 있다.** 페이드
구간에 들어올 때 그 자리는 이미 비어 있고, **페이드는 빈 칸을 페이드한다.**

폭을 어떻게 줄여도 이 관계는 변하지 않는다. `erase > fade` 인 한 지움이 항상 먼저다.

### 고친 방식

지움 막대를 **커서 바로 앞**(1.2 % ≈ 21 px)으로 좁혀 두 파형이 한 픽셀에서
겹치지 않게만 하고, 그 너머의 지난 바퀴는 **손대지 않는다.** 지우는 일은 페이드가
한다 — 같은 픽셀이 매 프레임 다시 칠해지고 커서가 가까워질수록 계수가 커지므로
곱이 지수로 떨어져, 커서가 닿을 때쯤 남는 것이 없다. 딱 잘라 지우는 것과 결과는
같고 **경계만 없다.**

### 실측 `[측정]`

두 바퀴째 커서 기준, 알파로 가중한 잉크량 (40 px 묶음):

| 커서로부터 | +0 | +40 | +80 | +120 | +160 | +200 | +240 | +280 |
|---|---|---|---|---|---|---|---|---|
| 잉크 | 0.8 | 0.5 | 1.1 | 0.6 | 1.7 | 13.8 | 155.9 | 98.4 |

계단이 아니라 경사다. 커서 뒤 잔광도 같은 탐침으로 잡힌다 — 바로 뒤 234 vs 먼 쪽 91.

### 탐침을 만들면서 한 번 더 속았다 `[측정]`

## UF-5. 다크를 **매체 질의에만** 적으면, 화면에서 다크를 고른 사람에게 두 테마가 섞인다

| | |
|---|---|
| 상태 | **확정** (OS 라이트 + `data-theme="dark"` 로 실측) |
| 발견 | 시안을 아티팩트로 올려 휴대폰에서 열어 보려고 테마 처리를 점검하다가 |
| 영향 | `demo/ui/layout_b.html`, 앞으로 만들 모든 화면 |

### 발단

아티팩트 뷰어는 보는 사람이 고른 테마를 루트에 `data-theme="dark"` 로 찍는다.
그래서 **OS 는 라이트인데 화면에서 다크를 고른** 조합이 실제로 생긴다.

### 먼저 의심한 것

**의심조차 안 했다.** `tokens.css` 가 두 벌(`@media` 와 `[data-theme]`)을 제대로
갖고 있는 것을 먼저 보고 **「이 프로젝트는 이미 이 함정을 알고 있구나」** 로
넘겼다. 토큰 파일이 맞으니 그 토큰을 쓰는 화면도 맞을 것이라고 본 것인데,
**두 파일은 각자 자기 토큰을 따로 갖고 있었다.**

### 관측 `[측정]`

`tokens.css` 는 두 벌을 갖고 있었다 — `@media (prefers-color-scheme:dark)` 와
`:root[data-theme="dark"]`. **`layout_b.html` 은 한 벌뿐이었다.** 그 결과 이 조합에서

* 방법 색(`tokens.css`) → 다크판으로 바뀐다
* 배경·잉크·격자(`layout_b.html`) → **라이트 그대로**

한 화면 안에서 두 테마가 섞인다. 자동 반전이 아니라 **선언이 반쪽**이었던 것이다.

JS 도 같은 곳이 틀어져 있었다. `isDark()` 가 `matchMedia` 로 직접 따지고 있어서,
이 조합에서 **잔광 톤업이 검정 쪽으로 섞였다** — 다크 배경 위에서 빛나야 할 것이
어두워진다.

### 고친 방식

CSS 에 `--dark: 0|1` 을 두고 세 블록(기본 · 매체 질의 · `[data-theme]`)이 정하게
한 다음, **JS 는 그 하나만 읽는다.** 네 조합을 JS 가 다시 재현할 일이 없어지므로
어긋날 자리가 사라진다.

### 남긴 것

`tests/test_demo_screens.py::test_explicit_dark_choice_darkens_the_page` —
**OS 라이트로 열고** `data-theme="dark"` 를 찍은 뒤 배경이 실제로 어두워지는지 본다.
매체 질의만 있는 화면은 여기서 걸린다.

### 놓쳤다면

노트북(OS 다크)에서는 멀쩡했을 것이다. **박람회 노트북이 라이트 OS 이고 관람객이
다크를 고르는 순간** 화면이 반쯤 뒤집힌 채로 서 있었을 것이다.

## UF-6. 시안이 **의도한 서체로 그려진 적이 없다** — 그래서 한글에는 굵기 위계가 아예 없었다

### 결정적 측정 — 폭을 재고, 실제로 쓰인 서체를 물었다 `[측정]`

Chromium 1194, 이 컨테이너. 같은 문자열을 `var(--font-sans)` 스택과 대체 스택으로

**완전히 같다** — 스택의 첫 항목이 한 번도 적용된 적이 없다. `fc-list` 에 IBM Plex 가

> 대체로 그릴 수 있으면 참인 API라 증거가 못 된다. **폭 비교가 증거다.**

그 다음 CDP `CSS.getPlatformFontsForNode` 로 **실제로 쓰인 서체**를 물었다:

### 그래서 무엇이 틀렸나

2. 개발자 기계에 Plex 가 깔려 있으면 **거기서만** 다르게 보인다. 「투박해 보인다」가

### 놓쳤다면

박람회 노트북에 무엇이 깔려 있느냐에 따라 **부스에서 처음 보는 화면**이 됐다.
그리고 그보다 나쁜 쪽 — 서체를 몇 번 바꿔 보고도 「그래도 투박하다」가 반복됐을 것이다.
바꾼 것이 한 번도 적용되지 않으니 무엇을 해도 같은 화면이다. **원인이 아닌 곳을

### 추기 (2026-09-19) — **결론 하나가 틀렸다. 폭은 한글 굵기의 자가 아니다** `[측정]`

서체를 실은 뒤(UD-9 0 번) 확인하다가 드러났다. 실린 Plex 로도 **한글 폭은 400 과
700 이 똑같았다**(93.19 px). 「그럼 Bold 가 안 실렸나」 싶어 **잉크**(검은 정도의 합)로

| | 400 | 700 | 차이 |
|---|---|---|---|
| **실린 Plex — 한글** | 922.9 | 1568.5 | **+70.0 %** |
| **대체 서체 — 한글** | 961.1 | 1486.6 | **+54.7 %** |

**대체 서체에서도 굵기는 작동하고 있었다.** 폭이 안 변한 것은 굵은 판이 없어서가

|---|---|
| IBM Plex 가 한 번도 실린 적이 없다 | **맞다** — CDP·폭 둘 다, 그리고 실으니 바뀌었다 |

**이 항목이 UF-7 이 경고한 실수를 스스로 범했다.** UF-7 은 「대리 지표로 재면 안

쓴 줄 몰랐다** — 위 인용구에서 「**폭 비교가 증거다**」라고 단언했다. 폭은

서체를 실은 것은 여전히 옳다 — 자형·조판이 의도한 것이 되고, 굵기 대비가 세지고,
기계마다 다르던 화면이 같아진다. 다만 **「위계가 없었다」가 아니라 「약했고, 의도한
서체가 아니었다」**가 맞는 서술이다.

### 남은 것

**어떤 서체를 실을지는 이 항목이 정하지 않는다** — UD-9 다. 여기까지는 「지금 것이
안 실린다」와 「한글 굵기가 죽어 있다」까지다.

## UF-7. 스윕 잔광 검사가 **잔광이 아니라 파형을 재고 있었다** — 화면은 설계대로였다

| | |
|---|---|
| 상태 | **확정** `[측정]` — 세 번 반복, ±0.5 |
| 발견 | UO-4 의 빨강(`test_sweep_glows_behind_the_cursor`)을 고치려고 탐침을 뜯어 보다가 |
| 영향 | 검사 하나를 다시 썼다. **화면 코드는 한 줄도 안 고쳤다** |

### 발단

검사는 커서 뒤 두 띠 — 바로 뒤 `(−60, −10)` 과 더 뒤 `(−180, −130)` — 에서
**밝은 픽셀(L > 80)의 개수**를 세어 앞쪽이 더 많아야 한다고 했다. 실패 메시지는
「바로 뒤 238 가 먼 쪽 246 보다 진하지 않다」였고, 병합 전 커밋에서도 소수점까지
같았다(UO-4).

### 먼저 의심한 것 — 그리고 그것이 틀린 지점

「**잔광 코드가 죽었다**」고 보았다 — 꼬리를 매 프레임 지우고 다시 그리는 자리
(`sweepPanel` 의 `xTail >= 0` 분기)가 안 타거나, 다크 판정 `--dark` 가 어긋난 줄
알았다. **틀렸다.** 탐침에 진단을 붙여 보니 `dark: "1"`, `toned: #f3a789`,
`tailPx: 79.4` 로 전부 정상이었다. 죽은 것은 화면이 아니라 **재는 방법**이었다.

### 결정적 측정 `[측정]`

**1. 개수는 파형이 정한다.** 같은 프레임에서 20 px 띠마다 ink 를 찍었다:

```
[-200..-180]  54.2
[-180..-160] 158.2   ← R 피크 하나
[-160..-140]  48.2
[ -40.. -20] 176.2   ← R 피크 하나
[ -20..  +0]  57.9
```

띠 하나에 R 피크가 들면 **48 → 158, 3 배**다. 꼬리 톤업이 만드는 차이는 그보다
훨씬 작다. 어느 띠에 피크가 걸리느냐는 커서 위치가 정하고, 13 초 뒤 커서 위치는
결정론적이다 — 그래서 **매번 같은 값으로 빨갰다.**

**2. 참값 회색선이 최댓값을 차지한다.** 열마다 칠해진 픽셀의 최대 L 을 보니
`181.8` 이 꼬리 밖에도 여기저기 찍혔다. `--role-clean` `#b8b6ae` 의 L 이 정확히
**181.9** 다. 참값은 톤업을 안 받으므로(설계 — 「목표가 발광하면 주객이 바뀐다」)
참값이 켜져 있으면 **잔광이 있어도 열의 최댓값은 안 움직인다.**

**3. 주장을 그대로 재니 선명했다.** 참값을 끄고, **같은 60 열**을 커서 바로 뒤에
있을 때와 2 초 뒤(커서 ≈380 px 전진)에 두 번 쟀다:

| 회 | 커서 뒤 평균 L | 2 초 뒤 | 낙차 |
|---|---|---|---|
| 1 | 154.1 | 129.3 | +24.9 |
| 2 | 154.9 | 129.3 | +25.6 |
| 3 | 154.8 | 129.3 | +25.5 |

`#eb6834` 의 순수 L 이 **128.1** 이다. 멀어진 뒤 129.3 은 **정확히 평소 색**으로
돌아온 것이고, 커서 뒤 155 는 `GLOW_DARK = 0.42` 만큼 흰 쪽으로 섞인 것이다.
**잔광은 설계대로다.**

### 놓쳤다면

「잔광이 안 된다」로 읽고 화면 코드를 손댔을 것이다 — 이미 두 번 그랬다
(`GAP` 을 50 % → 22 % 로, 커밋 `85efd07`). 되는 것을 고치면 다른 것이 깨지고,
검사는 여전히 빨갛다. **탐침이 틀린 채로는 몇 번을 고쳐도 초록이 안 된다.**

UF-2 · UF-6 과 한 줄이다: **대리 지표로 재면 안 된다.** 문자열 유무(UF-2),
스택에 이름이 있는지(UF-6), 밝은 픽셀 개수(UF-7) — 셋 다 「그것」이 아니라
「그것과 상관 있어 보이는 것」을 쟀다.

### 남은 것

검사를 다시 썼다 — 참값을 끄고, 개수 대신 밝기를, 다른 띠 대신 **같은 열**을
두 번 본다(`tests/test_demo_screens.py`). 되돌릴 조건: 세 번 돌려 한 번이라도
흔들리면 대기 시간(2 s)이나 열 범위를 고치지 **탐침 방식을 되돌리지는 않는다.**

## UF-8. **외부 레퍼런스가 이 환경에서 통째로 막혀 있다** — Director A 의 먹이가 없다

| | |
|---|---|
| 상태 | **확정** `[측정]` — 정책이지 고장이 아니다 |
| 발견 | UD-10 뒤 첫 「새 디자인 라운드」에서 Director A 의 L1 캡처를 준비하다가 |
| 영향 | UD-10 의 되돌릴 조건 하나가 **발동**했다 · `04_tools` capability 표 · 이번 라운드의 구성 |

### 발단

UD-10 은 레퍼런스 카드마다 **L1 캡처 의무**를 뒀다 — 「링크가 죽어도 카드가 산다」.
그리고 그 자리에 「아직 안 쟀다 `[추론]`」를 남겨 뒀다. 첫 라운드에서 쟀다.

### 먼저 의심한 것 — 그리고 그것이 틀린 지점

「**JS 렌더 사이트라 헤드리스가 본문을 못 읽는 것**」이라고 봤다(UD-10 §11 ⑥ 에 그렇게
적었다). 그래서 `--virtual-time-budget` 을 주고 찍었다. **틀렸다.** 찍힌 PNG 셋이
29~31 KB 로 크기가 비슷했고, 열어 보니 셋 다 **크롬의 「This site can't be reached」**
화면이었다. 렌더 문제가 아니라 **연결이 아예 안 된 것**이다.

### 결정적 측정 `[측정]` 2026-09-19

`curl` 로 다시 치니 전부 `http=000`. 프록시 상태 끝점이 이유를 적어 뒀다:

```
kind: connect_rejected
detail: "gateway answered 403 to CONNECT (policy denial or upstream failure)"
host: www.awwwards.com:443 · godly.website:443 · eyes.nasa.gov:443
      pudding.cool:443 · developer.mozilla.org:443
```

| 경로 | 결과 |
|---|---|
| 컨테이너 `chrome --screenshot` | **403** (CONNECT 거부) |
| 컨테이너 `curl` (명시적 `--proxy` + CA 포함) | **403** |
| 하니스 `WebFetch` | **`EGRESS_BLOCKED`** — 같은 정책 |
| `github.com` | **열린다** (`http=400` = 깃허브가 답한 것 → 터널은 섰다) |
| **MDN — MCP 커넥터** | **열린다.** `developer.mozilla.org` 는 컨테이너에서 403 인데 커넥터로는 답한다 |

마지막 줄이 중요하다: **「호스트가 막혔다」와 「capability 가 없다」는 다르다.**
커넥터는 다른 길이고, 그 길은 정책이 허용한 길이다.

### 놓쳤다면

`[추론]` 으로 남겨 둔 칸을 안 재고 A 를 돌렸으면, **기억으로 레퍼런스를 썼을 것이다** —
URL 은 그럴듯하고, 「어디를 볼지」도 쓸 수 있고, 사용자는 열어 보고서야 안다.
`expo-ui-art-director` 가 「기억으로 발산하지 않는다」를 첫 줄에 둔 이유가 이것이다.
카드 규격이 **L1 캡처를 의무로** 둔 덕에 발산 전에 걸렸다.

### 남은 것

**우회하지 않는다** — PhysioNet 403 과 같은 계열이다(CLAUDE.md). 대신 길을 나눈다:

- **Director B 는 여기서** 돈다 — 코드베이스·토큰·캡처가 먹이라 네트워크가 필요 없다.
- **Director A 는 로컬 세션에서** 돈다. 이 막힘은 **이 클라우드 환경의 egress 정책**이지
  저장소의 것이 아니다. 로컬은 그 프록시 뒤에 있지 않다.
- **그 분리가 UD-10 의 모델 분리보다 나은 격리다** — 다른 세션·다른 문맥이라
  1 차 패스의 오염 경로가 구조적으로 없다. UD-11 에 그렇게 적었다.
- 로컬 A 가 지킬 것 하나: **`docs/ui/10_decisions.md` 의 UD-11 B 절을 카드가 끝나기
  전에 열지 않는다.** 그것만이 남은 오염 경로다.

### 추기 (2026-09-20) — **디자인 도구의 API 도 같은 문 뒤에 있다** `[측정]`

레퍼런스 호스트만의 일이 아니었다. Superdesign 을 다시 보면서 재 봤다:

| 호스트 | 결과 |
|---|---|
| `api.superdesign.dev:443` | `gateway answered 403 to CONNECT` |
| `superdesign.dev:443` | 같음 — **가격 페이지를 못 읽는다** |
| `eu.i.posthog.com:443` | 같음 (그쪽 텔레메트리) |
| `registry.npmjs.org` | **열린다** — `noProxy` 목록에 있다. `npm pack` 으로 패키지를 열어 볼 수는 있었다 |

그래서 **패키지는 읽을 수 있고 서비스는 못 부른다.** 이 구분이 UD-12 의 판정을 갈랐다 —
기능 목록은 `[문헌]`·`[코드]` 로 확정했지만 **가격은 `기록 없음`** 으로 남는다.

**따라서 Director B 도 로컬로 간다.** 라운드 ① 에서는 B 가 여기서 돌 수 있었다(도구가
`frontend-design` 하나였으니 네트워크가 필요 없었다). Superdesign 을 쓰는 순간 **A·B 가 둘 다
로컬**이고, 격리는 「클라우드 ↔ 로컬」이 아니라 **「로컬 세션 두 개, 서로 다른 작업 폴더」**로
내려간다. 그 격리 조건을 UD-12 되돌릴 조건에 적었다.

### 추기 2 (같은 날) — **「통째로」가 틀렸다. GitHub 갈래는 열려 있고 이미지를 볼 수 있다** `[측정]`

이 항의 제목은 「외부 레퍼런스가 이 환경에서 **통째로** 막혀 있다」다. 사용자가 허브
사이트를 주겠다고 해서 다시 쟀더니 **통째로가 아니었다.**

| | |
|---|---|
| `awwwards.com` · `godly.website` · `siteinspire.com` · `land-book.com` | **전부 `000`** — 디자인 갤러리는 정말 다 막혔다 |
| `github.com` (HTML) | `400` / `403` |
| **`api.github.com`** | **`200`** |
| **`raw.githubusercontent.com`** | **`200`, 이미지도** — `.../react.png` 을 받아(41,453 B · `image/png`) **실제로 열어서 봤다** |

**「받았다」와 「봤다」는 다르다.** 이 항목을 세울 때 잰 것은 **텍스트 가져오기**였고
**이미지를 열어 보는 것**은 안 재 봤다. 재 보니 된다.

**그래서 B 에게 갈래가 하나 더 있다** — **GitHub 을 허브로 쓰는 레퍼런스 라운드.**
`api.github.com` 으로 찾고 README 의 스크린샷·데모 GIF 를 `raw` 로 열어 본다.
계정도 로컬도 필요 없고 **오늘 여기서 된다.** 갤러리가 아니라 오픈소스라
「craft · wow」 칸은 약하고 **「계측·시각화의 실제 구현」 칸은 강하다.**
A 도 B 도 안 쓴 갈래다 (`02_benchmark` §8.2.1 ⓐ-2).

**규칙으로**: 「막혔다」를 적을 때 **무엇을 재서 막혔다고 하는지** 적는다. 호스트 하나가
막힌 것과 **그 경로의 모든 형식**이 막힌 것은 다르다 — 이 항목은 그 둘을 한 문장으로 적었고,
그래서 라운드 ①·② 두 번 다 **쓸 수 있는 갈래를 안 썼다.**

## UF-9. 화면 캡처 도구가 **윈도우에서 두 곳 깨진다** — 로컬 디렉터가 넘긴 것

| | |
|---|---|
| 상태 | **확정 · 안 고쳤다** `[대화]` — 로컬 세션이 실측해 넘겼고, 이 세션은 윈도우가 없어 재현 못 한다 |
| 발견 | 라운드 ① 에서 Director A 를 **로컬 Windows 11** 에서 돌리다가 |
| 영향 | `scripts/shoot_screens.py` 를 윈도우에서 쓰는 모든 경우 |

### 발단

UD-11 의 A 를 로컬에서 돌리려면 레퍼런스 장면을 찍어야 한다(UD-10 의 L1 캡처 의무).
그 기계에서 `scripts/shoot_screens.py` 가 두 곳에서 걸렸다 `[대화]`.

### 먼저 의심한 것 — 그리고 그것이 틀린 지점

이 세션은 **「로컬이면 그냥 된다」**고 봤다 — UF-8 에서 막힌 것이 egress 정책이었으니
네트워크만 뚫리면 끝이라고 읽었다. **반쯤 틀렸다.** 네트워크는 뚫렸는데 **도구가 안
돌았다.** 이 컨테이너가 리눅스 + Chromium 이라 그 조합만 밟아 봤고, 스크립트가
**다른 OS 에서 어떻게 죽는지는 한 번도 안 봤다.**

### 결정적 측정 `[대화]` — 로컬 세션이 적어 보낸 것

| 무엇 | 증상 |
|---|---|
| `find_chromium()` | **Edge 를 못 찾는다.** PATH 의 `chromium`·`chromium-browser`·`google-chrome`·`chrome` 만 본다. 그 기계에 Chrome 이 없고 **Edge 153** 만 있었다 — 같은 Chromium 계열이라 실제로는 쓸 수 있다 |
| 마지막 요약 줄 | **`UnicodeEncodeError`** — cp949 콘솔에 `—`(em dash)를 찍다가 죽는다. **캡처 파일은 그 전에 저장된다** |

로컬 세션은 **저장소 코드를 안 고치고** 스크립트 밖에서 실행 파일 경로를 바꿔 끼워
돌렸다. 그래서 캡처 7 장은 정상이다.

### 놓쳤다면

「로컬에서 A 를 돌려라」만 적어 보냈으면 그 세션이 **캡처를 포기하거나**, 더 나쁘게는
**코드를 고쳐 돌렸을 것이다** — 그러면 이 라운드의 산출물에 의도하지 않은 코드 변경이
섞인다. 지시문에 「캡처가 안 되면 실패했다고 카드에 적어라. 지어내지 마라」를 넣어
둔 덕에 **막힌 것이 기록으로 돌아왔다.**

### 남은 것

고치는 것은 **이 항목이 아니다** — 재현할 기계가 없다. 고칠 때 볼 것 둘:

1. `find_chromium()` 에 **Edge 를 더한다**(`msedge` · `%ProgramFiles%\\Microsoft\\Edge\\...`).
   Chromium 계열이면 Playwright 가 그대로 띄운다 — 로컬 세션이 실증했다.
2. 콘솔 출력의 **비 ASCII 를 안전하게** 낸다(`errors="replace"` 또는 ASCII 요약).
   **캡처가 끝난 뒤에 죽는 것**이라 조용히 「실패」로 읽힌다 — 더 나쁜 종류다.

둘 다 **윈도우 기계에서 확인한 뒤에** 고친다. 이 세션에서 고치면 못 재현하는 수정이 된다.

## UF-10. 「3 m 에서 읽힌다」가 **판정 불가능한 조건**이었다 — 화면 인치가 문서에 없다

| | |
|---|---|
| 상태 | **확정** `[측정]` · 값은 사용자가 정할 것 |
| 발견 | UD-11 의 A5·A6 을 판정하려고 「3 m 가독」을 px 로 옮기다가 |
| 영향 | A5·A6 의 크기 · UD-6 #6 · UD-9 의 L4 · `02_benchmark` §10 |

### 발단

UD-11 의 A5 「재생 시계」와 A6 「숫자 한 개」는 둘 다 **글자가 전부**인 후보다.
판정 조건에 「3 m 가독」을 걸어 뒀는데, 막상 재려니 **px 로 못 옮겼다.**

### 먼저 의심한 것 — 그리고 그것이 틀린 지점

「**서체가 안 실려서 못 재는 것**」이라고 봤다(UF-6). 서체를 실으면 판정할 수 있다고
UD-11 에 적었고, 사용자에게도 그렇게 말했다. **반만 맞았다.** 서체를 실으니 폭은
재게 됐는데, **「3 m 에서 몇 px 여야 하나」는 서체가 아니라 화면 크기가 정한다.**

### 결정적 측정 `[측정]`

시각 관례(10 arcmin = 읽을 수 있음)를 3 m 에 대고 `font-size` 로 옮기면:

| 대각선 | 3 m 읽기 최소 |
|---|---|
| 13.3" | **81 px** |
| 15.6" | **69 px** |
| 27" | **40 px** |

**13.3" 와 27" 가 두 배 차이다.** 그런데 UD-1 의 표시 규격은
「**노트북 1920×1080** (최소 방어폭 1280×720)」까지만 적고 **인치가 없다.**
해상도는 레이아웃을 정하고 **인치는 가독을 정하는데**, 둘째가 비어 있었다.

곁가지로 하나 더 드러났다: `layout_b` 의 `--t-tick` 은 **13 px** 로,
표의 **어느 줄에서도 3 m 판독(5′)에 못 미친다** — 20 px 도 안 된다.

### 놓쳤다면

A5 를 「69 px 로 하면 된다」고 적고 넘어갔을 것이다. 부스 노트북이 13.3" 면
**81 px 가 필요한데 69 px 로 만들어 놓고 「3 m 에서 읽힌다」고 문서에 적혀 있는**
상태가 된다 — L4 에서야 드러나고, 그때는 이미 레이아웃이 그 크기로 짜여 있다.

### 남은 것

**사용자 답 (2026-09-19)** `[대화]`: 「**미정(여러 기기 가능). 일단 15.6 가정해.**」
→ **15.6" · 3 m 읽기 69 px** 를 쓰되 **가정으로 표시한다.** 크기를 화면에 박지 않고
토큰 `--t-far` 하나에 두어, 기기가 정해지면 한 줄로 바꾼다. 13.3" 면 81 px 다.
**「여러 기기 가능」이라는 답 자체가 설계 조건이다** — 어느 한 인치에 맞춘 픽셀값을
여기저기 흩뿌리면 기기가 바뀔 때 전부 찾아다녀야 한다.

원래 적었던 것: **박람회 노트북의 인치를 정해야 한다.** 사용자만 답할 수 있다. 정해지면:
`docs/ui/01_system.md` 의 표시 규격에 인치를 더하고, `02_benchmark` §10 표에서
해당 줄을 골라 HIGH 구역 글자 크기의 하한으로 쓴다.
정해지기 전에는 **가장 빡빡한 13.3"(81 px)** 를 가정한다 — 크게 만든 것은 줄일 수
있지만 작게 만든 것은 L4 에서 다시 짜야 한다.

## UF-11. 플러그인 셋이 꺼져 있었다 — **하나는 무관했고, 하나는 진짜였다**

사용자 `[대화]`: 「방금 확인해봤는데 superdesign, playground, frontend design 플러그인이

**조직 카탈로그에 없다고 없는 것이 아니다.**

## UF-12. `[측정]` 태그가 **어디서 쟀는지를 안 담았다** — 그래서 틀린 사실이 지시문에 실렸다

### 발단

라운드 ④ 를 돌린 로컬 세션이 브리프를 열자마자 `dir_B.md` 1.1 에 이렇게 적었다 `[측정]`:

| 허브 | `02_benchmark` §14 (내가 적은 것) | **로컬(실제)** |
|---|---|---|
| `minimal.gallery` | `000` | **200** — 태그 70 여 개, 페이지 131 |
| `land-book.com` | `000` | **200** — Websites / Sections / Mobile / **Motion** / OG Images / Headlines |
| `behance.net/galleries/ui-ux` | `000` | **200** — 검색까지 |

§14 는 이것을 **`[측정]` (2026-09-20)** 으로 적었다. 측정 자체는 맞았다 — **클라우드 세션에서는**
정말 `000` 이었다. 틀린 것은 **그 사실이 어디에서 참인지를 안 적은 것**이다.

### 먼저 의심한 것

「사이트가 그 사이에 막혔다가 풀렸나」 — **아니다.** 두 측정 사이는 사흘이고, 셋이 동시에
막혔다 풀릴 이유가 없다. **같은 시각에 두 환경에서 값이 달랐던 것**이다.

### 결정적 측정 `[측정]`

세 허브는 **클라우드에서 `000`, 로컬에서 `200`.** 같은 URL, 다른 컨테이너.
이 저장소는 이 구분을 **이미 한 번 배웠다** — UF-8 이 「호스트가 막혔다」와 「capability 가
없다」는 다르다고 적었고(MDN 이 컨테이너에선 403 인데 커넥터로는 답한다), 추기 2 가
「**받았다**와 **봤다**는 다르다」를 적었다. 이번은 **셋째 축**이다: **「여기서 막혔다」와
「막혔다」는 다르다.**

세 번 다 같은 실수의 다른 얼굴이고, 공통점은 **측정의 범위를 문장이 안 담은 것**이다.

### 놓쳤다면

로컬 세션이 §14 를 **그대로 믿었으면 라운드 ④ 를 아예 안 돌렸을 것이다.** 지시문이
「셋 다 `000`」이라고 단언했으니 열어 볼 이유가 없다. **틀린 사실이 지시문에 실리면
다음 실행자가 시도 자체를 안 한다** — 그 손실은 조용하고, 기록에도 안 남는다.

### 규칙으로 승급

**`[측정]` 은 「무엇을」과 **「어디서」**를 같이 적는다.**

- 네트워크·도구 가용성을 적을 때는 **환경 이름**을 문장 안에 넣는다 —
  「`000`」이 아니라 「**클라우드 세션에서** `000`」.
- 브리프·지시문에 넣을 때는 더 세게: 다른 환경에서 돌 사람이 읽는 글이므로
  **「거기서는 다를 수 있다. 먼저 재 봐라」**를 붙인다.
- 이미 적힌 것 중 같은 성질의 것: UF-8 본문과 추기 1·2, `04_tools` 의 RESEARCH 행.
  **전부 「이 환경」이라는 말을 이미 달고 있다** — 빠진 것은 §14 하나였다. 고쳤다.

## UF-13. `layout_b` 가 **42/98 장면을 라벨보다 낮은 이득으로** 그린다 — 라벨은 `10 mm/mV`, 실제는 4.3~8.6

### 발단

라운드 ①~④ 의 후보 20 개를 검증기 넷에 대 보던 중이었다(UD-18). E1(98 타일 격자)의 타일이
진폭을 담을 수 있는지 보려고 **은행의 실제 진폭**을 쟀다. 네 라운드 내내 레인 예산을
「**±1.0 mV = 75.9 px**」로 적어 왔는데, 그 가정이 몇 장면에 맞는지 한 번도 안 쟀다.

### 먼저 의심한 것

「타일이 작아서 잘리겠지」 — **그보다 컸다.** 가정이 후보만이 아니라 **지금 화면**에도
깔려 있었다.

### 결정적 측정 `[측정]`

**① 장면마다 세로 창이 다르다** — `layout_b` 는 `snapMv(s.ylim)` 으로 창을 정한다:

| 창(±mV) | 1.0 | 1.5 | 2.0 | 3.0 | 4.0 |
|---|---|---|---|---|---|
| 장면 수 | **7** | 49 | 21 | 14 | 7 |

「±1.0 mV」 가정이 맞는 장면은 **98 중 7** 이다.

**② 레인이 작으면 이득을 몰래 줄인다** — `demo/ui/layout_b.html` `draw()`:

```js
const scaleY = Math.min(h / 2 / halfPx, 1) * state.gain * PX_MM;   // ← 1 을 넘지 않는다
```

`halfPx = mv × gain × px/mm` 가 레인 반높이보다 크면 배율이 1 아래로 떨어진다. 주석은
「화면 높이가 남으면 이득을 올려 채운다」인데 `Math.min(…, 1)` 은 **올리는 일이 없고
줄이기만** 한다. 그리고 footer 는 `state.gain` 을 찍는다 — **명목값**이다.

**브라우저에서 재 봤다** (Chromium · 1920×910 · `layout_b` 그대로 · 레인 plot 130 px):

| 축 | 유효 이득 < 10 인 장면 | 유효 이득 분포 | 그때 화면 라벨 |
|---|---|---|---|
| d0 | **7 / 49** | 8.6 ×7 · 10 ×42 | `10 mm/mV` |
| d1 | **35 / 49** | **4.3** ×7 · 5.73 ×14 · 8.6 ×14 · 10 ×14 | `10 mm/mV` |

**42/98 장면에서 라벨이 거짓이다.** 가장 나쁜 d1 7 장면은 **43 %** 이득으로 그려진다.
그리고 **격자는 mm 로 고정**(`--bold` = 5 mm)이라, 그 장면들에서 **대칸 하나가 0.5 mV 가
아니다** — R-A 가 「세어서 읽을 수 있다」고 한 그 격자가 파형과 어긋난다.
MIT-BIH(d1)가 훨씬 나쁜 것은 실제 기록의 진폭이 크기 때문이다.

**③ 잘림** — 입력이 창을 넘는 장면 **17/98**(최대 표본 1.3 %, 대부분 impulse·근전도 스파이크).
**참값은 0/98** 로 안 잘린다 — 잘리는 것은 잡음뿐이다. 다만 `Math.max(-mv, Math.min(mv, v))`
로 **표시 없이** 평평하게 눌린다.

### 놓쳤다면

지금 화면의 결함으로 끝나지 않는다. **라운드 ①~④ 의 레인 예산이 전부 ±1.0 mV 를 가정했다**
— A4 `7×75.9 = 531 px`, E4 `523.5 px`, E1 타일 `0.98 s`, UD-11 변경 계약의 「레인 240 px(신호 76)」.
그 숫자들을 그대로 구현하면 **이 코드가 모자라는 만큼 이득을 몰래 줄여 맞춰 준다** —
화면은 멀쩡해 보이고, 라벨은 10 을 말하고, 검사는 통과한다. 발표장에서 누가 격자를 세어
보기 전까지 아무도 모른다.

### 규칙으로

- **한 화면(한 격자) 안의 레인은 같은 이득이고, 라벨은 실제 이득을 말한다.** 이득을 몰래
  줄이지 않는다 — 모자라면 **잘리되 잘린 표시**를 달거나, 이득 칩(5/10/20)을 **보이게** 바꾼다.
- **레인 예산은 ±1.0 mV 가 아니라 그 화면이 보일 장면들의 창으로** 잡는다.
- 이 결함의 고침은 **UD 를 먼저**(화면 고치기) — 여기서는 기록만 한다.

### 추기 (2026-09-24) — **고쳤다** (UD-19 ⓐ) · 고치다가 **더 넓었다**는 것이 드러났다 `[측정]`

footer 가 **실제로 그린 이득**과 그 이득에서 대칸이 뜻하는 mV 를 적는다. 줄었으면
「(10 에서 줄임)」을 붙인다. 레인 사이 이득은 가장 낮은 레인으로 **하나**로 계산한다.

**원래 적은 것보다 넓었다** — 「대칸 × 0.5 mV」가 **문자열로 박혀** 있었다. 격자는 mm 고정이라
5 칩이면 대칸이 1 mV 인데도 0.5 를 적었다. 그리고 레인이 작은 화면일수록 더 많이 줄어든다.
고친 뒤 **줄어드는 장면 수**(= 고치기 전에 라벨이 거짓이던 수), Chromium:

| 뷰포트 | 5 칩 | 10 칩 | 20 칩 |
|---|---|---|---|
| 1920×910 | 7 / 98 | **42 / 98** | **98 / 98** |
| 1280×720(최소 방어폭) | 42 / 98 | **98 / 98** | 98 / 98 |

→ **최소 방어폭에서는 기본 칩(10)으로 98 장면 전부가 라벨과 다르게 그려지고 있었다.**
20 칩은 1920 에서도 **한 장면도 20 으로 그려진 적이 없다.**

**고친 뒤** — 294 경우(칩 3 × 장면 98) × 두 뷰포트 전부 **라벨 = 실제**, footer 넘침 0,
콘솔 오류 0. 가장 긴 라벨은 84 자(`… 11.5 mm/mV (20 에서 줄임) · 대칸 0.10 s × 0.44 mV …`).
d1 ±4 mV 장면을 찍어서 **눈으로 봤다** — footer 에 `4.3 mm/mV (10 에서 줄임) · 대칸 0.10 s × 1.16 mV`.

**검사** `test_gain_label_tells_the_gain_actually_drawn` — 라벨을 공식이 아니라 **캔버스의
잉크 폭**과 대 본다. **고치기 전 코드로 돌리면 실패한다**: 「라벨 10.0 mm/mV 면 272.1 px 여야
하는데 그려진 폭은 115.0 px 다」. 고친 코드로 되돌리면 통과. 검사가 문다.

**아직 안 고친 것**: 잘림(17/98, 입력 스파이크, 표시 없이 눌림)은 ⓑ 의 일이라 그대로다.

## UF-14. 파형 선의 **이음(miter)이 뾰족한 꼭짓점을 최대 +5 px 부풀린다** — R 파가 실제보다 높게 그려진다

### 발단

UF-13 을 고치고 검사를 쓰던 중이었다(UD-19). 라벨의 이득이 그림과 맞는지 보려고 입력 레인의
**잉크 세로 폭**을 재서 「보이는 표본의 극값 × 이득」과 견줬는데, 대부분 ±1~2.6 px 인 차이가
**d0-pli-0 · 5 칩에서만 +5.04 px** 였다(잉크 45 px, 기대 40.0 px).

### 먼저 의심한 것

「선 굵기(1.2 px)와 안티앨리어싱」 — **그것만으로는 +5 px 가 안 나온다.** 선 굵기는 위아래로
합쳐 1.2 px 이고 다른 장면들은 그 근처였다. 뾰족한 R 피크에서만 튄다 → **꼭짓점의 이음**을 의심했다.
캔버스 2D 의 기본 `lineJoin` 은 `miter` 이고, 예각에서 이음이 선 굵기의 여러 배로 뻗는다.

### 결정적 측정 `[측정]`

같은 장면·같은 이득에서 **이음만 바꿔** 쟀다 (Chromium, 입력 레인, 참값 끔):

| 이음 | d0-pli-0 · 5 칩 | d0-pli--5 · 5 칩 | d0-pli-0 · 10 칩 |
|---|---|---|---|
| **miter**(지금) | 잉크 45.0 / 기대 40.0 → **+5.04 px** | +2.63 px | +1.09 px |
| **round** | 41.0 / 40.0 → **+1.04 px** | +0.63 px | +1.09 px |

**원인은 miter 다.** 50 mm/s 에서 표본 간격이 **0.76 px** 라 R 피크가 극단적인 예각이 되고,
miter 가 그 꼭짓점을 위로 뾰족하게 늘린다. 5 mm/mV 에서 +4 px 는 **약 0.2 mV** 다 —
가는 바늘 모양이라 눈에 띄지는 않지만, **파형이 실제 진폭보다 높은 곳까지 잉크를 찍는다.**

### 놓쳤다면

「세어서 읽는 격자」(R-A) 위에서 R 피크 끝이 실제보다 대칸 한두 개의 몇 분의 일만큼 높게
찍힌다. 방법 비교는 같은 조건끼리라 결론이 뒤집히지는 않는다 — 하지만 **이 과제가 경계하는
「그리기가 데이터를 바꾸는 것」**의 작은 사례이고, 이것을 몰랐다면 UD-19 의 검사가 이득이 아니라
꼭짓점 그리기를 재서 **이유 없이 빨갛거나 이유 없이 초록**이었을 것이다. 검사는 이 때문에
**사인파**로 잰다 — 마루가 평평해 이음이 안 튄다.

### 조치

**여기서는 기록만 한다.** 파형 스타일은 LOW 구역이고, 바꾸려면 UD 가 먼저다(`ecg-ui-validator`:
「파형 스타일 — L3 + 작은 굴곡 가독성(픽셀 측정)」). 후보 고침은 `g.lineJoin = "round"` 한 줄 —
위 표대로 +1 px 로 줄어든다. `live.html`(`demo/live_axis.js` 계열)의 레인 렌더러도 같은 기본값을
쓰는지 함께 봐야 한다.
