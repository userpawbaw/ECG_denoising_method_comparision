## UO-1. 한글 폰트가 없는 환경에서 그림을 만들어 **tracked 산출물을 깨진 것으로 덮어썼다**

| | |
|---|---|
| 시점 | UD-1 1 단계 — 팔레트 원본으로 전환한 뒤 「스크립트가 아직 도는가」를 확인하려고 |
| 상태 | **되돌림** (`git checkout`). 규칙은 이미 있었고 내가 안 지켰다 |

### 무엇을 했나

`python3 scripts/make_slides.py --only S5` 를 돌렸다. 목적은 **import 전환이
깨지지 않았는지 확인**하는 것이었는데, 이 스크립트는 확인만 하지 않는다 —
**그리고 저장한다.**

결과:

```
UserWarning: Glyph 51020 (HANGUL SYLLABLE EUM) missing from font(s) DejaVu Sans.
  S5_crossover.png
  docs/93_slides.md
```

이 컨테이너에는 한글 폰트가 없다. 그래서 **한글이 전부 두부(□)로 깨진 그림**이
`results/slides/S5_crossover.png` 를 덮었고, `docs/93_slides.md` 와
`results/slides/manifest.json` 까지 함께 바뀌었다. 셋 다 tracked 다.

### 어긋난 규칙 — 둘 다 CLAUDE.md 에 있었다

| 규칙 | 어떻게 어겼나 |
|---|---|
| **그림을 만들 때**: 저장 전에 검사하고 **눈으로 본다** | 저장하고 나서야 경고 줄을 읽었다. 그림을 열어 보지 않았다 |
| **산출물을 지우거나 덮어쓸 때**: tracked 산출물은 **새 것이 완성된 뒤에** 교체한다 | 「완성된 새 것」이 아니라 **깨진 것**으로 덮었다 |

### 왜 일어났나

**확인과 생성을 같은 명령이 한다.** 「import 가 깨졌나」를 묻고 싶었는데
`make_slides.py` 에는 그 질문만 하는 모드가 없다. `--only S5` 는 가장 작은
단위였을 뿐 여전히 **저장하는** 명령이다.

그리고 환경이 달랐다 — 이 컨테이너는 그림을 만들라고 준비된 곳이 아니다.
한글 폰트가 없다는 것을 **그림을 만들고 나서** 알았다.

### 조치

1. 즉시 되돌렸다 — `git checkout -- results/slides/S5_crossover.png
   results/slides/manifest.json docs/93_slides.md`.
2. **import 확인은 `ast.parse` 와 `import _palette` 로 한다.** 실제로 그 둘이
   먼저 통과했고, 그림 생성은 필요하지 않은 확인이었다.

### 규칙으로 승급시킬 것

> **그림 생성 스크립트는 「확인용」으로 돌리지 않는다.** 코드가 도는지 보려면
> `ast.parse`·`import`·`pytest` 를 쓴다. 그림을 만들어야 한다면 **한글 폰트가
> 있는 환경인지 먼저 확인**하고, 저장된 결과를 **열어 본** 뒤에 커밋한다.

이 저장소의 그림 산출물은 발표와 보고서에 그대로 들어간다. 깨진 그림이 조용히
섞이면 **커밋 이력만으로는 드러나지 않는다** — PNG diff 는 사람이 안 읽는다.

### 놓쳤다면

`S5_crossover` 는 `docs/34_visual_plan.md` 가 「**가장 설득력 있는 그림**」 계열로
꼽은 것 중 하나이고, 보고서 5.8.2 의 교차점 주장을 그대로 싣는다. 한글 라벨이
전부 두부로 바뀐 채 발표에 들어갔을 수 있다.

## UO-2. `pytest … | tail` 이 종료 코드를 가려서 **실패한 검사를 통과로 읽고 커밋·푸시했다**

| | |
|---|---|
| 시점 | 외부 UI/UX 시스템 검토서(`docs/ui/03_external_system_review.md`)를 커밋하면서 |
| 상태 | **바로잡음** — 실패 원인(없는 파일을 교차 참조)을 고친 커밋이 뒤따른다 |

### 무엇을 했나

「검사가 통과하면 커밋한다」를 한 명령으로 이었다:

```
python3 -m pytest tests/ -q 2>&1 | tail -6 && git add … && git commit … && git push …
```

pytest 는 **1 failed, 580 passed** 였다 — `test_doc_cross_references_resolve` 가
검토서 9 절의 가칭 `04_creative_data_motion.md` · `13_ai_collaboration.md` 를
**존재하지 않는 파일**로 잡았다(제안 단계의 이름을 실제 경로 형식으로 적었다).
그런데 `&&` 는 파이프라인의 **마지막 명령(`tail`)의 종료 코드**를 본다. `tail` 은
성공했고, 커밋과 푸시가 그대로 나갔다 `[로그]`.

### 어긋난 규칙

| 규칙 | 어떻게 어겼나 |
|---|---|
| CLAUDE.md 「커밋 전 `pytest tests/`」 | 돌리긴 했다. **결과를 읽지 않고 셸이 읽게 했는데, 셸이 보는 값이 틀렸다** |

### 왜 일어났나

출력을 줄이려고 `| tail` 을 붙였고, 파이프라인의 종료 코드가 마지막 명령의 것이라는
것을 잊었다. 검사와 커밋을 한 줄로 이은 것 자체는 좋은 습관이다 — **이음새가 틀렸다.**

### 조치

1. 검토서의 두 참조를 「제안 이름」임이 드러나는 형식으로 고쳤다 — 경로가 아니라
   가칭으로 적는다.
2. 다시 `pytest tests/` 를 돌려 **전부 통과를 눈으로 확인한 뒤** 커밋했다.

### 규칙으로 승급시킬 것

> 검사와 커밋을 한 줄로 이을 때 **`| tail` 을 쓰면 `set -o pipefail` 을 먼저 켠다.**
> 아니면 검사를 따로 돌려 요약 줄(`N passed`)을 **직접 읽고** 커밋한다.

이 검사(`test_doc_cross_references_resolve`)가 잡은 것은 진짜 결함이었다 — 아직 없는
파일을 있는 것처럼 가리키면 다음 세션이 그 파일을 찾는다. 검사는 제 일을 했고
**내가 그 결과를 버렸다.**

### 놓쳤다면

「검사 통과 후 커밋」이라는 이 저장소의 전제가 한 커밋만큼 거짓이 된다. 그 위에
다음 커밋이 쌓이면 어느 커밋부터 깨졌는지 역추적해야 한다.

---

### 추기 (2026-09-18) — **재발했다. 두 번째다**

`pytest tests/ -q 2>&1 | tail -1 && git add … && git commit … && git push` — 정확히
같은 모양이다. `tail` 이 0 을 돌려 **1 failed 인 판이 커밋·푸시됐다**(`docs/ui/05` 검토서
커밋). 깨진 것은 D-35 가 만든 `test_claude_md_test_count_matches_reality` — 새 문서가
매개변수 검사 둘을 늘려 699 → 701 이 됐는데 명판을 안 고쳤다. **검사는 제 일을 했고
파이프가 그것을 삼켰다.**

위의 「규칙」(`set -o pipefail` 또는 요약 줄을 직접 읽는다)은 **틀린 게 아니라 약했다** —
지킬지 말지가 매번 사람 손에 있었다. 승급한다:

> **검사와 커밋을 한 셸 줄에 두지 않는다.** `pytest` 는 자기 줄에서 돌리고 요약 줄을
> 읽은 **다음 호출**에서 커밋한다. `| tail` 뒤에 `&&` 를 두는 순간 종료 코드는 `tail` 의 것이다.

CLAUDE.md 「일곱 줄」표에 넣을지는 세 번째가 나면 — 지금은 `00_index` 「작업 직전」표의
그 줄을 이 문장으로 바꾼다.

## UO-3. `claude plugin uninstall` 이 **방금 만든 프로젝트 설정 파일을 비웠다**

| | |
|---|---|
| 시점 | UD-7 검증 중 — 사용자 범위 설치를 원점으로 되돌리려다 |
| 상태 | **되돌림** (다시 썼다). 잃은 것은 파일 하나와 몇 분 |

### 무엇을 했나

「프로젝트 설정만으로 되는가」를 재려고 **프로젝트 `.claude/settings.json` 을 먼저 쓰고**,
그 다음 앞서 해 둔 사용자 범위 설치를 지우려고 이 둘을 돌렸다 `[로그]`:

```
claude plugin uninstall frontend-design@claude-plugins-official
claude plugin marketplace remove claude-plugins-official
```

명령은 「Successfully uninstalled / removed」라고 답했다. 그런데 그 뒤 프로젝트 파일이
이렇게 돼 있었다:

```json
{ "enabledPlugins": {}, "extraKnownMarketplaces": {} }
```

### 왜 일어났나

`uninstall`·`marketplace remove` 는 **그 항목을 선언한 설정 파일을 찾아 거기서 지운다.**
내가 방금 프로젝트 파일에 그 둘을 적어 두었으므로, 사용자 범위를 지우라고 한 명령이
**프로젝트 파일**을 고쳤다. 「사용자 범위 설치를 지운다」와 「프로젝트 선언을 지운다」를
같은 명령이 한다는 것을 몰랐다.

커밋 전이라 `git checkout` 으로 되돌릴 수도 없었다 — **추적되지 않는 새 파일**이었다.

### 조치

순서를 뒤집었다 — **사용자 상태를 먼저 원점으로 돌리고, 그 다음 프로젝트 파일을 썼다.**
그 뒤 검증은 정상으로 돌았다(UD-7 표).

### 규칙으로 승급시킬 것

> **`claude plugin` 의 지우는 명령은 프로젝트 설정 파일을 고칠 수 있다.**
> 돌리기 전에 `.claude/settings.json` 이 **커밋돼 있는지** 보고, 아니면 먼저 커밋하거나
> 사본을 떠 둔다. 이는 명판의 「산출물을 지울 때 — 새 것이 완성된 뒤에 교체한다」와
> 같은 계열이고, **추적되지 않는 새 파일이 가장 약하다.**

## UO-4. 화면 검사 하나가 **빨간 채로 여러 커밋을 지났다** — 기본 실행에서 빠져 있어 아무도 안 봤다

| | |
|---|---|
| 시점 | 2026-09-18, 원본 합치기의 §8 「띄워 봤나」를 하려고 `pytest tests/ -m screens` 를 처음 돌렸을 때 |
| 상태 | **원인 규명 → UF-7.** 화면이 아니라 **검사가 틀렸다** — 잔광은 설계대로였다. 검사를 다시 썼다 |

### 무엇을 했나

병합 검증으로 `pytest tests/ -m screens` 를 돌렸다:

```
1 failed, 43 passed, 14 skipped, 700 deselected
tests/test_demo_screens.py::test_sweep_glows_behind_the_cursor
  커서 뒤 잔광이 없다 — 바로 뒤 238 가 먼 쪽 246 보다 진하지 않다
```

**병합 탓인지부터 갈랐다** `[측정]`. 병합 전 커밋으로 별도 워크트리를 만들어
같은 검사를 돌리니 **소수점까지 같은 값**이 나왔다:

| | 커서 바로 뒤 | 먼 쪽 |
|---|---|---|
| 병합 후 | 237.80392156862746 | 245.63137254901957 |
| 병합 전 (`pre-merge-b9c8f93`) | **237.80392156862746** | **245.63137254901957** |

**병합이 만든 것이 아니고, 흔들리는 것도 아니다** — 결정론적으로 빨갛다.
스윕 잔광은 커밋 `85efd07`(「스윕 페이드·잔광을 실제로 보이게 고치고」)에서
손봤고, 그 뒤 화면을 고친 커밋이 더 있었다.

### 어긋난 규칙

`docs/ui/00_index.md` 「작업 직전」 표: **「화면(HTML/CSS/JS)을 고쳤다 →
`pytest tests/ -m screens`」.** 규칙은 있었다. 안 돌렸다.

### 왜 일어났나

`pytest.ini` 의 `addopts = -m "not slow and not screens"` 때문에 **기본 실행에서
빠진다.** 그래서 `CLAUDE.md` 「커밋 전」이 시키는 `pytest tests/` 는 이 검사를
**한 번도 세지 않았다** — 689 개가 초록이어도 이건 안 들어 있었다.

빠뜨린 것 자체는 설계다(브라우저를 띄우면 2 분 걸린다). 문제는 **빠진 것을
누가 언제 도는지가 어디에도 안 적혀 있었다**는 것이다. 사람이 「화면을 고쳤다」를
스스로 알아채야 작동하는 규칙인데, 그 판단이 매번 맞을 이유가 없다.
UO-2 와 같은 모양이다 — **검사는 있었고 결과를 보지 않았다.**

### 조치

- 이 항목으로 **언제부터 빨간지**(병합 전에도)와 **왜 안 보였는지**를 먼저 적었다.
  고치는 것은 다음이다 — 원인(잔광 코드인지 탐침인지)을 아직 모른다.
- 병합 커밋 메시지에 「남은 빨강 — 머지 탓이 아니다」로 명시했다. **초록인 척하지 않는다.**

### 규칙으로 승급시킬 것

**「기본 실행에서 뺀 검사는, 무엇이 언제 그것을 도는지 같은 자리에 적는다.」**
빼는 것은 괜찮다. 빼 놓고 **도는 주체를 안 적는 것**이 사고를 만든다.
지금 후보는 둘이다 — CI 에서 `-m screens` 를 돌리거나(느려도 사람이 안 잊는다),
`demo/` 가 바뀐 커밋에서만 돌게 하거나. **UD 로 먼저 적는다.**

### 놓쳤다면

### 추기 (2026-09-18) — **전제가 틀렸다. CI 는 돌고 있었다**

`.github/workflows/checks.yml:110` 이 `pytest tests/test_demo_screens.py -m screens` 를
**이미 돈다** `[코드]`. 「기본 실행에서 빠져 아무도 안 봤다」의 앞 절반은 맞고 뒷 절반은
틀렸다 — **CI 가 봤고, 빨간 채로 Actions 에 떠 있었고, 사람이 안 읽었다.** 위 「규칙으로
승급시킬 것」의 후보 둘(CI 에 붙이기 · `demo/` 바뀔 때만 돌리기)은 이미 있는 것을
만들자는 제안이었다.

승급 후보를 바꾼다: **「push 뒤 Actions 결과를 읽는다 — 초록/빨강을 다음 커밋 전에
확인하고, 빨강이면 그 커밋에서 다룬다.」** 명판의 「push 하면 Actions 가 같은 것을
돌리고 스크린샷 42 장을 올린다」는 **올린다**까지만 말하고 **읽는다**를 안 시켰다.
개선은 멈춘 상태라(사용자 지시) 여기까지 적는다.

### 놓쳤다면

박람회 화면의 잔광이 「있다고 적혀 있고 실제로는 없는」 상태로 갔다.
그리고 더 나쁜 쪽 — **UD-9 가 이 화면 위에 재질·서체를 얹으려던 참이었다.**
빨간 검사 위에 새 작업을 쌓으면, 나중에 깨진 것이 새 작업 탓인지 원래 그랬는지
못 가린다. 이번에는 **병합 전 커밋으로 재서** 갈랐는데, 층이 더 쌓였으면
그 비교가 안 됐다.

## UO-5. 발산 결과를 **사용자에게 안 보이고** 판정으로 넘어갔다 — 절차에 있는 단계를 건너뛰었다

| | |
|---|---|
| 시점 | 2026-09-19, 라운드 ① 의 A 가 돌아온 직후 |
| 상태 | **되돌림** — 건너뛴 단계를 수행했고, 스킬에 그 단계를 넣었다 |

### 무엇을 했나

A 가 후보 **8 개**와 레퍼런스 카드 **7 장**(각 2,300 자, 규격 12 칸 전부 채움)을 냈다.
B 는 5 개를 냈다. 그런데 채팅에서 사용자에게 보인 것은:

| | 보였나 |
|---|---|
| B 의 후보 5 | 한 줄씩 — **판정과 함께** |
| **A 의 후보 8** | **한 개도 안 보였다** |
| **레퍼런스 카드 7 · URL · 「어디를 볼지」** | **한 장도 안 보였다** |
| 교차 검토 결과 · KEEP 5 / TUNE 3 | 보였다 |
| 변경 계약 | 보였다 |

즉 **판정된 것만 보이고 판정 대상은 안 보였다.** 사용자 말 그대로:

> "제시된 아이디어에 대한 설명과 검증기 통과 후 선별된 아이디어들이 왜 선별되었는지
> 그런게 있어야 내가 좋은 아이디어 같은지 아닌지 판단하고 논의할텐데"

> "네가 검증하고 알아서 구현하겠다는 느낌이야."

### 어긋난 규칙 — 문서에 있었다

`docs/ui/02_benchmark.md` §8.4:

> 카드 3~8 → 후보 5~8 → **사용자 정렬(카드를 보고 고른다)** → 2~4 로 →
> 필요하면 브랜치 시안 → 검증기 넷 → KEEP/TUNE/REJECT → UD

**사용자 정렬이 검증기 «앞»에 있다.** 순서가 그런 데는 이유가 있다 — 사람이 먼저
고르고 기계가 나중에 검사한다. 내가 한 것은 **검증기 → 교차 검토 → 계약**이고
사용자 정렬이 **통째로 빠졌다.**

### 왜 일어났나 — 스킬과 문서가 어긋나 있었다 `[코드]`

`.claude/skills/dual-creative-director/SKILL.md` 의 순서:

```
3. A 레퍼런스 디렉터
4. 교차 검토          ← 여기
5. 검증기 넷 → UD
```

**스킬에 「사용자 정렬」이 없다.** §8.4 에는 있고 스킬에는 없다. 나는 스킬을 따랐다.
**실행 경로가 문서 경로에서 한 단계를 잃은 것**이고, 문서만 고치면 다음에 또 같은 일이
난다 — 행동은 스킬이 정한다.

UO-4 와 같은 계열이다: 그때는 「검사는 있었고 결과를 안 봤다」, 이번엔
**「절차는 있었고 실행 경로에 그 단계가 없었다」**.

### 조치

1. **스킬에 단계를 넣었다** — `4. 사용자 정렬`, 검증기는 `6` 으로 밀렸다.
   「검증기를 먼저 돌려 후보를 줄이지 않는다 — 그러면 사용자는 남은 것만 보게 되고,
   고르는 일이 판정으로 바뀐다」를 이유와 함께 적었다.
2. **건너뛴 단계를 수행했다** — 카드 7 장(URL · 어디를 볼지 · 빌린 원리 · 거리 · 위험)과
   후보 8 개를 사용자에게 제시했다.

### 규칙으로 승급시킬 것

**「발산이 끝나면 판정보다 먼저 사용자에게 후보 전부와 그 근거를 보인다.」**
레퍼런스는 **URL 과 「어디를 볼지」를 함께** — 그것을 안 주면 레퍼런스 마이닝은
내 머릿속에서만 일어난 일이 된다.

### 놓쳤다면

변경 계약까지 승인받고 구현에 들어갔을 것이다. 그러면 **사용자가 한 번도 못 본 후보
8 개가 「검토됐다」는 기록만 남고** 사라진다. 기각 이력은 이 과제의 산출물인데(D-32),
사용자가 본 적 없는 것을 기각 이력이라 부를 수 없다.
