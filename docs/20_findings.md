## F-25. 실시간 경로에서 **front-end 를 어디서 도느냐**가 −15 dB 를 갈랐다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | `StreamProcessor` 첫 판이 오프라인 대비 −15.0 dB 를 내서 |
| 영향 | `30_realtime_demo` 5 절 난관 4 의 대응이 **틀렸다.** 실시간 시연의 신호 경로 |

### 발단

R-4 로 스트리밍 처리기를 만들고 오프라인 경로와 대조했다. **−15.0 dB.**
R-3 이 같은 질문에 ±0.36 dB 라고 이미 답해 뒀으므로 크기가 불가능했다.

### 먼저 의심한 것

**배관(링버퍼 · OLA · 내보내기 규칙)** 을 의심했다. 배제 근거: 항등 방법
(`M00`)을 흘려 보니 **출력이 입력과 4e-16 안에서 같았다** `[측정]`.
배관은 신호를 건드리지 않는다.

### 결정적 측정

같은 신호에 front-end 를 **미리** 걸고 방법의 FE 를 끄자 붙었다 `[측정]`:

| 조건 | 오프라인과의 상관 | 오프라인 대비 |
|---|---|---|
| `M04` (방법이 FE 를 내부에서 건다) | 0.8437 | **−15.00 dB** |
| `M04` (FE 를 미리 걸고 방법의 FE 는 끔) | **1.0000** | **−0.02 dB** |

**틀린 것은 필터를 어디서 도느냐 하나였다.** 방법을 링버퍼마다 호출하면
`filtfilt` 가 버퍼마다 다시 돌고, 그 결과들이 Hann² 로 겹쳐 더해진다.

### 왜 고칠 수 없는가 — 그리고 그것이 결론이다

`FrontEnd` 는 0.5 Hz HPF 의 링잉을 `8 × order / f_c` = **64 초**로 잡는다
(F-4 에서 이 패딩을 안 주면 왜곡이 11.9 dB 라고 쟀다). **영위상 필터를
100 ms 지연으로 돌릴 방법은 없다.** 실시간은 인과 필터를 써야 하고, 그러면
신호가 달라진다.

그래서 `StreamingFrontEnd`(같은 설계, `sosfilt` + 상태)를 앞단에 두고
대가를 쟀다. 두 열로 가른다 — 섞으면 −13.8 dB 와 +14.0 dB 라는 **서로 모순되는
표**가 나온다(실제로 둘 다 나왔다):

| D1 | 배관만 (FE 를 양쪽에서 뺌) | 파이프라인 전체 (각자 참조 기준) |
|---|---|---|
| `M04` SWT | +0.01 ~ +0.10 dB | **+0.4 ~ +0.7 dB** |
| `M06` U-Net (L1) | +0.53 ~ +0.86 | **−4.3 ~ −4.8** |
| `M06` U-Net (**L6**) | +0.04 ~ +0.23 | **−0.4 ~ −1.0** |

**배관 손해는 24 개 설정 전부에서 1.13 dB 이내다.** 잃는 것은 학습된 모델
뿐이고, `M06-L1` 이 4 dB 를 잃는 자리에서 **`M06-L6` 은 0.5 dB 만 잃는다.**

`L6` 은 "깨끗한 입력을 덜 건드려라" 를 손실에 넣은 것인데(5.8.9), 그 결과
**front-end 모양에 덜 의존하는 모델**이 됐다. 겨냥하지 않은 이득이다.

### 놓쳤다면

**시연이 보고서와 다른 신호를 보이면서 같은 수치를 달았을 것이다.**
그리고 파형만 봐서는 알 수 없다 — 상관 0.84 는 눈으로 구분되지 않는다.

### 조치

`ecgdn/realtime/` 에 `StreamProcessor` + `StreamingFrontEnd`.
방법이 자체 FE 를 든 채로 인과 FE 를 앞단에 두면 **생성자가 거부한다** —
조용히 두 번 걸리면 알아챌 방법이 없다. `tests/test_stream_processor.py` 9 건.

`M_FE`·`M01` 은 **필터 자체가 방법의 정의**라 분리할 수 없다. 그 실시간
대응물은 `StreamingFrontEnd` 자신이고, 검증에서 건너뛴다.

### 재사용 규칙

**오프라인 전용 연산이 방법 안에 숨어 있으면 "같은 방법을 호출했다" 가
보증이 되지 않는다.** `filtfilt` 는 방법의 일부처럼 보이지만 실시간에서는
쓸 수 없는 연산이다. 실시간 경로를 만들 때는 **각 부품이 미래를 보는지**를
먼저 세어야 한다.

그리고 **참조가 다르면 두 경로를 직접 비교할 수 없다.** 인과 FE 출력을
영위상 참조로 재면 처리 품질이 아니라 참조 정의를 재게 된다 — F-12 · F-15 와
같은 계열이고, 이번에는 그것이 **양방향으로** 나타났다.

### 그 뒤 — **손해의 절반 이상은 필터 «차수» 였다** (F-27 · D-19)

이 기록은 손해를 «인과 FE 라는 분포 이동» 으로 돌렸다. **절반만 맞았다.**
화면을 만들자 T-P 구간이 기우는 것이 보였고(F-27), 원인을 좇아 **차수만
4 → 1 로 낮추자** D1 의 파이프라인 열이 이렇게 바뀌었다 `[측정]`:

| D1 · 96 ms | order 4 (이 기록) | **order 1** |
|---|---|---|
| `M06` (L1) | −4.32 dB | **+0.89** |
| `M06` (L6) | −0.45 | **+1.19** |
| `M04` | +0.67 | **+0.73** |

**배관 열은 24 행 전부 비트 단위로 같았다** — 바뀐 것은 FE 하나다.
즉 손해의 원인은 «인과냐 영위상이냐» 가 아니라 **«그 인과 필터가 파형을
얼마나 망가뜨리느냐»** 였다. 아래의 `L6` 해석("front-end 모양에 덜 의존하는
모델")도 그만큼 약해진다 — order 1 에서는 `L1` 과 `L6` 의 격차가 0.3 dB 다.

## F-24. 축 평균이 없는 방법은 **구간 선정이 통제하지 못한다** — 44 개 중 최악이 뽑혔다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | 시연 은행의 `M06L6` 값이 `exp_g` 의 짝지은 결과와 **부호가 반대**여서 |
| 영향 | `L6` 의 잡음별 효과에 대한 서술. 이미 사용자에게 틀린 방향으로 보고했다 |

### 발단

시연 은행(R-1)을 만들고 D1 PLI 10 dB 칸을 보니 `M06L6` 9.13 dB, `M06` 16.12 dB
였다. **−7.0 dB.** 임펄스 칸은 반대로 +5.2 dB 였다. "손실 변경의 이득이 잡음
종류에 따라 부호가 갈린다" 로 읽었고, 그 문장으로 사용자에게 보고했다 `[대화]`.

구간 하나라는 단서는 달았지만 **"우연으로 보기 어려운 크기"** 라고 덧붙였다.
그 판단이 틀렸다.

### 결정적 측정

`exp_g` 로 기록 22 개 × 구간 2 개를 짝지어 다시 쟀다 `[측정]`:

| D1 PLI 10 dB, `M06L6 − M06` | |
|---|---|
| 평균 | **+4.00 dB** |
| 중앙값 | +3.75 dB |
| rank-biserial r | **+0.91** (44 중 40 이 양수) |
| **기록 214/0 (은행이 고른 구간)** | **−4.93 dB — 44 개 중 최솟값** |

**부호가 반대일 뿐 아니라, 은행이 고른 구간이 분포의 맨 끝이었다.**
D1 전체로는 21 칸 중 **유의 이득 12 · 유의 손해 3 · n.s. 6** 이고,
PLI 는 세 SNR 모두 유의 이득이다(+1.90 / +4.00 / +9.08).

### 왜 그렇게 됐나 — 기준의 구멍

D-17 의 선정 기준은 "방법별 `snr_imp` 벡터가 **축 평균 벡터**와 가장 가까운
구간" 이다. 그런데 그 거리는 **축 평균이 있는 방법에 대해서만** 계산된다:

```python
have = [m for m in methods if m in ref]      # ref 에 없으면 빠진다
dist = [mean(|seg[m] - ref[m]| for m in have) ...]
```

`M06L6` 은 손실 절제(`abl_loss`)가 `conditions: [mixed]` 만 돌아서 **잡음 칸에
축 평균이 없었다.** 그래서 `have` 에 들어가지 못했고, **선정이 통제한 것은
10 개 방법이고 11 번째는 자유롭게 튈 수 있었다.**

`no_ref` 목록은 처음부터 있었다. 다만 그것을 **"화면에 평균 칸을 비우라"**
는 표시로만 썼고, **"이 방법은 대표성이 보장되지 않았다"** 는 뜻인 줄은
몰랐다. 같은 한 줄이 두 가지를 말하고 있었는데 하나만 읽었다.

### 먼저 의심한 것

**"체크포인트가 잘못 물렸다"** 를 먼저 봤다 — 은행과 `exp_g` 가 같은
`results/d1/m06_l6/best.pt` 를 쓰는지. **같았다** `[코드]`. 평가 길이가 다른
것(은행 20 s / 실험 60 s)도 의심했지만, 그것으로 7 dB 가 뒤집히지 않는다.

기록별 값을 늘어놓고서야 답이 나왔다 — 214/0 이 **최솟값**이라는 것.
가설이 아니라 **분포를 본 것**이 답을 줬다.

### 놓쳤다면

**보고서에 "`L6` 의 이득은 잡음 종류에 따라 부호가 갈린다 — PLI 에서는 크게
진다" 가 실렸을 것이다.** 실제 D1 결과는 정반대에 가깝다. PLI 는 `L6` 이
**가장 크게 이기는** 잡음 중 하나이고(20 dB 에서 +9.08), 손해는 잡음 종류가
아니라 **저 SNR**에 몰려 있다(0 dB 에서 3 칸).

즉 결론의 축이 "어떤 잡음이냐" 가 아니라 **"입력이 얼마나 더러우냐"** 였다.
잘못된 축으로 이야기를 쓸 뻔했다.

### 조치

1. `exp_g` 가 `M06L6`·`M08L6` 을 포함하므로, 은행을 다시 만들면 두 방법이
   **거리 계산에 들어간다** — 선정이 통제하는 목록이 넓어진다.
2. `no_ref` 가 비어 있지 않으면 빌더가 **경고를 찍는다.** 문구를 "평균이
   없다" 가 아니라 **"선정이 통제하지 못했다"** 로 바꿨다. 화면도 같은 말을
   한다.
3. `tests/test_demo_bank.py` — 은행의 모든 방법이 선정 기준에 들어갔는지.

### 재사용 규칙

**대표성 기준에서 빠진 항목은 대표되지 않는다.** 그런데 화면에는 나란히
놓이므로 보는 사람은 **같은 보증을 받았다고 생각한다.** 기준에 못 들어간
것은 빼거나, 못 들어갔다고 화면이 말해야 한다.

그리고 **구간 하나로 부호를 말하지 않는다.** F-22 에서 "p 가 작을수록 더
그럴듯해 보였다" 를 배웠는데, 여기서는 **크기가 클수록 더 그럴듯해 보였다.**
−7 dB 는 "우연이 아니겠지" 로 읽혔지만 그냥 꼬리였다.

## F-23. 스트리밍 평가의 기준선을 손으로 재구현해, "스트리밍이 오프라인보다 좋다" 가 나왔다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | 첫 표에서 스트리밍이 오프라인을 약 2 dB 앞서서 |
| 영향 | **30_realtime_demo 2.3.** hop 선택과 crossfade 필요 여부의 근거 |

### 발단

실시간 시연에서 window 를 `hop` 만큼 밀며 이어 붙이면 **이음매가 생기는지,
품질이 얼마나 깎이는지**를 재려 했다(R-3). 기준선은 보고서가 실제로 쓰는
오프라인 처리다.

첫 표에서 스트리밍이 **오프라인보다 약 2 dB 높게** 나왔다 `[대화]`.

### 왜 문제인가

**부호가 물리적으로 불가능하다.** 스트리밍이 시각 `t` 에 쓰는 정보는 오프라인이
쓰는 정보의 **부분집합**이다 — 오른쪽 끝이 `t` 이하인 window 만 쓸 수 있다.
같은 모델·같은 전처리라면 스트리밍은 **오프라인 이하**여야 하고, 잘해야 같다.

그리고 2 dB 는 이 프로젝트에서 **방법을 바꿔 얻는 것과 같은 크기**다
(`L6` 의 D1 이득이 +1.42 dB). "작은 오차" 로 넘길 수 없는 크기였다.

### 먼저 의심한 것

**"overlap-add 평균이 이득을 준다"** 가 첫 해석이었고 **절반은 맞다** — hop 이
작으면 한 샘플이 여러 window 의 평균으로 나오므로 잡음이 조금 더 줄 수 있다.
최종 표에도 `+0.09~+0.36 dB` 로 양수가 남아 있다.

배제 근거 둘:

- **크기가 안 맞는다.** 그 효과라면 hop 에 단조로 의존해야 하는데, 첫 표는
  hop 512(거의 안 겹치는 설정)에서도 2 dB 를 줬다.
- **기준선이 상수가 아니었다.** 오프라인 값이 행마다 23.68 / 22.58 / 21.68 dB
  로 흔들렸다 `[대화]`. 행마다 달라지는 것은 기준선이 아니다.

### 결정적 측정

두 곳이 틀려 있었다 `[코드]`:

1. **오프라인 경로를 손으로 재구현했다.** `DLDenoiser` 가 하는 일 중
   **공통 front-end · reflect 패딩 · window 별 `robust_scale`** 을 빠뜨렸다.
   스트리밍 쪽은 새로 짜면서 그 셋을 넣었으니, 그 표가 잰 것은 **스트리밍 대
   오프라인이 아니라 "정규화 있음 대 없음"** 이다.
2. **행마다 비교 구간이 달랐다.** hop 이 크면 버퍼가 차는 데 오래 걸려 유효
   구간의 시작이 뒤로 밀리는데, 오프라인 값을 그 구간에 맞춰 매번 다시 쟀다.
   구간이 다르면 SNR 도 달라진다.

고쳤다 — **기준선을 재구현하지 않고 실제 `DLDenoiser` 를 호출**하고, 비교
구간은 모든 행에서 **하나로 고정**했다. 그러자 오프라인은 **24.15 dB 하나**가
되고 스트리밍은 전부 그 **±0.36 dB** 안에 들어왔다 `[측정]`
(`results/stream_seam.json`).

### 놓쳤다면

**hop 을 512 로 골랐을 것이다** — 첫 표에서는 hop 이 커도 품질이 좋았으니
추론을 초당 0.5 회만 하면 되는 쪽이 당연히 낫다. 그런데
`30_realtime_demo` 2.2 의 관계식 `L ≥ d + hop` 때문에 hop 512 는 **지연 2 초**다.
시연에서 심박과 눈에 띄게 어긋난다.

반대 방향의 손해도 있다. 이음매를 "주변 대비 3.5 배" 로만 읽으면 **crossfade 를
넣었을 것이다.** 백분위로 보면 **49~66 번째** — ECG 가 정상적으로 내는 크기다.
배수가 커 보이는 것은 **국소 중앙값 대비**라 조용한 구간에서 부풀려지기 때문이다.

F-8·F-10·F-11·F-12·F-15·F-17·F-20·F-21·F-22 와 같은 계열이다. 다만 **이번에는
출력이 멀쩡하지 않았다** — 불가능한 부호가 표 위에 그대로 찍혀 있었다.
앞의 아홉은 그럴듯한 표를 만들어냈고 이것은 아니었다. 그래서 몇 분 만에 잡혔다.

### 조치

`scripts/measure_stream_seam.py` 는 기준선을
`ecgdn.methods.dl_wrapper.DLDenoiser` **호출**로 만든다. 산출물
`results/stream_seam.json` 은 `offline_db` 를 **스칼라 하나**로 적어, 행마다
다른 기준선이 들어갈 자리를 아예 없앴다.

### 재사용 규칙

**A 와 B 를 비교하면서 둘 중 하나를 새로 짜면, 재는 것은 A 대 B 가 아니라
"내 구현 대 원래 구현" 이다.** 기준선은 항상 **실제로 쓰이는 코드를 호출**해서
만든다. 재구현이 불가피하면 먼저 **같은 입력에서 원래 경로와 같은 값이
나오는지** 확인한다.

그리고 **부호가 물리적으로 가능한지부터 본다.** 정보가 적은 쪽이 이겼다면,
이유를 찾기 전에 측정을 의심한다.

## F-22. 이상값이 1 인 지표를 부호 있는 차이로 비교해 판정 4 개가 뒤집혔다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | M09 의 D0 결과에서 `gain_bias` 만 유독 강한 열세로 나와서 |
| 영향 | **F-20 · 5.9 의 `gain_bias` 판정.** 새 판정 1 개 추가 |

### 발단

M09 의 D0 판정을 보니 주 지표는 전부 n.s. 인데 `gain_bias` 만
**+0.0373, p = 7.15e-06, rank-biserial r = +1.000**(22 기록 전부)이었다.
"주 성능은 같은데 진폭만 그렇게까지 나쁘다" 는 조합이 어색했다.

절대값을 열어보고 이유를 알았다 `[측정]`:

| D0 | `gain_bias` | **이상값 1 과의 거리** |
|---|---|---|
| `M06` | **0.9803** | 0.0197 |
| `M09` | **1.0176** | **0.0176** |

**둘이 1 의 반대편에 있다.** `M09` 가 오히려 **약간 가깝다.** 그런데 부호 있는
차이는 `+0.037` 이고, 22 기록 전부에서 같은 부호라 검정이 최대 유의를 준다.

### 왜 문제인가

`gain_bias` 는 `α* = argmin_a ‖a·x̂ − x‖²` 이고 **이상값이 0 이 아니라 1** 이다.
1 보다 크면 출력이 참값보다 작고, 작으면 크다. 즉 **양쪽 다 나쁘다.**

이상값을 넘나드는 지표를 부호 있는 값으로 비교하면 **"누가 이상값에
가까운가" 가 아니라 "누가 더 큰가" 를 재게 된다.** 두 질문은 값들이 이상값의
같은 쪽에 있을 때만 일치한다.

**실제로 넘나든다** `[측정]` — D1 `exp_a` 에서 `gain_bias` 값의 **44 %가 1 을
넘는다**(범위 0.099~1.243).

**다른 지표는 안전하다.** `cc`·`beat_cc` 도 이상값이 1 이지만 **상관이라 1 을
넘지 못한다**(실측 최대 1.0000). 값이 클수록 좋은 단조 관계라 부호차로 비교해도
같은 답이 나온다. 문제는 `gain_bias` 하나뿐이다.

### 먼저 의심한 것

**"M09 가 정말 진폭을 못 지킨다"** 가 첫 해석이었다. r = 1.000 은 강한 신호고,
`M10` 도 같은 패턴을 보였으니 "해상도·문맥을 건드린 모델이 진폭을 흘린다" 는
그럴듯한 이야기가 됐다.

배제 근거: **절대값을 봤다.** `M06` 0.9803 과 `M09` 1.0176 은 1 을 사이에 두고
거의 대칭이다. 이야기가 성립하려면 `M09` 가 1 에서 **더 멀어야** 하는데 아니다.

### 결정적 측정

`|gain_bias − 1|` 로 다시 검정했다 `[측정]`. **판정 4 개가 뒤집힌다:**

| 비교 | 부호차 (틀림) | **거리 (맞음)** | |
|---|---|---|---|
| D0 `M06`→`M08` | p = 7.7e-04 열세 | **p = 0.092 n.s.** | 뒤집힘 |
| D0 `M06`→`M09` | p = 7.2e-06 열세 | **p = 0.387 n.s.** | 뒤집힘 |
| **D0 `M06`→`M10`** | **p = 7.2e-06 열세** | **p = 0.965 n.s.** | **뒤집힘 — F-20 에 실려 있다** |
| **D1 `M06`→`M08`** | p = 0.61 n.s. | **p = 0.0018 열세** | **뒤집힘 — 놓치고 있었다** |
| D1 `M06`→`M10` | p = 4.7e-05 열세 | p = 0.018 열세 | 유지 |
| `M_FE`→DL (양축) | p = 7.2e-06 | p = 7.2e-06 | 유지 |

**세 개는 없던 열세를 만들어냈고, 하나는 있는 열세를 가리고 있었다.**

`M_FE` 대비 딥러닝의 진폭 보존 우위(5.8.4)는 **그대로다** — `M_FE` 0.842/0.848,
DL 0.987~1.013 로 애초에 같은 쪽이 아니라 거리로 봐도 −0.125~−0.131 이다.

### 놓쳤다면

**F-20 이 "`M10` 은 신호를 체계적으로 2~5 % 눌러 내보낸다 — D0 에서 22 기록
전부" 라고 실었을 것이다.** D0 에서는 사실이 아니다. `M10` 의 열세 판정 중
`beat_cc`(양축)는 살아남지만 `gain_bias` 는 **D1 에서만** 남는다.

그리고 **`M08` 이 D1 에서 진폭을 못 지킨다는 것을 영영 몰랐을 것이다.**
`M08` 은 5.2 에서 실용 최선으로 꼽히는 방법이라 이 항목이 빠지면 그 서술이
한쪽으로 기운다.

F-8·F-10·F-11·F-12·F-15·F-17·F-20·F-21 과 같은 계열이다 — **방법이 아니라
측정 틀이 틀렸고, 출력은 멀쩡했다.** 이번에는 `p` 가 작을수록 더 그럴듯해
보였다는 점에서 특히 고약하다.

### 조치

`ecgdn/eval/stats.py` 에 `IDEAL = {"gain_bias": 1.0}` 를 두고
`compare_methods` 가 **기본으로 거리 비교**를 하게 했다. 부호 있는 원값이
필요하면 `use_ideal=False` 를 명시해야 한다.

`cc`·`beat_cc` 는 **일부러 넣지 않았다** — 이상값이 1 이지만 넘지 못하므로
단조이고, 넣으면 오히려 "1−cc" 로 뒤집혀 읽기 어려워진다. 그 판단 근거를
코드 주석에 남겼다.

### 재사용 규칙

**지표를 비교하기 전에 이상값이 어디인지, 값이 그것을 넘나드는지 본다.**
`docs/03_metric_floor*.md` 의 표에 **이상값 열이 이미 있었다** — 분해능을 위해
만든 열인데, 비교 방향을 정하는 데도 쓰였어야 했다. 있는 정보를 안 쓴 것이다.

## F-21. 손실 항의 명목 가중치가 실제 기여와 50 배 어긋나 있었다 — 학습 전에 재고서야 알았다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | `L5`·`L6` 을 학습에 걸기 전에 데이터로 부분 검증하다가 |
| 영향 | **모든 복합 손실의 해석.** L5/L6 설계 3 판이 이것 때문에 기각됐다 |

### 발단

`L5`(SNR 층 균등)와 `L6`(clean 보존)을 구현하고, 8 회 학습(≈ 5.5 시간)을
걸기 전에 **학습된 M06 체크포인트로 손실 항의 크기를 먼저 재봤다** `[측정]`.

`L3 = MSE + 0.5·MAE + 0.3·diff` 의 실제 기여:

| 항 | 명목 가중치 | **실제 기여** |
|---|---|---|
| MSE | 1.0 | **8~10 %** |
| MAE | 0.5 | **89~90 %** |
| diff | 0.3 | 1.1~1.3 % |

**가중치는 0.5 인데 기여는 90 % 다.**

### 왜 문제인가

이유는 단순하다. **오차가 1 보다 작으면 제곱하면 더 작아진다.**

| 오차 \|e\| | MSE = e² | 0.5·MAE | MAE 항이 |
|---|---|---|---|
| 0.1 | 0.010000 | 0.050000 | 5 배 |
| 0.03 | 0.000900 | 0.015000 | 17 배 |
| **0.01** | 0.000100 | 0.005000 | **50 배** |

신호가 정규화돼 있어 학습 후반의 오차가 0.01~0.03 이다. 그 구간에서
`0.5·MAE` 는 `MSE` 의 **17~50 배**다.

**그리고 이것이 L5·L6 을 둘 다 무력화하고 있었다** `[코드]`:

- 첫 `L5` 는 **MSE 항만** 재가중했다 → 손실의 **10 %** 만 건드린다
- 첫 `L6` 의 clean 항은 **MSE 만** 썼다 → 총손실의 **1~4 %**

**둘 다 "효과 없음" 이 나왔을 것이다.** 그런데 그것은 가설이 틀려서가 아니라
**개입이 손실에 닿지 않아서**다. 그 둘은 표에서 구분되지 않는다.

### 먼저 의심한 것

**"MAE 가 90 % 인 것 자체가 버그다"** 가 첫 반응이었다. 가중치 0.5 를 준
항이 손실을 지배하면 설정이 의도와 다르다.

배제 근거: **의도와 다르지만 결과는 나쁘지 않았다.** loss ablation 이 이미
`L1`(MSE 만) → `L2`(+MAE) 를 재놨고 **D0 +0.952(p = 1.2e-03), D1 +0.888** 로
MAE 추가가 유의하게 좋았다 `[측정]`. 즉 "MAE 가 지배하는 손실" 이 실제로 더
나은 모델을 만든다. 고칠 것은 가중치가 아니라 **새 항을 그 형태에 맞추는
쪽**이었다.

### 결정적 측정

**세 판을 다 실측이 죽였다.** 각 판은 몇 분이 걸렸고, 안 쟀으면 5.5 시간짜리
학습이 무의미한 null 을 뱉었을 것이다.

**1 판 — `1/p`(잡음 전력 역수) 가중.** 역분산 가중은 표준 기법이고
(`ε ~ N(0, σ²)` 의 최대우도 가중이 `1/σ²`), 학습 SNR 범위 −5~20 dB 이니
가중치가 316 배쯤 퍼지리라 봤다.

실측 `[측정]`:

| | 가정 | 실측 |
|---|---|---|
| `p` 범위 (300 window) | 316 배 | D0 **127 만 배** / D1 **2.8 억 배** |

두 가지가 어긋나 있었다. (a) `p` 는 절대 잡음 전력이라 SNR 이 아니라 window
의 **신호 진폭**을 함께 반영한다. (b) 더 큰 이유 — **메타의 `snr` 은 60 초
구간의 목표값이지 window 의 실제 SNR 이 아니다.** EM/MA 같은 실잡음은
폭발적이라 같은 구간 안에서도 window 마다 받는 양이 딴판이다. `s/p` 로 다시
재니 목표 −5~20 dB 에 대해 **실제는 −8.8~+80.4 dB** 였다.

**그리고 역분산 가중의 전제가 깨져 있었다.** 그 가중이 옳으려면 **잔차가
잡음에 비례**해야 하는데, 같은 배치의 두 window 를 보면 `[측정]`:

| | 잡음 전력 `p` | 손실 기여 |
|---|---|---|
| `p` 최소 window | 5.42e−09 | 2.18e−03 |
| `p` 최대 window | 1.04e−01 | 7.86e−03 |
| **비** | **1,900 만 배** | **3.6 배** |

**잡음이 1,900 만 배 차이나는데 손실은 3.6 배만 다르다.** 모델의 오차가
잔여 잡음이 아니라 **자기 왜곡 바닥**에 지배되기 때문이다 — EXP-C 가 이미
재고 있던 그 바닥이다(잡음이 전혀 없어도 22 dB 만큼 망가뜨린다).

그래서 `1/p` 는 균형을 맞추는 대신 뒤집는다. 실측으로 퍼짐이 **20 배에서
3,780 배로 악화**됐다.

**2 판 — SNR 구간별 개수 균등.** 구간마다 총 무게를 같게 줬다. 실측이 즉시
기각했다 — **방향이 반대**였다 `[측정]`:

| 구간 | L3 기여 | 2 판 적용 후 | window 수 |
|---|---|---|---|
| < 0 dB | 20.2 % | **32.5 %** ↑ | 44 |
| ≥ 20 dB | 12.0 % | **6.1 %** ↓ | **139** |

고 SNR 구간에 window 가 3 배 많아 개당 무게가 1/3 로 줄었다. **진단이 이미
통제한 변수를 처방이 다시 건드린 것**이다 — 4.8 배 쏠림은 **5 분위(개수
균등)** 로 잰 수치였는데, 처방은 개수를 다시 맞췄다.

**3 판 — 구간별 손실 기여 균등 (채택).** 맞출 것은 개수가 아니라 기여다.
구간 `k` 의 현재 몫 `S_k` 로 나누면 대수적으로 모든 구간이 같은 몫을 갖는다.
실측 확인 — 6 구간이 **정확히 16.7 % 씩** `[측정]`. 가중 평균이라 손실 크기가
보존돼 learning rate 를 그대로 쓴다.

**곁들여 잡은 것 둘.**

- 스케일 보존을 `mean(e/p)·mean(p)` 로 하려다 **17.8 배 부풀었다.** `e/p` 와
  `p` 의 음의 상관 때문이다(체비쇼프 합 부등식). **테스트가 잡았다** — 가중
  평균 꼴로 바꾸니 수학적으로 보장된다.
- 스모크 학습이 **학습을 하나도 안 하고 "통과" 하고 있었다.** window 18 개 <
  batch 64 인데 `drop_last=True` 라 배치가 0 개가 되고, 루프가 그냥 안 돈다.
  초기 가중치가 `best.pt` 로 저장되고 표에는 정상적으로 행이 실린다.
  `RuntimeError` 로 막았다.

### 놓쳤다면

**L5 와 L6 이 둘 다 "효과 없음" 으로 실렸을 것이다.** 그리고 그 결론은
**"손실 변경도 소용없다"** 로 읽혔을 것이다 — 구조 변경 3 연속 기각(F-20)
다음이라 특히 그럴듯했다. 실제로는 개입이 손실의 1~10 % 에만 닿고 있었다.

그리고 그것을 **표만 봐서는 알 수 없다.** `M06-L5` 행은 정상적으로 생성되고
숫자도 그럴듯하다. F-8·F-10·F-11·F-12·F-15·F-17·F-20 과 같은 계열이다 —
**방법이 아니라 측정(여기서는 개입)의 틀이 틀렸는데 출력은 멀쩡한 것.**

### 재사용할 수 있는 것

**복합 손실에 항을 더할 때는 "명목 가중치" 가 아니라 "실제 기여" 로 정한다.**
학습된 체크포인트 하나에 배치 하나만 통과시키면 몇 초에 잴 수 있다. `L6` 의
`w_clean = 0.5` 도 그렇게 골랐다(총손실의 19~27 %).

**손실 항이 새 방향인지는 gradient 코사인으로 잰다.** D-13 에서 `order=2` 를
기각한 것이 이 도구였다 — `d1` 과 `d2` 의 코사인이 0.947/0.993 이라 새 기제가
아니라 가중치 변경임이 드러났다. 같은 측정이 **차분항의 이득이 D0 전용인
이유**까지 설명했다(D0 는 MSE 와 거의 직교 −0.069, D1 은 중복 +0.826).

## F-20. 시간 해상도를 끝까지 유지해도 QRS 는 나아지지 않는다 — 오히려 beat 형태가 나빠진다

| | |
|---|---|
| 상태 | **확정** (D0 · D1 양축 재현) |
| 발견 | TCN 계열을 추가할 가치가 있는지 묻다가 (사용자 질문, P-9) |
| 영향 | "구조를 바꾸면 나아진다" 는 기대. **모델 선택과 다음 실험 방향** |

### 발단

사용자가 다른 경로에서 **TCN**(temporal convolutional network)을 새 알고리즘
후보로 들었다 `[대화]`. TCN 의 핵심은 **downsampling 없이 dilation 으로
수용영역을 넓히는 것**이다. 우리 딥러닝 3종(`M06` U-Net, `M07` SWT→U-Net,
`M08` wavelet-subband U-Net)은 **전부 U-Net 계열이라 1/2 씩 4회 줄였다가
복원**한다.

여기서 그럴듯한 가설이 나온다. **QRS 는 폭 80~100 ms(20~25 샘플)의 가장
빠른 성분**이다. 1/16 까지 줄이면 QRS 는 1~2 샘플이 된다. **그 병목이
QRS 를 뭉개는 것 아닌가.**

TCN 을 통째로 들여오는 대신 **이 질문 하나만 남기는 판**을 만들었다(D-11):
`M10` DilatedResNet1D 는 `M06` 과 **params 를 0.4 %, 수용영역을 0.9 % 안에서
맞추고, 손실·데이터·분할·일정·시드를 전부 공유**한다. 차이는 시간 해상도
하나다. (TCN 의 causal masking 은 **일부러 뺐다** — 우리는 오프라인 후처리라
미래 샘플을 쓸 수 있고, causal 로 묶으면 해상도가 아니라 인과성을 재게 된다.)

### 먼저 의심한 것

D0(합성)만 먼저 나왔을 때 `M10` 이 VAL 에서 **2.3 dB 나 나빴다**. 첫 해석은
**"dilated 구조가 실제로 약하다"** 였다.

배제 근거: 학습 궤적을 열어보니 `M10` 은 **6 번째 epoch 에 최고를 찍고 18
epoch 에 멈췄고**, `M06` 은 37 epoch 을 돌았다 `[로그]`. 즉 **조기 종료가
두 모델을 다르게 대접**했다. 이것을 파고들어 나온 것이 F-19 다 — VAL 이
수렴 후에도 크게 흔들려서 `best` 선택이 런마다 다르게 부풀려진다.

**그래서 VAL 로는 이 질문에 답할 수 없다.** TEST 로, 양축에서, floor 대조를
붙여서 다시 물었다.

### 결정적 측정

D0·D1 `exp_a` TEST, `M10 − M06`, paired Wilcoxon + Holm, 기록 단위 n=22
`[측정]`. `floor` 는 각 축의 `floor_p95`(`docs/03_metric_floor*.md`)이고,
**`|Δ|/floor < 1` 이면 유의성과 무관하게 구분 불가**다(O-14).

**세 가지가 나왔다.**

**(1) 핵심 가설이 기각됐다.** QRS 폭 오차는 어느 축에서도 나아지지 않았다.
**D0 는 이 지표가 실제로 답할 수 있는 축**이다 — floor 0.640 ms 이고 관측된
차이는 그 2.9 배다. 그런데도 `p = 0.897` 이다. D1 은 floor 가 28.07 ms 라
애초에 못 가른다(F-16).

**(2) 오히려 beat 형태가 나빠졌다 — 양축에서, 거의 같은 크기로.**
`beat_cc`(beat 단위 파형 상관)는 D0 −0.00552(r = −0.723), D1
−0.00190(r = −0.715). **효과 크기가 두 축에서 사실상 같다.** floor 의
4,700~15,000 배라 분해능 문제도 아니다. `beat_cc` 는 상관이라 진폭 배율에
불변이므로, 아래 (3)의 이득 편향과 **독립된 별개의 손상**이다.

**(3) `M10` 은 신호를 체계적으로 2~5 % 눌러 내보낸다.** `gain_bias` 는
`argmin_a ||a·x̂ − x||²` 이라 **1 보다 크면 출력이 참값보다 작다**는 뜻이다.
`M10` 은 D0 1.027 / D1 1.029, `M06` 은 0.980 / 1.010. D0 에서 **rank-biserial
r = +1.000 — 22 기록 전부**가 같은 방향이다.

**대가는 크다.** 같은 params 로 연산량이 **10.4 배**(95.9 → 999.6 MMAC/window,
이론값), 실측 벽시계는 **3.0 배**(CPU 1 thread, 1024 window: 11.1 → 33.6 ms)
`[측정]`. downsampling 이 없으니 모든 블록이 전 길이에서 도는 탓이다.
**이 프로젝트는 임베디드 실시간을 향하고 있어 10 배는 결정적이다.**

**잡음 종류를 가려도 유리한 자리가 없다.** EXP-B(잡음 7종, 10 dB 고정)로
갈라 보니 **D0 는 7종 전부 M10 열세이고 전부 유의**하며(`awgn`·`ma_synth` 는
r = −1.000, 22 기록 전부), D1 은 4종이 유의하게 열세다 `[측정]`. 부호가 한 번
뒤집히는 곳이 D1 의 `em_synth`(+0.196)뿐인데 `p = 1` 이다. **어느 축, 어느
잡음에서도 M10 이 유의하게 앞선 자리는 없다.** (표는 5.9.5.)

**세 관측이 하나로 묶인다 — `M10` 은 더 억누른다.** `M10` 은 안전성
프로브에서 **전 방법 중 가장 낮고**(halluc_energy P1: D0 0.0182 vs `M06`
0.0337, D1 0.0109 vs 0.0137), clean 신호 보존은 **딥러닝 중 최하위**이며
(EXP-C: D1 20.92 vs `M06` 22.43), 잡음 제거량도 낮다 `[측정]`. 따로 보면
어긋나지만 "출력 진폭을 깎는다" 로 읽으면 넷이 같은 이야기다 —
`gain_bias` > 1, 빈 자리에 에너지를 덜 만듦, 신호도 함께 깎임, 그 깎임이
형태 왜곡으로 나타남. **안전성 1 위를 성능으로 읽으면 안 된다.** (5.9.6)

### 왜 그런가 — 해석

U-Net 의 downsampling 은 **QRS 를 뭉개는 병목이 아니라 대역을 나누는
장치**였다고 보는 것이 관측에 맞다. skip connection 이 원해상도 경로를
그대로 남겨 두므로 고주파(=QRS 에지)는 최상위 스케일에서 처리되고, 줄인
경로는 **기저선 변동 같은 느린 성분**을 맡는다. `M10` 은 그 분업을 없애고
같은 해상도에서 전부 처리하게 만들었고, **그 결과가 형태 손상**이다.

### 놓쳤다면

**D1 만 보고 "M10 이 스펙트럼 거리에서 낫다" 고 실었을 것이다.** D1 의
`psd_logdist` 는 −0.731, `p = 0.012` 로 M10 의 **유일한 우세 항목**이었다.
그런데 (a) D1 floor 가 0.998 이라 **분해능 아래**고, (b) D0 에서는 **부호가
반대**(+0.320)다. 축 하나와 유의성 하나만 보면 통과했을 서술이다 — 실제로
압축 인수인계 문서에 그렇게 적혀 있었다(O-14).

**그리고 반대 방향으로도 틀릴 뻔했다.** D0 VAL 만 보면 `M10` 은 2.3 dB
열세인데, 그 수치의 상당 부분은 **조기 종료가 M10 을 18 epoch 에 끊은 것**
이지 구조 탓이 아니다(F-19). D1 에서는 `M10` 이 오히려 **더 오래(52 vs 46
epoch)** 돌았고 수렴 VAL 중앙값은 `M10` 이 **더 높다**(+2.985 vs +2.645, F-19 표).
**그럼에도 TEST 의 `beat_cc` 열세는 양축에서 그대로**다(`gain_bias` 는 D1
뿐이다 — F-22) — 학습량
탓으로 돌릴 수 없는 것은 이 둘뿐이고, 그래서 결론을 이 둘에만 얹었다.

### 그래서 무엇을 하나

`M10` 은 **비교군으로 남기고 후보에서 뺀다.** 이것으로 "구조를 바꾸면
나아진다" 가 세 번 연속 기각됐다 — `M07`(SWT 를 앞에), `M08`(wavelet subband),
`M10`(해상도 유지). 반면 **손실 변경은 유의했다** `[측정]` — 다만 어느
모델이 반응하는지는 축마다 다르다.

| | D0 | D1 |
|---|---|---|
| `M06` L1→L3 | **+1.175 (p = 1.7e-04)** | +0.869 (p = 0.051) |
| `M08` L1→L3 | +0.070 (p = 0.420) | **+1.032 (p = 1.1e-03)** |

**양축 어디서도 유의한 구조 변경은 없었고, 양축 모두 유의한 손실 변경이
하나씩 있다.** 다음 자원은 구조가 아니라 손실에 넣는 것이 맞다.

## F-19. VAL 이 수렴 후에도 ±1.5 dB 튀어서, '최고 epoch' 선택이 런마다 다르게 부풀려진다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | M10(dilated) 학습 결과를 M06 과 대조하다가 |
| 영향 | 학습 요약표의 VAL 수치 해석. **체크포인트 선택과 조기 종료 시점** |

### 배경 — VAL 이 하는 두 가지 일

학습 중 매 epoch 끝에 검증 세트(VAL)로 성능을 잰다. 그 값이 두 가지를 결정한다.

1. **체크포인트 선택** — 가장 좋은 epoch 의 가중치를 `best.pt` 로 남긴다
2. **조기 종료** — 최고 기록이 `patience`(12) epoch 동안 갱신되지 않으면 멈춘다

둘 다 **VAL 이 모델의 진짜 성능을 안정적으로 반영한다**는 가정 위에 있다.

### 발단

M10 을 학습하고 M06 과 나란히 놓으니 D0 에서 **2.3 dB 나 나빴다**
(M06 +6.214, M10 +3.899). 그런데 M10 은 **18 epoch 만에 멈췄고 최고 기록이
6 번째 epoch** 이었다 `[로그]`.

**이 조합이 이상했다.** 6 epoch 에 최고를 찍고 이후 12 epoch 동안 한 번도
넘지 못했다는 것은, 모델이 6 epoch 만에 수렴했다는 뜻이거나 **그 6 epoch 이
운이 좋았다**는 뜻이다. 같은 조건의 M06 은 37 epoch 을 돌았다.

### 먼저 의심한 것

**dilated 구조가 D0 에서 실제로 약하다**가 첫 가설이었다. 그럴듯했다 —
합성 ECG 는 beat 형태가 규칙적이라 downsampling 으로 얻는 다중 스케일
표현이 더 유리할 수 있다.

배제 근거: 학습 궤적을 열어봤다. **두 모델 모두 수렴 후에도 VAL 이 epoch
마다 크게 흔들렸다** `[측정]`. M06 D0 는 +3.1~+5.0 사이를 오갔고 M10 D0 는
+2.6~+3.9 사이를 오갔다. 즉 "최고 기록" 은 안정적인 성능이 아니라
**흔들림의 상단**이다.

### 영향 범위 확인

이미 발표된 결론이 흔들리는지 확인했다. 다행히 **주 결과는 전부 TEST split
기준**이고(F-9 이후 규약), VAL 은 체크포인트 선택에만 쓰인다.

VAL 로 유도했던 유일한 서술인 "D1 이 D0 의 약 6할" 을 두 기준으로 다시
계산했다 `[측정]`:

| 기준 | m06_l1 | m08_l1 | m07_l1 | 평균 |
|---|---|---|---|---|
| `best` | 0.553 | 0.480 | 0.605 | 0.546 |
| 수렴 중앙값 | 0.533 | 0.460 | 0.561 | **0.518** |

결론이 유지된다. 그리고 그 서술은 이미 5.8 의 TEST 기반 분석으로 대체됐다.

### 조치와 검토한 대안

| 안 | 내용 | 판단 |
|---|---|---|
| A | 평활된 VAL(3-epoch 이동평균)로 선택·조기종료 | **옳지만 지금은 못 쓴다** — 규칙을 바꾸면 기존 체크포인트 전부와 비교가 성립하지 않는다 (F-9) |
| B | M10 만 더 오래 학습 | **기각.** 한 모델에만 다른 규칙을 주는 것이라 반대 방향의 불공정 |
| **C** | TEST 로 판정하고, VAL 산포를 함께 보고한다 | 채택 |

**C.** 원래 규약이 이미 "판정은 TEST" 다(F-9). 이 항목은 **VAL 수치를
성능처럼 인용하지 말 것**과, M10 D0 가 적은 예산을 받았다는 사실을
결과 해석에 함께 적기 위한 것이다.

A 는 다음 전면 재학습 때 적용한다 — 그때는 모든 모델이 같은 새 규칙을 받는다.

### 놓쳤다면

**"downsampling 을 없애면 D0 에서 2.3 dB 나빠진다"** 가 결론으로 실렸을
것이다. 그 2.3 dB 중 상당 부분이 선택 운(+1.25 vs +0.90)과 학습 예산
차이(37 vs 18 epoch)이고, 같은 비교를 D1 에서 중앙값으로 하면 **부호가
뒤집힌다.**

### 일반화

> **선택에 쓰는 지표의 산포를 먼저 재라.** `max` 는 잡음이 클수록 커지므로,
> 산포가 다른 런끼리 `best` 를 비교하면 **잡음이 큰 쪽이 이긴다.**
> 이 프로젝트의 지표 분해능(F-16)과 같은 논리인데, 대상이 결과 지표가
> 아니라 **모델 선택 지표**라는 점만 다르다.
>
> 조기 종료도 같은 함정을 공유한다 — 운 좋은 초기 epoch 하나가 학습을
> 통째로 잘라낼 수 있다.

## F-18. SNR 추정기의 천장이 축마다 8 dB 다른데 포화 경고는 상수 하나였다 — 실기록에서는 한 번도 뜨지 않았다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | P-9. F-13 을 해결하려고 편향의 크기를 재다가 |
| 영향 | **5.8.2 의 13 dB 판단 기준을 이 추정기로는 잴 수 없다는 것이 확정됐다** |

### 배경 — 왜 이 추정기가 필요한가

실측 장비 ECG 에는 참값이 없어 SNR 을 직접 계산할 수 없다. 그래서 **beat 반복성**
을 이용해 참값 없이 추정한다 (F-13 의 (A)(B)(C) 세 가지).

`ceiling_warning` 은 그 추정치가 신뢰 구간을 벗어났음을 알리는 장치다. 추정치가
너무 높으면 **"그 이상은 구분되지 않는다"** 는 뜻이지 그 값이 실제 SNR 이라는
뜻이 아니기 때문이다.

### 발단

F-13 은 실데이터에서 추정기가 −7.6 dB 편향된다는 것과 그 원인(beat 마다 형태가
달라 그 변동이 잡음으로 계산된다)까지 짚었지만, **크기를 재지는 않았다.**
P-9 에서 그 크기를 재려고 가장 단순한 측정을 했다 — **잡음을 하나도 넣지 않은
신호에 추정기를 돌린다.**

MIT-BIH 원본(추가 잡음 없음)에서 추정치가 **12.9 dB** 로 나왔다 `[측정]`.

**이것이 왜 이상한가.** 잡음을 넣지 않았으므로 참 SNR 은 (그 기록 자체의 잡음을
빼면) 무한대여야 한다. 유한한 값이 나온다는 것은 **추정기가 신호의 무언가를
잡음으로 세고 있다**는 뜻이고, 그 값이 이 추정기의 **천장**이다.

그런데 같은 실행의 `ceiling_warning` 이 **0** 이었다. 추정치가 이미 천장인데
경고가 뜨지 않았다.

### 먼저 의심한 것

`ceiling_warning` 계산 자체의 버그를 의심했다 — 조건식이 뒤집혔거나 값이
NaN 이면 그렇게 될 수 있다.

배제 근거: 코드는 `any(v >= SNR_CEILING_DB for v in vals)` 로 정상이었고,
`vals` 도 유한했다 `[코드]`. 틀린 것은 식이 아니라 **상수** 였다 —
`SNR_CEILING_DB = 22.0` 이고 추정치가 12.9 이니 당연히 뜨지 않는다.

### 결정적 측정

두 축에서 잡음 없는 신호의 추정치를 쟀다 (5 기록 중앙값, front-end 적용 후)
`[측정]`.

| 추정기 | D0 (합성) | **D1 (실기록)** | 차이 |
|---|---|---|---|
| (A) beat 평균 잔차 | 19.6 | **11.9** | **−7.7** |
| (B) half-sample | 19.8 | **12.8** | **−7.0** |
| (C) 등전위 구간 | 16.8 | 15.6 | −1.2 |

세 가지가 한 번에 드러났다.

1. **천장이 축마다 다르다.** (A),(B) 가 실기록에서 8 dB 낮다.
2. **그 8 dB 가 F-13 의 −7.6 dB 편향과 일치한다.** F-13 이 지목한 원인이
   맞았고, 크기까지 설명된다.
3. **`SNR_CEILING_DB = 22.0` 은 D0 의 천장(19.6~19.8)조차 넘는다.** 즉 이
   경고는 **어느 축에서도 사실상 뜨지 않는 장치**였다.

그리고 (C)만 거의 떨어지지 않는다(−1.2). (C)는 등전위 구간의 분산을 보므로
beat 형태가 달라도 흔들리지 않기 때문이다 — 나머지 둘은 beat 반복성이
유일한 근거다.

### 이 결과가 프로젝트에 미치는 영향

**5.8.2 는 "입력 SNR 13 dB" 를 딥러닝 사용 여부의 분기점으로 만들었다.
그런데 (A),(B) 의 천장이 11.9~12.8 dB 다 — 판단해야 할 지점이 정확히
측정 수단의 천장에 놓여 있다.**

두 값이 비슷한 것이 우연인지 공통 원인이 있는지는 확인하지 못했다.
`[미확정]` 다만 실용적 결과는 우연 여부와 무관하다: **이 추정기로는
장비가 분기점의 어느 쪽인지 판정할 수 없다.**

(C)는 천장이 15.6 dB 라 13 dB 위에 여유가 있다. 그래서 P-10 의 실측
절차는 **(C)를 주 추정기로** 쓰되, (C)가 약한 burst 잡음 여부를
`artifact_beat_frac` 으로 먼저 판정하도록 정했다.

### 조치와 검토한 대안

| 안 | 내용 | 판단 |
|---|---|---|
| A | 상수를 12 로 낮춘다 | **기각.** D0 결과의 경고 판정이 소급해 바뀐다 |
| B | 추정기를 고쳐 천장을 올린다 | beat 변동과 잡음을 분리하는 새 방법이 필요하다. 과제 범위 밖 |
| **C** | 천장을 **축별 실측값**으로 두고 호출자가 넘긴다 | 채택 |

**C.** `SNR_CEILING_BY_AXIS = {"d0": 19.0, "d1": 12.0}` 를 두고
`estimate_snr_all(..., ceiling_db=)` 로 받는다. 기본값은 기존 `22.0` 을
유지해 D0 산출물이 소급 변경되지 않게 했다. 실측 장비 신호는 실데이터이므로
`estimate_real_snr.py` 가 `d1` 값을 넘긴다.

B 는 실제로 매력적이다 — beat 변동은 호흡 주기로 **느리게** 변하고 잡음은
빠르므로, 인접 beat 쌍과 먼 beat 쌍의 잔차를 비교해 외삽하면 분리할 수 있다.
`estimate_snr_hsc_far` 가 그 방향의 절반이다. 다만 새 추정기를 만들고 교정까지
하는 것은 이 과제의 목표(denoising 기법 비교)가 아니라 별도 연구다.

### 놓쳤다면

실측 장비의 SNR 을 재고 **"12 dB 로 나왔으니 딥러닝을 쓰는 구간"** 이라고
결론지었을 것이다. 그 12 dB 는 장비의 SNR 이 아니라 **추정기가 낼 수 있는
최대치**였고, 경고도 뜨지 않으니 알아챌 단서가 없다. 장비가 실제로 18 dB
여도 같은 값이 나온다.

### 일반화

> **경고 장치의 임계값도 측정해야 한다.** 이 경고는 코드가 정상이고 값도
> 정상인데 **한 번도 뜨지 않아서** 아무 일도 하지 않고 있었다. 테스트는
> "경고가 뜨는 조건에서 뜨는가" 를 확인하지 "실제 데이터에서 뜬 적이 있는가"
> 를 확인하지 않는다.
>
> 진단 질문: **이 경고가 마지막으로 뜬 것이 언제인가.** 한 번도 없다면
> 임계값이 틀렸거나 그 경고가 불필요한 것이다.

## F-17. Sameni 자가진단의 "참 파라미터" 가 실데이터에서는 참이 아니었다 — F-14 의 근거표를 무효화

| | |
|---|---|
| 상태 | **확정** |
| 발견 | P-8. F-14 를 '잠정' 에서 '확정' 으로 올리려고 근거를 다시 읽다가 |
| 영향 | **F-14 의 핵심 근거표를 철회.** `06_sameni_diagnosis_d1.md` 의 DoD 판정을 N/A 로 |

### 배경 — DoD 검사가 재려던 것

Sameni EKF/EKS 는 ECG 를 McSharry ODE(심장 주기를 위상 `θ` 로 두고 P·Q·R·S·T 를
위상 위 가우시안 봉우리의 합으로 쓰는 미분방정식)로 모형화하고, 그 모형을
상태방정식 삼아 칼만 필터를 돌린다. 그래서 **커널 파라미터**(각 봉우리의 진폭
`α`, 폭 `b`, 위상 `θ`)를 알아야 한다. 실제로는 신호에서 추정(적합)해야 한다.

자가진단의 **DoD** 항목은 그 추정 오차를 배제하려고 **파라미터를 정답으로
주입한 뒤** 성능을 잰다. "파라미터만 맞으면 이 방법이 원리적으로 얼마나 하는가"
를 재는 검사이고, 여기서 낮으면 구현이나 가정에 문제가 있다는 뜻이다.

### 발단

F-14 를 확정으로 올리려고 그 근거표를 다시 봤다.

| | D0 | D1 |
|---|---|---|
| DoD 개선폭 | +16.2 dB | +5.91 dB |

F-14 는 이 격차를 **"실제 ECG 는 McSharry 모형을 따르지 않는다"** 의 증거로 썼다.
그런데 같은 문서의 다른 줄이 걸렸다 — D1 에서 **적합 커널(+11.23 dB)이 주입
커널(+5.91 dB)보다 좋다** `[측정]`.

**이것이 왜 이상한가.** 주입 커널은 "정답을 준" 조건이므로 추정해서 얻은
커널보다 **나쁠 수가 없다.** 정의상 천장이어야 하는 값이 천장이 아니었다.

### 먼저 의심한 것

**적합 절차가 주입 절차보다 유리한 부수 효과**(예: 적합 쪽만 진폭 정규화가
걸린다든지)를 의심했다. 그렇다면 두 값의 비교 자체가 성립하지 않는다.

배제 근거: 코드에서 두 경로가 같은 `SameniKalman`·같은 `_imp()` 를 쓰고 차이가
`kernel=` 인자 하나뿐임을 확인했다 `[코드]`.
그러자 남는 설명은 **주입한 커널이 그 신호의 정답이 아니다** 하나였다.

### 결정적 측정

코드를 따라가면 바로 나온다 `[코드]`.

```python
d_true = SameniKalman(smooth=True, kernel=DEFAULT_KERNEL)   # scripts/diagnose_sameni.py
```

그리고 `DEFAULT_KERNEL` 은 **합성 신호를 만드는 바로 그 커널**이다:

```python
# ecgdn/data/synthetic.py
def synth_ecg(..., kernel: ECGKernel = DEFAULT_KERNEL, ...)
```

| 축 | 신호 | `DEFAULT_KERNEL` 의 지위 |
|---|---|---|
| D0 | `synth_ecg` 출력 | **생성에 쓴 커널** — 주입은 곧 정답 주입 |
| D1 | MIT-BIH 실기록 | **아무 관계 없는 남의 커널** |

실제 ECG 에 대응하는 "McSharry 참 파라미터" 라는 것은 **존재하지 않는다.**
그러므로 D1 의 +5.91 dB 는 "정답을 줬을 때의 성능" 이 아니라 **"환자와 무관한
커널을 억지로 끼웠을 때의 성능"** 이다. 적합 커널이 이겼다는 사실이 그 직접
증거다.

> D0 에서도 엄밀히는 완전한 정답이 아니다. F-8 을 고치면서 기록마다
> `jitter_kernel(DEFAULT_KERNEL, ...)` 로 커널을 흔들었기 때문에, 주입값은
> 각 기록의 커널이 아니라 **그 분포의 중심**이다. D1 만큼 어긋나지는 않지만
> "참 파라미터" 라는 이름은 두 축 모두에서 과장이다.

### 조치와 검토한 대안

| 안 | 내용 | 판단 |
|---|---|---|
| A | D1 의 DoD 기준을 낮춘다 | **기각.** 값이 낮은 게 문제가 아니라 그 값이 다른 양이다 |
| B | D1 에서도 커널을 적합해 '참값' 으로 쓴다 | **기각.** 적합값 주입은 `C5` 와 같은 측정이 되어 검사의 의미가 사라진다 |
| **C** | DoD 를 **합성축 전용 검사**로 선언하고 D1 에서는 N/A 로 보고 | 채택 |

C 를 골랐다. 이 검사가 재려던 것("파라미터 추정 오차를 뺀 방법의 잠재력")은
**생성 커널을 아는 축에서만 잴 수 있다.** 실데이터에서 그 양은 정의되지 않는다.

부수 효과로 D1 자가진단이 "6/7 통과(1 FAIL)" 에서 **"6/6 통과 + 1 N/A"** 가 됐다.
FAIL 로 세는 것은 구현에 결함이 있다는 뜻이 되는데 사실이 아니었다.

### 비용

F-14 의 근거표 철회. F-14 자체는 살아남지만 **다른 근거(EXP-A)로 다시 세웠고,
주장의 범위가 좁아졌다.** 재실행은 자가진단 2회(수 분)뿐이다.

### 놓쳤다면

**"실데이터에서는 참 파라미터를 줘도 5.91 dB 밖에 안 된다 — 모형 가정이
실제 ECG 에서 무너진다"** 가 보고서에 실렸을 것이다. 문장은 그럴듯하고
숫자도 실재하지만, 그 5.91 dB 는 참 파라미터를 준 값이 아니다.

### 일반화

> 상수 하나에 **"참값"·"oracle"·"상한" 같은 이름이 붙어 있으면, 그 이름이
> 어느 조건에서 붙은 것인지 확인한다. 데이터축을 옮기면 같은 상수가 같은
> 이름을 유지하지 못한다.** 이 프로젝트에서 F-12(참조), F-15(왜곡 하한),
> F-17(참 파라미터)이 모두 같은 모양이다 — **정의가 축을 따라 움직이는데
> 이름만 그대로 남았다.**
>
> 진단 지표: **천장이어야 할 값이 천장이 아니면**, 성능 문제가 아니라
> 정의 문제다. 이번에는 적합 커널이 주입 커널을 이긴 것이 그 신호였다.

## F-16. 지표의 분해능이 데이터축에 따라 44 배 달라진다 — D1 에서 QRS duration 은 방법을 가르지 못한다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | P-8 (D1 실험 결과를 읽다가) |
| 영향 | D1 의 `qrs_dur_err_ms` 비교 전부. loss ablation 표에서 '최선' 표시를 제거 |

### 배경 — metric floor 란

**metric floor(지표 분해능)** 는 "이상적인 출력을 넣어도 지표가 얼마나 흔들리는가"
다. 측정 방법은 이렇다: clean 신호에 **40 dB AWGN**(거의 없는 수준의 교란)을
10 개 seed 로 준 뒤, 그 출력을 이상값과 비교해 지표가 벌어지는 폭을 잰다.
그 폭의 95 퍼센타일이 `floor_p95` 다.

**왜 필요한가.** 두 방법의 지표 차이가 이 값보다 작으면, 그것은 방법의 차이가
아니라 **지표 자체의 잡음**이다. 표에 굵게 표시하고 "A 가 B 보다 낫다" 고 쓰면
없는 차이를 주장하는 것이 된다.

`qrs_dur_err_ms` 는 QRS 폭(심실 탈분극 구간의 길이)을 추정한 값이 참값에서
몇 ms 벗어났는가다. 추정은 **delineator**(P·QRS·T 경계를 찾는 알고리즘)가 한다.

### 발단

D1 결과표(T1)에서 **거의 모든 방법의 `qrs_dur_err_ms` 에 `*`(구분 불가)가
붙어 있었다** `[측정]`. D0 에서는 몇 개만 붙던 표시다.

같은 표에서 값 자체는 18~51 ms 로 방법마다 꽤 달라 보였다. **값은 다른데 전부
구분 불가**라는 조합이 이상해서 floor 를 직접 열어봤다.

### 먼저 의심한 것

**`*` 판정 코드가 축을 잘못 읽는 것**을 먼저 의심했다. D1 표의 각주가
`docs/03_metric_floor.md` — **D0 의 floor 문서**를 가리키고 있었기 때문이다.
D0 의 floor 로 D1 결과를 판정하고 있다면 명백한 버그다.

배제 근거: `make_report.py:61` 을 읽으니 실제 판정은
`results/{TAG}/metric_floor/floor.csv` 를 읽고 있었다 — **축을 제대로 따라간다.**
틀린 것은 판정이 아니라 **각주에 인쇄된 문서 경로**뿐이었다 `[코드]`.
(이 각주는 별건으로 고쳤다.)

### 결정적 측정

두 축의 floor 를 나란히 놓자 답이 나왔다 `[측정]`.

| metric | D0 floor p95 | **D1 floor p95** | 배수 |
|---|---|---|---|
| `qrs_dur_err_ms` | 0.640 ms | **28.07 ms** | **44×** |
| `r_amp_err_pct` | 0.143 % | 0.226 % | 1.6× |
| `rmse` | 0.00150 | 0.00421 | 2.8× |
| `rpeak_mae_ms` | 0 | 0.046 | — |

`qrs_dur_err_ms` 만 44 배다. 나머지는 2~3 배 안에 있다.

**원인은 delineator 다.** 합성 ECG 는 beat 마다 파형이 거의 같아서 QRS 경계
탐색이 안정적이다. 실기록은 beat 마다 형태가 달라(호흡, 축 변화, 부정맥)
같은 40 dB 교란에도 경계 판정이 훨씬 크게 흔들린다.

이 한계는 **D0 floor 문서가 이미 예고하고 있었다**: *"여기서 쓴 것은 합성 ECG
다. 파형이 실제보다 규칙적이라 `qrs_dur_err_ms` 의 floor 가 낙관적으로 나올 수
있다."* 예고가 맞았고, 크기가 44 배였다 `[문헌]`(자체 문서).

### 조치와 검토한 대안

D1 loss ablation 표에서 `qrs_dur_err_ms` 의 loss 간 폭은 **3.7~13 ms** 로 floor
28.07 ms 에 한참 못 미친다. 그런데 표는 최소값을 굵게 표시하고 있었다.

| 안 | 내용 | 판단 |
|---|---|---|
| A | 각주로만 경고 | 기존 방식. **실제로 내가 그 각주를 읽고도 표의 굵은 글씨를 먼저 믿을 뻔했다** |
| **B** | 폭이 floor 미만인 열은 **굵게 표시하지 않고**, 그 사실을 표 아래 명시 | 채택 |
| C | 그 지표를 D1 표에서 제거 | 값 자체는 정보다(모든 방법이 20 ms 대라는 것). 과잉 |

**B.** 표를 읽는 사람이 각주까지 가지 않아도 '여기서는 승자가 없다' 가 보이게 했다.
`make_ablation_table.py` 가 축별 floor 를 읽어 열 단위로 판단한다.

### 놓쳤다면

**"D1 에서는 L2/L3 손실이 L1 보다 QRS 를 잘 보존한다"** 가 결과로 실렸을 것이다
(표상 25.995 → 22.267 ms). 실제로는 그 3.7 ms 차이가 delineator 자체의 흔들림
28 ms 안에 완전히 묻혀 있어 아무것도 주장할 수 없다.

### 일반화

> 지표의 분해능은 **데이터에 따라 달라진다.** 한 데이터셋에서 잰 floor 를
> 다른 데이터셋의 판정에 쓰면 안 된다. 특히 **알고리즘(delineator)이 개입하는
> 파생 지표**는 신호의 규칙성에 민감해서, 합성에서 잰 분해능이 실데이터에서
> 그대로일 것이라 기대할 근거가 없다.

## F-15. D1 에서 `M_FE` 의 왜곡 하한 147 dB 는 성능이 아니라 참조 정의의 항등식이다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | P-8 (EXP-C 표를 읽다가) |
| 영향 | D1 의 EXP-C 표와 Pareto 그림(F5) 해석 |

### 배경 — 왜곡 하한(distortion floor)이란

**잡음이 전혀 없는 clean 신호**를 방법에 그대로 통과시켰을 때의 출력 SNR 이다.
낮으면 그 방법은 잡음이 없어도 신호를 망가뜨린다는 뜻이고, 출력 SNR 은 원리적으로
이 값을 넘을 수 없으므로 **성능의 천장**이기도 하다 (F-4 가 이 측정으로
front-end 버그를 잡았다).

`M_FE` 는 공통 front-end(HPF 0.5 + LPF 100 + 조건부 60 Hz notch)만 적용한
기준선이다.

### 발단

D1 EXP-C 표에서 `M_FE` 의 왜곡 하한이 **147.29 dB** 로 나왔다 `[측정]`.
D0 에서는 34.13 dB 였다. 다른 방법은 D0 20~34 dB, D1 18~40 dB 로 비슷한데
`M_FE` 만 4 배 넘게 뛰었다.

**147 dB 는 잡음 전력비 10^14.7 이다.** float64 연산의 수치 오차 수준이지
물리적으로 의미 있는 값이 아니다. 이 크기 자체가 단서였다.

### 먼저 의심한 것

**guard band 나 정렬 문제로 잔차가 0 에 가까워진 것**을 의심했다. F-3/F-4 에서
비슷한 경계 효과를 겪었기 때문이다.

배제 근거: 같은 실행에서 `B01`(71.57 dB)·`B02`(50.41 dB)도 D0(둘 다 34.13)보다
크게 올랐다 `[측정]`. `M_FE` 하나의 문제가 아니라 **D1 축 전체에서 front-end
계열이 함께 올랐다**는 것이 드러나, 경계 효과가 아니라 정의 문제로 방향이 바뀌었다.

### 결정적 측정

D-3 으로 **D1 의 참조를 `FE(원본)` 으로 정의**했다. 그러면 왜곡 하한의 정의상:

```
왜곡 하한 = SNR( 참조 , 방법(clean) )
          = SNR( FE(x) , FE(x) )        ← M_FE 의 경우
          = ∞  (수치 오차만 남는다)
```

**즉 `M_FE` 의 왜곡 하한이 무한대인 것은 측정 결과가 아니라 항등식이다.**
147 dB 는 그 무한대가 float64 에서 잘린 값이다.

| | D0 (참조 = clean 원본) | D1 (참조 = `FE(clean)`) |
|---|---|---|
| `M_FE` | 34.13 | **147.29** |
| `B01` | 34.13 | 71.57 |
| `B02` | 34.13 | 50.41 |
| `M06` | 24.88 | 22.22 |
| `M08` | 27.42 | 23.51 |

front-end 를 쓰지 않는 계열(`M06`/`M08`)은 D0/D1 이 비슷하다. **front-end 를
통과시키는 방법만 D1 에서 올랐다.** 참조가 그쪽으로 옮겨갔기 때문이다.

### 조치

**수치를 고치지 않는다.** D-3 은 유효한 결정이고, 이 값은 그 정의의 정확한 귀결이다.
대신 **해석을 문서에 못박는다** — D1 의 EXP-C 에서 front-end 계열의 왜곡 하한은
"신호를 잘 보존한다" 가 아니라 **"참조와 같은 연산을 적용했다"** 로 읽어야 한다.

### 놓쳤다면

Pareto 그림(F5)에서 `M_FE` 가 왜곡 축의 맨 오른쪽 끝에 찍힌다. **"front-end 는
신호를 전혀 손상시키지 않으면서 잡음만 제거한다"** 가 결론으로 실렸을 것이다.
실제로는 그 축에서 `M_FE` 를 다른 방법과 비교하는 것 자체가 성립하지 않는다.

### 일반화

> 참조(정답)의 정의를 바꾸면, **그 정의에 포함된 연산을 쓰는 방법은 자동으로
> 유리해진다.** 이것은 성능이 아니라 순환이다. 참조를 재정의할 때는
> "어떤 방법이 이 정의로 인해 공짜 점수를 받는가" 를 먼저 따져야 한다.
> D-3 은 옳은 결정이었지만, 이 귀결까지 그때 적어뒀어야 했다.

## F-13. ground-truth 없는 SNR 추정기가 실데이터에서 8배 편향된다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | P-7(D1 사전 측정) |
| 영향 | 실측 장비 SNR 인용(STEP 29, RQ1 의 "실측 조건 ≈15 dB")의 신뢰도 |

### 배경 — 왜 'ground truth 없는 SNR 추정기' 가 필요한가

지금까지의 모든 SNR 지표는 **참값 `x` 를 알아야** 계산된다. 그런데 실측 장비로
찍은 ECG 에는 참값이 없다 — 잡음이 섞인 신호 하나뿐이다.

그래도 "우리 장비의 SNR 이 대략 얼마인가" 는 알아야 한다. EXP-A 는 입력 SNR 에
따라 최적 기법이 달라진다고 말하는데, 우리 장비가 그 곡선의 어디에 있는지
모르면 **어떤 기법을 쓸지 고를 수 없기 때문**이다.

그래서 참값 없이 SNR 을 추정하는 방법 셋을 두고, **참값을 아는 데이터로
교정표를 만들어** 그 편향을 미리 재둔다.

| | 원리 |
|---|---|
| (A) beat-averaged residual | beat 들을 평균 낸 것을 '신호', 각 beat 와 그 평균의 차이를 '잡음' 으로 본다 |
| (B) half-sample consistency | 데이터를 두 절반으로 나눠 상관 `r'` 을 구하고 `corr = r'/(1+r')` 로 SNR 을 역산 |
| (C) isoelectric TP segment | T파와 P파 사이 평평해야 할 구간의 분산을 잡음 전력으로 본다 |

**편향**은 (추정값 − 참값)이다. 기준을 1.5 dB 로 둔 것은, 그보다 크면
EXP-A 곡선에서 엉뚱한 지점을 지목하게 되기 때문이다.

### 발단

D1 에서 SNR 추정기 교정을 돌리니 AWGN 조건 편향이 **7.59 dB** 로 나왔다
(D0 는 0.9 dB). 기준의 5배를 넘는 실패다.

### 먼저 의심한 것과 배제

**F-12 의 참조 정의 결함**을 의심했다. 같은 P-7 실행에서 SWT 튜닝이 그것 때문에
음수였기 때문이다. 그런데 참조를 고치고 재측정해도 **7.56 dB** 로 거의 그대로였다.
즉 참조와 무관한 별개 원인이다.

### 결정적 측정

참조 정의를 고치기 **전후**로 같은 교정을 돌려 비교했다.

| | AWGN 편향 (기준 < 1.5 dB) |
|---|---|
| D0 (합성) | **0.9 dB** (통과) |
| D1, 잘못된 참조 | 7.59 dB |
| D1, **올바른 참조** | **7.56 dB** | `[측정]`

참조를 고쳐도 값이 그대로라는 것이 "이건 F-12 와 다른 원인" 이라는 증거였다.

### 원인

세 추정기 모두 **"beat 가 반복되고 그 잔차가 잡음"** 이라는 가정 위에 서 있다.
- (A) beat-averaged residual: beat 를 평균 내 신호로, 잔차를 잡음으로 본다
- (B) half-sample consistency: 두 절반의 상관에서 SNR 을 역산
- (C) isoelectric TP segment: 등전위 구간의 분산을 잡음으로 본다

실제 ECG 는 **beat 마다 형태가 다르다.** 그 변동이 전부 잡음으로 계산된다.
합성 ECG 는 커널이 정해져 있어(F-8 수정 후에도 기록 내에서는 일정) 이 가정이
훨씬 잘 맞는다.

### 놓쳤다면

실측 장비의 SNR 을 **8 dB 낮게** 추정하고, 그 값으로 "우리 장비는 EXP-A 곡선의
이 지점" 이라고 잘못 지목했을 것이다. RQ1 의 답이 "15 dB 조건" 이 아니라
"7 dB 조건" 으로 바뀌면 최적 기법이 달라진다.

### 조치

`docs/04_snr_estimator_calibration_d1.md` 의 편향표를 **D1 기준으로 갱신**하고,
실측 SNR 을 인용할 때 이 편향을 함께 쓰도록 한다. 단일 값으로 인용하지 않는다.

### 일반화

> ground truth 가 없는 추정기는 **그 가정이 성립하는 데이터에서만** 교정된다.
> 합성 데이터로 교정한 추정기를 실데이터에 쓰면 편향이 그대로 남는다.
> 교정표는 **적용할 데이터와 같은 축에서** 만들어야 한다.

## F-14. Sameni 는 커널을 아는 조건에서만 강하다 — 실제 파이프라인에서는 단순 bandpass 이하

| | |
|---|---|
| 상태 | **확정** (근거 교체 — 아래 '초판 근거의 철회') |
| 발견 | P-7 에서 제기, P-8 의 D1 EXP-A 로 확정 |
| 영향 | `M05` 를 "저 SNR 대안" 으로 쓰려던 서술 폐기 |

### 배경 — Sameni 방법이 필요로 하는 것

Sameni EKF/EKS 는 ECG 를 McSharry ODE 로 모형화한다 — 심장 주기를 위상 `θ` 로
표현하고, P·Q·R·S·T 파를 위상 위의 가우시안 봉우리 합으로 쓰는 미분방정식이다.
그 모형을 상태방정식으로 삼아 칼만 필터를 돌린다. EKF 는 전방 필터,
EKS 는 거기에 후방 평활(RTS smoother)을 더한 것이다.

따라서 이 방법은 **커널 파라미터**(봉우리마다 진폭 `α`, 폭 `b`, 위상 `θ`)를
알아야 한다. 실제로는 신호에서 추정한다.

### 발단

F-12 를 고치고 D1 사전 측정을 다시 돌렸을 때, SWT 는 −0.49 → +12.47 로 완전히
회복됐는데 **Sameni 만 +0.40 → +5.91 에 그쳤다** `[측정]`. 같은 참조 결함을
공유했는데 회복 정도가 크게 달랐다.

### 먼저 의심한 것

**구현 결함**을 먼저 의심했다 — F-6 에서 실제로 Sameni 구현 버그 2건이
성능을 10 dB 이상 떨어뜨린 전례가 있었기 때문이다. 그때 얻은 규칙이
*"어떤 방법이 기대보다 못하면 방법을 탓하기 전에 구현을 검증한다"* 였다.

배제 근거: 그 규칙대로 만들어 둔 자가진단(`C1`~`C6`)을 D1 에서 돌렸고
**전부 통과했다** `[측정]` — 위상 정렬(median |Δ| = 0.00 ms), front-end 전치
효과(+5.48 dB), template 적합(R² = 0.9888), 측정잡음 추정(−2.86 dB),
EKS > EKF(+0.41 dB), 진폭 정규화(gain_bias 0.9739). 구현은 건전했다.
(`docs/06_sameni_diagnosis_d1.md`)

### 결정적 측정 — D1 EXP-A

`M05` vs `M01`(단순 bandpass 0.5–40 Hz + auto notch), paired Wilcoxon + Holm,
22 기록 `[측정]`:

| | D0 | D1 |
|---|---|---|
| `snr_imp_scaled` Δ | +0.074 | **−2.001** |
| p(Holm) | 0.827 | 0.109 |
| effect r | −0.075 | −0.581 |
| `qrs_dur_err_ms` Δ | — | **+30.444** |
| p(Holm) | — | **4.01e-04** |
| effect r | — | +0.905 |

**두 축 모두에서 `M05` 는 단순 bandpass 를 이기지 못한다.** D0 에서는 무승부고
(p = 0.83), D1 에서는 SNR 이 2 dB 밀린다 — Holm 보정 후 유의하지는 않으나
부호가 뒤집혔고 effect r 이 −0.58 로 커졌다.

**그리고 D1 에서 QRS 폭을 명백히 망가뜨린다.** Δ +30.4 ms 는 이 축의 지표
분해능 28.07 ms(F-16)를 넘고, 22 기록 대부분에서 일관되게 나쁘다
(effect r +0.905, p(Holm) = 4e-04). `M05` 의 절대값 50.72 ms 는 `M00`(무처리,
35.50 ms)보다도 나쁘다 — **평활이 QRS 를 실제로 뭉갠다.**

반면 커널을 주입한 조건(D0 자가진단 DoD)에서는 **+16.21 dB** 로 매우 강하다.
이 격차가 이 항목의 요지다.

### 초판 근거의 철회

초판은 다음 표를 핵심 근거로 삼았다.

| | D0 | D1 |
|---|---|---|
| DoD 개선폭 | +16.2 dB | +5.91 dB |

**이 비교는 성립하지 않는다 (F-17).** 주입한 `DEFAULT_KERNEL` 은 D0 에서는
생성 커널이지만 D1 에서는 그 환자와 무관한 커널이다. 두 칸이 서로 다른 양이다.
지금은 위의 EXP-A 근거로 대체했고, D1 의 DoD 는 N/A 로 보고한다.

### 이 확정이 말하는 것과 말하지 않는 것

**말하는 것**: `M05` 의 인상적인 숫자(+16.2 dB)는 **커널을 아는 조건**에서만
나온다. 커널을 추정해야 하는 실제 파이프라인에서는 D0 에서 bandpass 와 무승부,
D1 에서는 그 아래이고 QRS 를 훼손한다.

**말하지 않는 것**: "D0 가 McSharry ODE 로 생성됐기 **때문에**" 라는 인과는
직접 검증되지 않았다. D0→D1 은 생성 모형만 바뀌는 것이 아니라 잡음 조성·형태
다양성·참조 정의가 함께 바뀐다. 분리하려면 **McSharry 가 아닌 다른 생성기로
만든 합성축**이 필요한데 이 과제 범위에 없다. 보고서에는 관측까지 쓰고 원인은
가설로 제시한다.

### 놓쳤다면

`M05` 의 D0 DoD 성능(+16.2 dB)을 그대로 인용해 **"모델 기반 방법이 저 SNR 에서
경쟁력 있다"** 고 썼을 것이다. 실측 장비에 적용했을 때 그 성능이 나오지 않는데
왜인지 설명하지 못했을 것이다.

### 일반화

> 어떤 방법이 **부가 정보를 받은 조건**에서 낸 성능을, 그 정보를 추정해야 하는
> 조건의 성능처럼 인용하지 않는다. 그 둘의 격차 자체가 결과다 —
> 이 경우 16.2 dB 대 −2.0 dB 다.

## F-12. MIT-BIH 를 '정답' 으로 두면 front-end 를 쓰는 모든 방법이 부당하게 진다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | `72fcc52` / P-7(D1 사전 측정) 중 |
| 영향 | D1 실험 **전체**. 이대로 돌렸다면 "아무 처리도 하지 않는 것이 최선" 이라는 결론이 나왔다 |

### 발단 — 무엇이 이상해 보였나

D1 용 SWT 파라미터를 TRAIN split 에서 재탐색했는데 결과가 **음수**로 나왔다. `[측정]`

```
D1:  tune mean = -0.49 dB   holdout = -0.55 dB   (교과서 설정 -4.67)
D0:  tune mean = +11.4 dB
```

#### 이 숫자들이 무엇인가

`snr_imp_scaled` **[dB]** 의 평균이다. 방법을 통과시킨 뒤의 SNR 에서 입력 SNR 을
뺀 값이므로, **양수면 잡음을 줄인 것이고 음수면 오히려 나빠진 것**이다.
0 이면 아무 효과가 없다는 뜻이다.

`tune` 과 `holdout` 은 **파라미터를 고르는 데 쓴 데이터**와 **고르는 데 쓰지 않고
검증만 한 데이터**를 각각 가리킨다. 파라미터 탐색에서 이 둘을 나누는 이유는,
파라미터를 고른 그 데이터로 성능을 보고하면 값이 낙관적으로 편향되기 때문이다 —
그 데이터에 맞춰 고른 것이므로 잘 나오는 게 당연하다. 둘 다 TRAIN split 안에서
나눈다(TEST 에서 고르면 그 선택이 평가에 새어 들어간다).
`textbook-baseline` 은 **튜닝하지 않은 교과서 기본 설정**의 성능으로, 튜닝이
실제로 이득을 냈는지 보는 대조군이다. (→ `18_glossary.md` 6절)

#### 왜 "파라미터 문제가 아니다" 라고 판단했는가

두 값의 관계로 진단할 수 있는 경우가 셋이다.

| 관측 | 진단 |
|---|---|
| tune 높음 · holdout **낮음** | **과적합.** 파라미터가 tune 데이터의 특성에 맞춰졌다 |
| tune ≈ holdout, 둘 다 높음 | 정상. 파라미터가 일반화된다 |
| **tune ≈ holdout, 둘 다 낮음** | **파라미터 문제가 아니다** |

여기서 관측된 것은 세 번째다. tune −0.49 와 holdout −0.55 가 **거의 같으면서
둘 다 음수**였다.

이것이 왜 "파라미터를 잘못 골랐다" 를 약화시키는가. 탐색이 잘못된 파라미터를
골랐다면 그것은 **tune 데이터에 과하게 맞춰진 파라미터**일 것이고, 그렇다면
적어도 tune 에서는 좋아야 한다 — 탐색 알고리즘이 tune 성능을 최대화하도록
돌아가기 때문이다. 그런데 **탐색이 도달한 최선조차 tune 에서 음수**였다. `[로그]`

교과서 설정(−4.67)보다는 나았으므로 탐색 자체는 작동하고 있었다. 즉
"탐색이 고장났다" 도 아니었다.

> **여기서 결론을 한 단계 밀어붙이지 않는다.** 이 관측은 "특정 파라미터 하나를
> 잘못 골랐다" 로 설명하기 어렵다는 **근거**이지, *탐색 공간의 모든 조합이
> 음수임을 증명하지는 않는다.* 탐색은 2단계로, 1단계는
> `sigma_source`(4) × `mode`(3) × `protect_qrs`(2) = 24 조합을 전수 평가하지만
> 2단계의 `k` 벡터는 **좌표탐색**이라 전수가 아니다 `[코드]`.
>
> 게다가 당시 24 조합 각각의 값은 **지금 확인할 수 없다** — 참조를 고친 뒤
> 재실행하면서 `search.csv` 가 덮어써졌고, 로그에는 각 단계의 최선만 남아 있다
> (stage1 최선 −0.75, stage2 최선 −0.49) `[로그]`. 이 기록 손실은 O-10 에 남겼다.

그래서 당시 판단은 **"파라미터가 아니라 그 바깥을 봐야 한다"** 는 잠정 가설이었다.
그 바깥이 무엇인지는 다음 단계에서 좁혔다.

### 먼저 의심한 것과 그것을 배제한 방법

1. **"D1 파라미터가 D0 와 달라서"** — 재탐색을 이미 했는데도 음수였으므로 기각.
2. **"실제 잡음(NSTDB)이 합성 잡음과 달라서"** — 코드를 보니 `build_cases` 는
   합성 잡음만 쓴다. clean 만 D1 이었다. 잡음 종류는 D0 와 동일하므로 기각.
3. **"SWT 가 실데이터에서 원래 약해서"** — 여기서 멈출 뻔했다. 그런데 그렇다면
   front-end 단독(`M_FE`)은 여전히 양수여야 하는데, 확인해 보니 그것도 음수였다.
   즉 **SWT 의 문제가 아니라 front-end 를 쓰는 것 자체가 손해**였다.

3번이 결정적인 방향 전환이었다. "SWT 가 나쁘다" 에서 "front-end 가 손해다" 로
질문이 바뀌자, 원인이 **참조 신호 쪽**에 있다는 가설이 나왔다.

### 결정적 측정

MIT-BIH 신호에 **잡음 없이 front-end 만** 통과시키고 원본과의 SNR 을 쟀다.

| | 잡음 없이 FE 만 통과 → 원본과의 SNR | 10 dB 에서 FE 의 효과 |
|---|---|---|
| D0 (합성) | 53.24 dB (사실상 무해) | **+1.06 dB** |
| D1 (MIT-BIH) | **9.32 dB** | **−3.10 dB** |

**MIT-BIH 신호는 clean 이 아니다.** 이미 기저선 변동을 담고 있는데 그것을 정답으로
두었으므로, front-end 가 그 성분을 지울수록 정답에서 **멀어진다.**

참조를 바꾸면 순서가 정상화된다 (10 dB, 4 record):

| 방법 | 참조 = raw | 참조 = FE(raw) |
|---|---|---|
| `M00` 무처리 | **10.42** | 8.02 |
| `M_FE` | 10.58 | **21.67** |
| `M04` | 10.49 | 19.03 |
| `M01` | 10.64 | 17.93 |
| `M05` | 9.48 | 13.46 |

참조=raw 에서는 모든 방법이 10.4~10.6 에 뭉치고 **무처리가 `M04` 보다 높다.**

### 조치와 검토한 대안

과제 목표를 **"0.5~100 Hz 대역의 ECG 를 복원한다"** 로 명시하고 참조를
`x_ref = FE(x_raw)` 로 정의했다. 검토한 대안은 D-3 에 기록.

잡음은 여전히 **원본**에 섞는다(취득계는 대역제한 전 신호를 본다). EXP-C 의
왜곡 측정도 원본을 입력으로 준다 — 참조를 입력으로 주면 front-end 가 두 번 걸린다.
학습 타깃도 같은 대역으로 맞췄다. 다르면 신경망이 front-end 를 되돌리는 법을 배운다.

### 비용

D1 사전 측정 4종 전부 재실행(약 50분). **D0 는 재실행하지 않아도 된다** —
같은 비교를 D0 에서 하면 차이가 0.02 dB 이하다(위 표의 53.24 dB 가 그 이유).
측정으로 확인했다.

### 놓쳤다면

D1 주 결과표에 **"무처리(M00)가 튜닝된 SWT보다 낫다"** 가 실렸을 것이고,
그 표를 보고도 틀렸다는 것을 알아채기 어려웠을 것이다 —
모든 방법이 10.4~10.6 으로 촘촘히 뭉쳐 있어 "차이가 없다" 로 읽히기 때문이다.

### 일반화

> 공개 데이터셋의 '깨끗한' 기록을 ground truth 로 쓸 때, 그것이 **정말로
> 우리가 복원하려는 신호인지** 확인해야 한다. 아니라면 전처리를 거친 방법일수록
> 손해를 보고, 그 손해는 성능 차이처럼 보인다.
> **이 함정은 합성 데이터에서는 드러나지 않는다** — 거기서는 clean 이 정의상
> clean 이기 때문이다. D0 만으로 검증을 마쳤다면 영원히 못 봤을 결함이다.

### 수정 후 검증 — 참조가 원인이었음이 확인됐다

D1 사전 측정 4종을 올바른 참조로 다시 돌린 결과:

| 측정 | 잘못된 참조 | **올바른 참조** | D0 |
|---|---|---|---|
| SWT 튜닝 tune | −0.49 | **+12.47** | +11.4 |
| SWT 튜닝 holdout | −0.55 | **+12.58** | — |
| Sameni 진단 DoD | +0.40 dB | **+5.91 dB** | +16.2 |
| Sameni 통과 | 5/7 | **6/7** | 7/7 |
| SNR 추정기 AWGN 편향 | 7.59 dB | 7.56 dB | 0.9 |

**SWT 는 완전히 뒤집혔다** (−0.49 → +12.47, D0 와 같은 수준). holdout 이
tune 보다 높아 과적합도 없다. 발단이 된 그 음수는 SWT 의 문제가 아니었다.

**Sameni 는 부분적으로만 회복됐다** (+0.40 → +5.91, D0 는 +16.2). 참조 결함이
일부였고 나머지는 다른 원인이다 — F-14 로 따로 추적한다.

**SNR 추정기 편향은 참조와 무관했다** (7.59 → 7.56). 이건 실제 특성이며
F-13 으로 기록한다.

> 이 검증이 없었다면 "합성이 모델 기반 방법을 과대평가한다" 는 잠정 가설을
> 그대로 결론으로 실었을 것이다. 실제로는 **SWT 에 대해서는 완전히 틀린 가설**
> 이었다. 잠정 관측을 `[미확정]` 으로만 표시하고 F 로 승격하지 않은 것이
> 결과적으로 옳았다.

### 후속 정정 — 같은 원칙을 일괄 적용한 것이 실수였다

F-12 를 반영하며 보조 스크립트 네 개 모두 "잡음을 원본에 섞도록" 일괄 수정했는데,
**metric floor 측정에는 그게 틀렸다.** 이 측정의 질문은 "이상적인 출력을 넣었을 때
지표가 얼마나 흔들리는가" 이므로 출력이 참조와 **같은 대역**에 있어야 한다.
원본에 섞으면 front-end 차이(9.3 dB)가 통째로 들어가 floor 가 부풀려진다.

이상을 알아챈 신호는 **`r_amp_err_pct` floor 가 242 %** 로 나온 것이었다. `[측정]`

`r_amp_err_pct` 는 R-peak 진폭의 **상대오차 백분율**이다:

$$\text{r\_amp\_err\_pct} = 100 \times \operatorname{mean}_i
\frac{\lvert \hat a_i - a_i\rvert}{\lvert a_i\rvert}$$

`a_i` 는 i번째 beat 의 R-peak 진폭이고, 0 이 완벽하다. 242 % 는 "진폭이 평균
2.42배 어긋났다" 는 뜻이다.

**수학적으로 242 % 가 불가능한 것은 아니다.** 상한이 없는 지표이므로 출력이
참값의 3.4배면 그 값이 나온다. 불가능한 것은 **이 측정의 맥락**이다 —
metric floor 는 참조에 40 dB AWGN(거의 무시할 수준의 교란)만 더한, 사실상
참조와 같은 신호를 '출력' 으로 넣고 재는 값이다. **그런 입력에서 R-peak 진폭이
2.4배 어긋날 수는 없다.** 정상이라면 0.1 % 수준이어야 한다(D0 는 0.134 %).

값이 그럴듯한 범위(예: 5 %)였다면 "실데이터라 그런가 보다" 하고 받아들였을
것이다. **자릿수가 어긋난 덕분에 측정을 의심하게 됐다.** 정정 후 0.226 %.

정정 전후의 D1 floor (`floor_p95`, D0 와 비교): `[측정]`

| 지표 | D0 | D1 (잘못된 측정) | **D1 (정정 후)** |
|---|---|---|---|
| `qrs_dur_err_ms` | 0.639731 | 40.997 | **28.072098** |
| `r_amp_err_pct` | 0.134493 | 242.22 | **0.226334** |
| `rmse` | 0.001504 | — | 0.004207 |

`qrs_dur_err_ms` 의 큰 값은 정정 후에도 남는다(D0 의 **44배**). 이것은 측정
오류가 아니라 **실데이터의 실제 특성**이다 — beat 마다 형태가 달라 거의 완벽한
입력에서도 QRS 경계 추정이 28 ms 흔들린다. **D1 에서 이 지표는 사실상 판별력이
없고**, D0 보고서에서 논한 정도의 차이(10~17 ms)는 전부 이 안에 묻힌다.

> **교훈**: 같은 원칙이 목적에 따라 반대로 적용된다. "파이프라인을 모사하는
> 측정" 과 "지표 자체의 안정성을 재는 측정" 은 참조 기준이 다르다.

## F-11. oracle 도 front-end 의 천장에 걸려 있다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | `7415e26` / P-4 의 EXP-C 결과를 읽다가 |
| 영향 | "`M04` 가 oracle 과 동일한 무손실" 이라는 초판 서술의 근거를 무너뜨림 |

### 발단

#### EXP-C 가 무엇을 재는가

**잡음을 전혀 넣지 않고 깨끗한 신호를 그대로 통과시킨 뒤**, 출력이 입력과
얼마나 달라졌는지를 SNR 로 잰다. 이 값이 **왜곡 하한(distortion floor)** 이고,
"이 방법은 지울 잡음이 없을 때도 신호를 얼마나 망가뜨리는가" 를 답한다.

값이 높을수록 무손실이다. 무처리(`M00`)는 입력을 그대로 내보내므로 ∞ 다.
이 값은 **그 방법이 도달할 수 있는 천장**이기도 하다 — 잡음을 아무리 잘 지워도
자기 자신이 만드는 왜곡보다 좋아질 수 없기 때문이다.

#### oracle 이 무엇인가

`B01`/`B02` 는 **정답을 미리 아는** 가상의 방법이다. `B01` 은 참값을 보고 각
wavelet 계수를 최적으로 살릴지 죽일지 정하고, `B02` 는 참값을 보고 최적 Wiener
필터를 만든다. 실제로는 구현할 수 없지만, **"이 계열이 최선을 다하면 어디까지
갈 수 있는가"** 를 보여주는 상한선이다. (→ `18_glossary.md` 8절)

#### 관측

EXP-C 출력에서 `B01`(oracle wavelet), `B02`(oracle Wiener),
`M_FE`(front-end 단독) 세 개가 **소수점까지 같은 34.13 ± 3.72 dB** 로 나왔다.

**이것이 왜 이상한가.** 세 방법은 원리가 전혀 다르다 — 하나는 wavelet 계수를
조작하고, 하나는 주파수영역 Wiener 필터이며, 하나는 단순 대역통과 필터다.
서로 다른 세 알고리즘이 소수점까지 같은 값을 내는 것은 우연으로 설명되지 않는다.

게다가 oracle 은 **정답을 알고 있다.** 잡음이 없는 입력을 받았으니 그대로
통과시키면 완벽한 복원(∞ dB)이 가능한데, 왜 34 dB 에서 멈추는가.

### 먼저 의심한 것

**우연의 일치**를 의심했다. 그런데 셋 다 `34.13 ± 3.72` 로 **표준편차까지**
같았다. 22개 record 에 대한 분포가 통째로 일치하는 것은 우연일 수 없다.

두 번째로 **측정 버그**(같은 값을 세 번 복사)를 의심했으나, `M04` 34.10 /
`M04np` 34.00 처럼 **가까우면서 다른** 값들이 함께 있어 기각했다.

### 결정적 측정

세 값이 같다는 사실 자체가 측정이었다 `[측정]`. 공통 요소는 하나뿐이다 —
**셋 다 front-end 를 통과한다.** 즉 34.13 dB 는 어떤 방법의 성질이 아니라
**공통 전처리가 정한 천장**이고, front-end 를 쓰는 모든 방법이 이 위로 갈 수 없다.

같은 실행에서 두 번째 사실도 나왔다 (`M_FE` 대비 순수 기여분, 10 dB):

| method | bw | em | impulse |
|---|---|---|---|
| `M04` | **−0.00** | **−0.00** | **+0.00** |
| `B01` (oracle) | **−0.00** | +0.07 | +8.21 |

**wavelet thresholding 은 bw·em 에서 구조적으로 0 을 기여한다.** `M04` 뿐 아니라
oracle 조차 그렇다. 기저선 변동은 근사계수 `A5` 에 실려 있고 thresholding 은
세부계수만 건드리므로 **정답을 알아도 못 고친다.**

### 놓쳤다면

"SWT 가 baseline wander 에서 oracle 수준" 이라는 서술이 유지됐을 것이다.
실제로는 **둘 다 아무것도 못 하고 있었고**, 그 조건의 19 dB 는 전부 front-end 몫이다.

### 일반화

> oracle 을 "이론적 상한" 으로 인용하기 전에 그것이 **어떤 전처리를 포함하는지**
> 확인해야 한다. 전처리를 공유하면 oracle 은 그 전처리의 상한이지 문제의 상한이 아니다.
> 그리고 **oracle 이 못 고치는 조건은 그 계열 전체가 못 고치는 조건**이며,
> 그 사실 자체가 결과다.

## F-10. "모든 방법에 동일 조건" 이 선언에 그쳐 있었다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | `cfb5d1a` / 외부 검토자의 지적을 확인하던 중 |
| 영향 | **RQ1·RQ4 의 결론이 뒤집힘.** 전 모델 재학습 + 전 실험 재실행 |

### 배경 — 공정성 규약과 `M_FE`

이 프로젝트는 **모든 방법이 동일한 전처리를 받는다**는 규약을 세웠다.
그 전처리(front-end)는 HPF 0.5 Hz + LPF 100 Hz + 조건부 60 Hz notch 이고,
`M_FE` 라는 이름으로 **방법 목록에도 등록**되어 있다.

`M_FE` 를 방법으로 등록한 이유는, 어떤 방법의 성능을 볼 때
**"그 이득 중 얼마가 이 공통 전처리에서 온 것인가"** 를 표에서 바로 읽기
위해서다. 예를 들어 `M04` 가 20 dB 를 내고 `M_FE` 도 20 dB 를 낸다면,
`M04` 의 고유 기여는 0 이라는 뜻이다.

### 발단 — 지적은 오탐이었는데 그것을 확인하다 진짜를 찾았다

외부 검토자가 "공통 front-end 와 `M01` 의 notch 가 중복 적용될 수 있다" 고
지적했다. 코드를 확인하니 **중복은 없었다** (`run_exp` 에 전역 FE 단계가 없고
각 방법이 내부에서 정확히 1회만 적용). 지적 자체는 오탐이었다.

그런데 "각 방법이 FE 를 몇 번 적용하는가" 를 세는 과정에서 표가 이렇게 나왔다:

| 방법 | front-end |
|---|---|
| `M01`~`M05`, `B01`, `B02` | ✅ |
| **`M06`, `M08`** | ❌ **없음** (학습·추론 모두 raw 입력) |

**딥러닝만 공통 front-end 를 받지 않고 있었다.** 규약을 문서에 써 두고
코드에서 확인하지 않은 결과다.

### 먼저 의심한 것 — 지적 자체는 오탐이었다

외부 지적은 "notch 가 중복 적용된다" 였다. 이것부터 확인했고 **틀렸다**.
`run_exp` 에 전역 front-end 단계가 없고, 각 방법이 내부에서 정확히 1회만
적용한다는 것을 코드로 확인했다.

**지적이 오탐이라는 것을 확인하는 과정에서** "그럼 각 방법이 FE 를 몇 번
적용하는가" 를 전수 조사했고, 거기서 딥러닝이 **0회**라는 것이 나왔다.

### 결정적 측정

`M_FE`(front-end 만)를 대조군으로 넣어 기여를 분해했다 (입력 10 dB):

| 잡음 | `M_FE` 만 | `M04` | `M06` |
|---|---|---|---|
| baseline wander | **20.26** | **20.26** | 6.25 |
| pli 60 Hz | 17.46 | 19.41 | 11.99 |
| awgn | 1.46 | 7.91 | 8.46 |
| impulse | 0.44 | 0.44 | **10.58** |

**baseline wander 에서 `M04` 와 front-end 단독이 소수점까지 동일하다.** `[측정]`
(이 관찰이 나중에 F-11 로 이어졌다.)

### 조치

학습·추론 양쪽에 동일하게 front-end 를 적용하도록 고치고, 체크포인트에
`frontend` 플래그를 기록해 추론이 학습과 같은 전처리를 쓰도록 했다.
주 조건은 `frontend: true`(실사용 시나리오), 부록이 `false`(알고리즘 본질) — D-1 참조.

창 양쪽에 실제 이웃 구간을 여유로 붙여 필터링한 뒤 가운데만 사용한다.
그러지 않으면 4.096 s 창 전체가 HPF 트랜지언트가 된다.

### 비용

전 모델 재학습 + EXP-A/B/C/E 전부 재실행. 그리고 그 여파로 F-9 가 발생했다.

### 놓쳤다면

"실측 조건(15 dB)에서는 튜닝된 DSP 가 딥러닝보다 낫다" 는 결론이 유지됐을 것이다.
재측정 결과 15 dB 최고가 `M04` 7.79 → **`M08` 8.71** 로 바뀌었고,
`M06`/`M08` 이 `M01` 대비 통계적으로 **유의하지 않음(p=0.101) → 유의(p=9e−6, r≈1.0)** 로 바뀌었다.

### 일반화

> 공정성 규약은 **선언이 아니라 측정으로** 확인해야 한다.
> 그래서 이제 모든 결과표에 `M_FE`(front-end 단독)를 필수 행으로 넣는다.
> 각 방법의 이득 중 얼마가 공통 전처리에서 온 것인지 표 안에서 바로 읽히지
> 않으면, 같은 착각이 반복된다.

## F-9. 앞단을 고치면 뒤에 학습된 모든 체크포인트가 동시에 무효가 된다

| | |
|---|---|
| 상태 | **확정** (결론 철회 후 재측정) |
| 발견 | `e6d92ff` / 무결성 점검 중 |
| 영향 | STEP 19 loss ablation 의 결론 철회 |

### 배경 — VAL 과 TEST, 그리고 early stopping

데이터를 셋으로 나눈다: **TRAIN**(가중치를 학습), **VAL**(언제 멈출지와 어느
체크포인트를 쓸지 고름), **TEST**(최종 성능 보고).

`early stopping` 은 VAL 성능이 일정 epoch(patience) 동안 나아지지 않으면 학습을
멈추고, **VAL 이 가장 좋았던 시점의 가중치**를 최종 모델로 채택하는 방식이다.

여기서 중요한 것: **VAL 성능은 모델 선택에 이미 쓰인 값**이다. 여러 epoch 중
VAL 이 가장 좋은 것을 골랐으므로, 그 값은 "우연히 VAL 에 잘 맞은 정도" 만큼
부풀려져 있다. 그래서 **VAL 값으로 방법 간 우열을 주장하면 안 되고** TEST 에서
다시 재야 한다.

`DoD`(Definition of Done)는 이 프로젝트에서 각 STEP 의 완료 조건을 가리킨다.
STEP 19 의 DoD 는 "TEST split 에서 `snr_imp_scaled` / `qrs_dur_err_ms` /
`beat_cc` 를 함께 실은 표" 였다.

### 발단

상태표에 STEP 19 가 **✅ "L3/L4 가 L1 보다 우수"** 로 적혀 있었다. 그런데
DoD 산출물(`results/ablation_loss.csv`)을 찾으니 **존재하지 않았다.**

### 먼저 의심한 것

산출물이 없는 것을 보고 **"파일이 지워졌나"** 를 의심했다. `git log` 와
`results/` 를 확인하니 **생성된 적이 없었다.** 그렇다면 ✅ 의 근거가 무엇인지를
역추적해야 했고, 학습 로그의 VAL 값이 근거였다는 것이 드러났다.

### 두 가지가 틀렸다

1. **근거가 VAL 값이었다.** 학습 로그의 `snr_imp` 를 비교한 것인데, VAL 은
   early stopping 이 best 체크포인트를 고른 바로 그 대상이다. 그 위에서의
   비교는 낙관적으로 편향된다. DoD 가 요구한 것은 **TEST split** 표였다.
2. **교란 변수가 들어갔다.** F-10 을 고친 뒤 L1 체크포인트만 재학습되어,
   `L1(FE 있음)` vs `L3/L4(FE 없음)` 를 비교하는 꼴이 됐다. 이 차이는 손실
   함수 효과가 아니라 front-end 효과다.

### 조치

상태를 🔄 로 되돌리고 결론을 철회했다. 재발 방지로 `make_ablation_table.py` 가
체크포인트의 `frontend` 플래그와 **학습 시점 git hash** 를 표에 함께 싣고,
설정이 섞여 있으면 경고 후 **종료코드 2** 로 비교를 거부한다.

### 결정적 측정

DoD 산출물의 부재 자체가 첫 측정이었다 `[로그]`.

```
$ ls results/ablation_loss.csv
ls: cannot access 'results/ablation_loss.csv': No such file or directory
```

그리고 체크포인트의 학습 조건을 열어보니 섞여 있었다:

| run | frontend | 학습 시점 |
|---|---|---|
| m06_l1 (L1) | **True** | FE 수정 **후** |
| m06_l3 (L3) | **없음** | FE 수정 **전** |
| m08_l4 (L4) | **없음** | FE 수정 **전** |

`frontend` 키가 아예 없는 체크포인트가 있다는 것이 결정적이었다 — 그 값들은
서로 다른 파이프라인에서 나온 것이다.

### 놓쳤다면

"L3/L4 가 우수하다" 가 DoD 표 없이 결론으로 남았을 것이다. 실제로 TEST 에서
재보니 **`M06` 은 L2 만으로 효과의 대부분을 얻고**(미분항의 추가 이득은 작다),
**`M08` 의 L4 는 SNR 을 얻고 `beat_cc` 를 잃는다.** 원래 결론과 방향이 다르다.

### 재측정 결과 (TEST split)

`M06` 은 L2/L3 가 L1 을 **trade-off 없이** 지배한다 (20 dB: SNR 4.37→6.27,
QRS 폭 오차 13.99→10.50 ms). 효과의 대부분은 MAE 항이 낸다.
`M08` 의 L4 는 SNR 을 얻고 `beat_cc` 를 잃는다 (0.997→0.978, floor 의 5만 배).

### 일반화

> ablation 표는 **"각 행이 언제 학습됐는가"** 를 기록하지 않으면 파이프라인
> 수정 이후 조용히 거짓이 된다. 표는 숫자만이 아니라 그 숫자가 만들어진
> 조건을 함께 실어야 한다.

## F-8. 합성 벤치마크가 딥러닝을 12 dB 과대평가하고 있었다

| | |
|---|---|
| 상태 | **확정** |
| 발견 | EXP-A 예비 실행 결과가 비상식적이어서 |
| 영향 | 합성 데이터 생성기 전면 수정 + 그 이전 모든 DL 수치 무효 |

### 배경 — split 과 leakage

기계학습에서 **학습에 쓴 데이터로 성능을 재면** 그 값은 의미가 없다. 모델이
그 데이터를 외웠을 수 있기 때문이다. 그래서 데이터를 나눠(split) 학습에 쓰지
않은 부분에서 성능을 잰다.

**leakage** 는 그 분리가 실패해서 학습 정보가 평가로 새어 들어가는 것이다.
ECG 에서는 **record 단위**(=환자 단위)로 나누는 것이 표준이다. 같은 환자의
다른 구간을 평가에 쓰면, 모델이 그 환자의 파형을 외운 것을 성능으로 착각한다.

**morphology** 는 ECG 파형의 모양 — P파·QRS·T파의 위치, 진폭, 폭 — 을 가리킨다.
사람마다 다르고, 이것이 ECG 개인차의 핵심이다.

### 발단

EXP-A 예비 실행에서 **DL +26 dB vs DSP +3 dB** 가 나왔다.

**이 격차가 왜 이상한가.** 26 dB 는 잡음 전력을 **400배** 줄인다는 뜻이다
(10^(26/10) ≈ 400). 같은 평가 세트에서 고전 DSP 는 +3 dB(2배)에 그쳤는데,
같은 입력·같은 지표에서 한 방법만 200배 더 잘한다는 것은 **방법의 차이로
설명하기 어려운 크기**다 `[측정]`.

> 초판 기록에는 "문헌에서 보고되는 개선폭은 대개 한 자릿수 dB" 라고 적었는데,
> 이 프로젝트에 문헌 목록이 없어 **출처를 댈 수 없다.** 검증할 수 없는 외부
> 사실 주장이므로 뺐다. 위의 내부 대조(같은 세트에서 DSP +3 vs DL +26)가
> 훨씬 강한 근거이고, 실제로 당시 판단의 근거이기도 했다.

### 먼저 의심한 것

**부분적으로만 기록이 있다.**

확실한 것: 예비 실행에서 **DL +26 dB vs DSP +3 dB** 가 나왔고 `[측정]`,
그 결과를 "방법의 우열이 아니라 **벤치마크의 인공물**" 로 결론지었다 `[대화]`.

재구성: record 단위 split 자체는 정상이었으므로(코드에서 확인 가능),
"record 는 나뉘었는데 **무엇이 공유되는가**" 로 질문을 좁히면 남는 것이
**morphology** 다. 커널이 기록마다 같았으므로 그것이 답이었다. `[재구성]`

### 결정적 측정

같은 모델을 두 조건에서 평가했다 (입력 5 dB):

| 조건 | `M06` U-Net | `M04` SWT |
|---|---|---|
| 학습에 쓰인 morphology | **+16.5 dB** | +7.2 dB |
| **커널을 교란한** morphology | **+4~6 dB** | +8~12 dB |

딥러닝만 12 dB 가까이 떨어지고 SWT 는 오히려 올랐다. morphology 를 외웠다는
직접 증거다.

### 원인

초기 `SyntheticSource` 는 **모든 기록에 같은 커널**을 썼다. record 단위로
split 을 해도 morphology 는 train/test 가 완전히 동일하므로, 1 M 파라미터
신경망이 생성기를 통째로 외운다.

| 조건 (입력 5 dB) | `M06` U-Net | `M04` SWT |
|---|---|---|
| 학습에 쓰인 morphology | **+16.5 dB** | +7.2 dB |
| 커널을 교란한 morphology | **+4~6 dB** | +8~12 dB |

### 조치

기록(=피험자)마다 파형 위치·진폭·폭을 흔들고 낮은 확률로 T파를 역전시켰다
(`jitter_kernel`). 기록 간 beat template 상관이 **1.0 → 0.0~0.6** 으로 떨어졌고,
회귀 테스트 `test_synthetic_records_have_distinct_morphology` 로 고정했다.

### 놓쳤다면

**"딥러닝이 고전 DSP 를 26 dB 압도한다"** 가 주 결과로 실렸을 것이다.
그 격차는 방법의 우열이 아니라 신경망이 생성기를 외운 결과였고, 실데이터에
적용하면 재현되지 않았을 것이다. 졸업과제의 핵심 주장이 통째로 틀렸을 사안이다.

### 일반화

> split 축(record)과 **변이 축(morphology)이 일치하지 않으면** record split 은
> leakage 를 막지 못한다. MIT-BIH 에서는 기록마다 실제로 다른 환자이므로
> 이 문제가 없다 — **합성 데이터 고유의 함정**이다.

## F-7. SNR sweep 은 잡음 실현을 1회만 뽑고 스케일만 바꿔야 한다

| | |
|---|---|
| 상태 | 확정 (**설계 단계에서 선제 반영** — 사고가 나기 전에 막았다) |
| 영향 | EXP-A 의 전제 |

### 발단

이 항목은 다른 F 와 성격이 다르다. **실제로 겪은 것이 아니라 EXP-A 를 설계하다
발견한 함정**이다. `build_eval_set` 을 쓰면서 "SNR 마다 새 잡음을 뽑으면
어떻게 되는가" 를 따져보다 나왔다.

### 왜 문제인가

SNR 마다 다른 잡음 실현을 뽑으면, 성능–입력SNR 곡선의 변화가
**(a) SNR 이 낮아져서**인지 **(b) 우연히 더 어려운 잡음이 뽑혀서**인지
분리할 수 없다. 곡선의 기울기가 방법의 특성이 아니라 표집 잡음이 된다.

### 결정적 측정

이 항목은 사고 전에 막은 것이라 '틀린 값' 이 없다 `[커밋]`. 대신 규약이 지켜지는지를
**코드로 고정**했다 — `build_eval_set` 이 `(record, seg, cond)` 마다 잡음을
한 번만 뽑고 SNR 루프는 그 안에서 돈다는 구조 자체가 검증이다.

```python
g = make_rng(seed, name, si, cond)      # SNR 이 아니라 조건까지만 salt 에 넣는다
nz, w = mixed_noise(n_seg, rec.fs, g)   # 잡음은 여기서 1회
for snr in snr_grid:                    # SNR 은 스케일만 바꾼다
    y, _, _ = mix_at_snr(x_raw, nz, float(snr))
```

### 조치

잡음 실현은 `(record, seg, cond)` 마다 **한 번만** 뽑고 SNR 로 **스케일만**
바꾼다. `dataset.py:build_eval_set` 에 규약으로 못박고 주석에 이유를 남겼다.

### 놓쳤다면

EXP-A 곡선의 교차점(`M04` 와 `M08` 이 10 dB 부근에서 뒤집히는 지점)이
실재하는지 표집 잡음인지 판단할 수 없었을 것이다. **RQ1 의 답이 곡선의
교차에 걸려 있으므로** 곡선을 못 믿으면 RQ1 을 못 쓴다.

### 일반화

> sweep 실험에서 **바꾸려는 변수 하나만 바꾸고 나머지는 고정**한다.
> 당연해 보이지만 잡음처럼 '매번 새로 뽑는 것이 자연스러운' 대상에서
> 놓치기 쉽다.

## F-6. Sameni 구현 버그 2건 — "방법이 안 된다" 가 아니라 "구현이 틀렸다"

| | |
|---|---|
| 상태 | **확정** |
| 발견 | 외부 검토 A-2 지적을 자가진단으로 검증하다가 |
| 영향 | `M05` 성능 +5.9 → **+16.2 dB** (입력 5 dB) |

### 발단

초기 관찰에서 Sameni EKF/EKS 가 기대보다 훨씬 못했다.

### 먼저 의심한 것

**"이 방법이 우리 조건(fs 250 Hz, 이 잡음 조성)에 안 맞는다"** 가 첫 가설이었다.
모델 기반 방법은 가정이 어긋나면 급격히 나빠지므로 그럴듯했다. 여기서 멈췄다면
`M05` 를 약한 상태로 둔 채 비교표를 만들었을 것이다.

그러나 외부 검토자의 지적
**"약한 상태의 방법을 다른 방법과 비교하면 그 비교는 무효"**(A-2)가 있었기 때문에
**자가진단 절차를 먼저 만들었다.** 7개 검사(C1~C6 + DoD)로 각 구성요소를
따로 점검하는 방식이다.

### 결정적 측정

자가진단이 두 곳을 짚었다.

| 버그 | 내용 |
|---|---|
| (a) | phase-averaged template 의 **상수 오프셋**. 상태방정식은 `dz/dθ` 만 규정하므로 오프셋은 동역학과 무관한데, 방치하면 적합 R² 가 0.99 → 0.82 로 떨어지고 그 잔차가 `q_z` 과대추정으로 전파된다 |
| (b) `[측정]` | **`q_z` 를 누적 분산으로 잘못 계산.** `q_z` 는 매 샘플의 상태잡음 분산인데, 관측되는 모델 잔차는 beat 한 개 길이 `L` 동안 누적된 편차다. random walk 의 누적 분산은 `L·q_z` 이므로 `L` 로 나눠야 한다. 이 정규화를 빼면 `q_z` 가 수백 배 과대추정되어 필터가 사실상 평활화를 하지 않는다 |

### 놓쳤다면

**"Sameni 는 우리 조건에 맞지 않는다" 는 틀린 결론**을 냈을 것이다.
비교 대상 하나를 약한 상태로 둔 채 "딥러닝이 낫다" 고 쓰는 것과 같다.

### 일반화

> 어떤 방법이 기대보다 못하면 **방법을 탓하기 전에 구현을 검증하는 절차**를
> 먼저 만든다. baseline 을 약하게 두면 그 위의 모든 비교가 무효다.

## F-5. SWT 의 σ 를 level 별 MAD 로 추정하면 안 된다 — 내 초기 권고를 정정

| | |
|---|---|
| 상태 | **확정** (초판 권고 철회) |
| 영향 | `M04` 성능. 검증 세트 **−3.5 → +11.4 dB** |

### 발단

`00_review.md` B-1 에서 내가 "σ 를 level 별 MAD 로 추정하라" 고 권고했다.
구현 후 성능이 나오지 않아 대역별로 실측했다.

### 먼저 의심한 것

**기록 없음** — 판단 순서가 남아 있지 않다.

확실한 것은 **결론을 낼 때 자기가 쓴 설계 문서를 반증했다**는 점이다.
`00_review.md` B-1 은 이 프로젝트의 초기 검토에서 **내가 직접 쓴 권고**였고,
그것을 실측으로 뒤집었다 `[대화]`. 세션 보고에 그렇게 적혀 있다:
*"제 권고 중 하나는 실측으로 틀린 것이 확인되어 정정했습니다."*

### 배경 — SWT thresholding 과 σ 추정

정지 웨이블릿 변환(SWT)은 신호를 주파수 대역별 **세부계수** `D1..D5` 와 최저주파
**근사계수** `A5` 로 나눈다. `D1` 이 가장 높은 주파수다. 잡음 제거는
세부계수에 threshold 를 걸어 작은 계수를 죽이는 방식으로 한다.

threshold 는 보통 `k · σ` 로 정한다. `σ` 는 **잡음의 표준편차**이고 `k` 는 배수다.
그런데 σ 를 모르므로 계수로부터 추정해야 한다. 표준 방법은
**MAD**(median absolute deviation)를 쓰는 것이다:

$$\hat\sigma_j = \frac{\operatorname{median}(\lvert D_j\rvert)}{0.6745}$$

`0.6745` 는 정규분포에서 MAD 를 표준편차로 환산하는 상수다.

**핵심 가정**: 이 추정이 맞으려면 그 레벨의 계수가 **거의 잡음이어야** 한다.
신호 성분이 섞여 있으면 σ 가 부풀려진다.

### 결정적 측정

`fs = 250 Hz`, 입력 10 dB(AWGN):

| Band | 대역 | band SNR | `MAD(D_j) / 참 σ` |
|---|---|---|---|
| D1 | 62.5–125 Hz | −13.2 dB | 1.00 |
| D2 | 31–62.5 | +0.5 dB | 1.05 |
| D3 | 15.6–31 | +12.3 dB | 1.23 |
| D4 | 7.8–15.6 | +17.5 dB | **2.01** |
| D5 | 3.9–7.8 | +18.5 dB | **4.98** |

표의 `band SNR` 은 그 레벨의 계수에서 신호가 잡음보다 얼마나 센가를 뜻한다.
양수면 신호가 지배한다.

**D3 이상은 ECG 가 계수를 지배한다**(band SNR +12 ~ +18 dB). 그 대역의 MAD 는
잡음이 아니라 **ECG 자체**를 재게 되고, 그래서 σ 를 2~5배 과대추정한다.
threshold `k·σ` 도 함께 커지므로 **QRS 의 계수까지 잘라낸다.**

반대로 `D1`/`D2` 는 band SNR 이 −13 ~ +0.5 dB 로 잡음이 지배하므로 MAD 가
참 σ 와 거의 같다(비율 1.00~1.05). **거기서 추정한 σ 를 전 레벨에 공통으로
쓰는 것**(전역 σ)이 옳은 선택이었다.

검증 세트 `snr_imp_scaled`: **전역 σ(D2) +11.4 dB vs level별 σ −3.5 dB.**

### 놓쳤다면

`M04` 가 **−3.5 dB**(무처리보다 나쁨)인 채로 표에 실렸을 것이고,
"wavelet thresholding 은 이 과제에 쓸모없다" 는 결론이 났을 것이다.
실제로는 튜닝 후 **+11.4 dB** 로 고전 기법 중 최고다.

### 조치

`00_review.md` B-1 에 **정정 표시와 근거를 남겼다** (지우지 않았다).

### 일반화

> 설계 문서의 권고도 측정으로 검증해야 한다. 그리고 틀렸을 때는
> **지우지 말고 정정 표시**를 남긴다 — 무엇이 왜 바뀌었는지가 결과다.

## F-4. `filtfilt` 기본 padlen 으로는 front-end 자체가 11.9 dB 왜곡

| | |
|---|---|
| 상태 | **확정** |
| 발견 | **EXP-C(왜곡 하한)가 잡아낸 첫 실제 버그** |
| 영향 | 평가 guard band 5 s 를 전 방법 공통 규약으로 확정 |

### 발단

EXP-C 는 "잡음 없이 clean 을 통과시키면 얼마나 망가지는가" 를 잰다.
front-end **단독**으로 11.9 dB 왜곡이 나왔다. 아무 잡음도 없는데 그 정도가
망가진다는 것은 설명이 안 됐다.

### 먼저 의심한 것

**기록 없음** — 당시 판단 순서가 남아 있지 않다.

세션에 남은 서술은 이것이다: *"`filtfilt` 기본 padlen이 0.5 Hz HPF에는 턱없이
짧아 경계 트랜지언트가 생겼습니다 — 이것 자체가 **EXP-C(distortion floor)가
잡아낸 첫 실제 버그**입니다."* `[대화]`

즉 **발견 경로가 EXP-C** 였다는 것은 확실하다. 같은 실행에서 `M00`(identity)은
정상값(∞)이 나왔으므로 측정 자체는 건전했고 front-end 만 낮았다 `[측정]`.

원인은 경계였다. 0.5 Hz HPF 는 수 초간 링잉하는데 scipy 의 기본 `padlen` 은
**15 샘플(60 ms)** 이다.

### 조치와 측정

`filtfilt` 는 **zero-phase 필터링**을 위해 신호를 앞뒤로 두 번 통과시킨다.
그때 경계에서 생기는 트랜지언트를 줄이려고 신호 양끝을 반사해 붙이는데,
그 길이가 `padlen` 이다. scipy 기본값은 필터 차수에 비례한 작은 값이라
**0.5 Hz 같은 아주 낮은 컷오프에는 턱없이 짧다** — 그 필터의 임펄스 응답은
수 초에 걸쳐 있기 때문이다.

`padlen` 을 명시하고, 그와 **별개로** 평가 구간 양끝을 잘라내는
**guard band** 를 두기로 했다. 필터·칼만·OLA 모두 경계에서 불안정하므로,
아예 평가에서 제외하는 것이 안전하다. 얼마를 자를지는 실측으로 정했다:

| guard | front-end 왜곡 하한 |
|---|---|
| 0 s | 11.5 dB |
| 3 s | 40.9 dB |
| **5 s** | **41.9 dB** (포화) |

### 놓쳤다면

**모든 방법이 11.9 dB 의 공통 왜곡을 안고** 측정됐을 것이다. 그 왜곡은 모든
행에 똑같이 실리므로 순위는 유지되지만, "이 방법이 신호를 얼마나 보존하는가"
라는 EXP-C 의 질문 자체가 무의미해진다. 그리고 그 사실을 알아챌 단서가 없다.

### 일반화

> **"기법을 만들기 전에 평가를 먼저 만든다"** 는 원칙의 첫 배당금이었다.
> EXP-C 가 없었다면 이 왜곡은 모든 방법의 성능에 섞여 들어가 보이지 않았을 것이다.

## F-3. 250 Hz 에서 1 샘플(4 ms) 정렬 오차가 SNR 추정을 6 dB 왜곡

| | |
|---|---|
| 상태 | **확정** |
| 발견 | ground-truth 없는 SNR 추정기를 교정하다가 |

### 발단

참값 20 dB 를 아는 신호에 beat-averaged 추정기를 적용했는데 **14 dB** 가 나왔다.
6 dB 는 너무 큰 오차라 추정기 자체를 의심했다.

### 먼저 의심한 것

**기록 없음** — 당시 판단 순서가 남아 있지 않다.

세션에 남은 것은 결론뿐이다: *"1샘플(4 ms) 정렬 오차가 원인입니다.
업샘플 기반 sub-sample 정렬로 다시 구현하겠습니다."* `[대화]`

### 결정적 측정

정렬 방식만 바꿔 같은 신호를 다시 쟀다.

| 정렬 | 추정 SNR (참값 20 dB) |
|---|---|
| 정수 샘플 | 14 dB |
| **4배 업샘플 + 교차상관** | **20.5 dB** |

QRS 는 σ 가 10 ms 수준이라 **1 샘플(4 ms)만 어긋나도** beat 잔차가 부풀어 오른다.

### 놓쳤다면

실측 장비의 SNR 을 **6 dB 낮게** 추정했을 것이다. 그러면 "우리 장비는 15 dB
조건" 이 아니라 "9 dB 조건" 이 되고, EXP-A 곡선에서 최적 기법이 달라진다.

### 조치

4배 업샘플 후 template 교차상관 정렬을 **필수 단계**로 넣었다.
20 dB → 14 dB 였던 것이 **20.5 dB** 로.

## F-2. PVC 커널의 위상 평균이 정상 beat 와 달라 beat 마다 DC 계단 발생

| | |
|---|---|
| 상태 | **확정** |
| 발견 | front-end 왜곡 하한이 40 dB → 13 dB 로 붕괴 |

### 발단

PVC 를 합성에 섞기 시작하자 front-end 왜곡 하한이 **40 dB → 13 dB** 로 무너졌다.
PVC 를 넣기 전에는 정상이었으므로 원인이 PVC 쪽이라는 것은 분명했다.

### 먼저 의심한 것

**PVC 커널의 파형 자체**(진폭이 크고 폭이 넓다)가 필터를 힘들게 하는 것으로
생각했다. 그런데 파형을 그려보니 문제는 파형이 아니라 **beat 경계**에 있었다 —
정상 beat 와 PVC 사이에서 신호가 계단처럼 튀었다.

### 결정적 측정

커널별 위상 평균을 직접 쟀다 `[커밋]`. 정상 beat 와 PVC 커널의 평균이 서로 달랐고,
그 차이가 beat 경계의 계단 높이와 일치했다. 커널을 zero-phase-mean 으로
정규화하자 왜곡 하한이 **13 dB → 40 dB** 로 복구됐다.

원인은 커널마다 **위상 평균이 달라** beat 경계에서 DC 계단이 생긴 것이다.
0.5 Hz HPF 에 계단 입력은 최악의 입력이다.

### 놓쳤다면

부정맥을 포함한 모든 평가(특히 EXP-E 의 PVC 보존 측정)가 **27 dB 낮은
왜곡 바닥** 위에서 이뤄졌을 것이다. 방법 간 차이가 그 바닥에 묻힌다.

### 조치

모든 beat 종류가 같은 등전위선을 공유하도록 커널을 **zero-phase-mean 으로
정규화**했다.

## F-1. `motion_synth` 가 드물게 전(全) 0 잡음을 생성

| | |
|---|---|
| 상태 | **확정** |
| 발견 | 학습이 매번 에폭 6 부근에서 죽어서 |

### 발단

학습이 **매번 비슷한 지점(에폭 6 부근)에서 죽었다.** 매번 같은 곳이라는 것이
단서였다 — 무작위 실패였다면 지점이 흩어졌을 것이다.

### 먼저 의심한 것

**기록 없음** — 당시 세션에 판단 순서가 남아 있지 않다.

다만 남아 있는 증거로부터 다음은 말할 수 있다. 에러 메시지가
`ValueError: noise has zero power` 로 **데이터 쪽을 직접 가리켰고** `[로그]`,
학습이 **매번 비슷한 지점(에폭 6 부근)** 에서 죽었다 `[로그]`. 후자가 중요한
단서인 이유는, 학습 불안정(발산·LR 과다)이라면 죽는 지점이 흩어져야 하는데
일정하다는 것은 **"누적해서 일정 수의 window 를 보면 반드시 한 번은 걸린다"**
는 뜻이고, 그것은 낮은 확률의 **결정론적** 버그를 시사하기 때문이다. `[재구성]`

### 결정적 측정

`motion_synth` 를 대량 시행해 전(全) 0 출력의 빈도를 쟀다. 약 **1/2600 window**.
이벤트가 창 끝에 놓이면 상승항이 0 이라 기여가 전혀 없다.

### 놓쳤다면

**딥러닝 학습을 완주할 수 없었다.** 매번 에폭 6 에서 죽으므로 `M06`/`M07`/`M08`
결과 자체가 존재하지 않았을 것이고, "DSP vs DL 비교" 라는 과제의 절반이 사라진다.

### 조치

`lead` 마진과 폴백을 넣고, 회귀 테스트를 **400 → 8000 시행**으로 강화했다.

**왜 8000 인가.** 발생 확률이 약 1/2600 이므로, 400 시행에서 한 번이라도
걸릴 확률은 `1 − (1−1/2600)^400 ≈ 14 %` 다. 즉 **버그가 그대로 있어도 86 %
확률로 테스트가 통과**한다. 8000 시행이면 `1 − (1−1/2600)^8000 ≈ 95 %` 로
올라간다.

### 일반화

> 확률적 버그의 회귀 테스트는 **발생 확률의 역수보다 충분히 많은 시행**이
> 필요하다. 시행 수를 근거 없이 정하면 테스트가 통과해도 의미가 없다.

## F-26. R-4 의 CPU 열이 **첫 호출 한 번**을 잰 값이었다 — 같은 문서 안에서 9 배 어긋났다

### 그 표의 "CPU %" 가 무슨 뜻인가 — 이것부터 정의하지 않아 혼란이 있었다

스트리밍은 **`hop` 샘플마다 한 번씩** 모델을 돌린다. `fs = 250`, `hop = 12` 면
**신호 1 초마다 20.8 번**이다. 한 번 도는 데 `cost` 초가 걸린다면

    CPU 분율 = (초당 호출 횟수) × (1 회 비용) = 20.8 × cost

이 값이 **신호 1 초를 따라가려고 CPU 를 몇 초 쓰는가**다. 그래서

| 값 | 뜻 |
|---|---|
| 0.30 (30 %) | 1 초짜리 신호를 0.3 초에 처리한다 — **여유 3 배** |
| 1.00 (100 %) | 딱 맞는다. 조금만 흔들려도 밀린다 |
| **1.88 (188 %)** | **1 초를 따라가는 데 1.88 초가 든다 — 영원히 밀린다** |

즉 188 % 는 "느리다" 가 아니라 **"실시간이 불가능하다"** 는 말이다.

### 발단

R-5(시리얼 브리지)를 만들고 정상 상태 처리량을 재니 **`M06` 을 포함해 방법
넷을 돌려도 벽시계 RTF 가 0.44** 였다 `[측정]`. 그런데 2.4 의 표는 `M06`
**하나**를 **188 %** 로 적고 있었다. 하나가 못 따라간다는데 넷이 여유 있게
돈다 — **둘 다 맞을 수는 없다.**

### 먼저 의심한 것

**(a) 컨테이너가 더 빠른가.** 방향이 반대다. 4 vCPU 컨테이너가 "데스크탑"
보다 빠를 이유가 없다.

**(b) 스레드 수.** 브리지는 torch 기본값(코어 4 개)을 쓰고 2.4 는 1 thread
였다면 최대 4 배까지 설명된다. 그래서 브리지의 **CPU 시간**(모든 스레드 합)을
따로 쟀다 — `M06` 하나가 **0.63 코어**였다 `[측정]`. 스레드를 다 합쳐도
1.88 코어가 안 된다. **설명이 안 된다.**

### 결정적 측정

같은 체크포인트를 **같은 프로세스에서 연속으로** 호출했다 `[측정]`:

| 1024 window 1 회 | 시간 | 그것으로 계산한 CPU 분율 |
|---|---|---|
| **첫 호출** | **50.6 ms** | 20.8 × 50.6 ms = **105 %** |
| 이후 중앙값 | **14.4 ms** | 20.8 × 14.4 ms = **30 %** |

**같은 모델, 같은 입력, 같은 프로세스인데 첫 번째만 3.5 배 느리다.**
PyTorch 의 첫 호출에는 계산이 아닌 것들이 들어간다 — 메모리 할당자가 풀을
잡고, 스레드풀이 뜨고, 어떤 컨볼루션 커널을 쓸지 고른다. 두 번째부터는
그것이 다 준비돼 있다.

그리고 2.4 를 만든 코드가 이랬다 `[코드]`:

```python
t0 = time.perf_counter()
_ = meth_nofe(segs[0][0][:1024], FS, {})   # 1 회 비용 (win 하나)
cost = time.perf_counter() - t0
```

**첫 호출 한 번**을 재서 `cost` 로 삼았다. 그리고 그것에 20.8 을 곱했다.
**곱셈이 오차도 함께 곱한다.**

### 왜 여섯 칸 중 한 칸만 크게 틀렸나 — 이것이 이 기록의 요점이다

`cost` 는 **(축 × 방법) 조합마다 한 번**, 총 여섯 번 쟀다. 여섯 번 모두
"그 모델 객체의 첫 호출" 이다. 고친 뒤와 비교하면:

| 96 ms (d=hop=12) | 전 | 후 | 배수 |
|---|---|---|---|
| d0 `M06` | 34 % | 28 % | 1.2 |
| d0 `M06L6` | 30 % | 32 % | 0.9 |
| d0 `M04` | 12 % | 9 % | 1.3 |
| **d1 `M06`** | **188 %** | **29 %** | **6.5** |
| d1 `M06L6` | 31 % | 32 % | 1.0 |
| d1 `M04` | 17 % | 8 % | 2.1 |

**"첫 호출은 늘 3.5 배 느리다" 로는 이 표가 설명되지 않는다.** 대부분은 거의
안 틀렸고 한 칸만 6.5 배 틀렸다. 즉 첫 호출 오버헤드는 **크기가 들쭉날쭉하다** —
그 순간 프로세스가 무엇을 하고 있었는지, 메모리가 얼마나 조각나 있었는지,
OS 가 언제 스케줄했는지에 달린다. d1 `M06` 은 MIT-BIH 기록을 적재한 **직후**의
첫 DL 호출이라 그 자리에 걸렸을 것으로 보이지만 `[추론]`, **어느 칸이 걸릴지는
사전에 알 수 없다.**

> **그래서 한 번 재는 것이 나쁜 추정량이다.** 대개는 그럴듯한 값이 나오고
> **가끔 6.5 배가 나온다.** 표를 훑어서는 어느 칸이 그 칸인지 알 수 없다 —
> 188 % 가 눈에 띈 것은 값이 100 을 넘어 **물리적으로 이상해 보였기** 때문이지,
> 대조해서 잡은 것이 아니다. 34 % 가 28 % 여야 했다는 것은 아무도 못 봤다.

### 그리고 맞는 값이 이미 같은 저장소에 있었다

보고서 5.10.5 는 `M06` 의 추론을 **1 thread 10.0 ms** 로 쟀다. `hop = 12` 면
20.8 × 10.0 ms = **21 %** 다. 30_realtime_demo 5 절도 그렇게 적어 뒀다.

**한 문서 안에 21 % 와 188 % 가 같이 있었고, 9 배 어긋났는데 아무도 대조하지
않았다.** 두 값은 서로 다른 절에 있었고, 각각은 그 자리에서 그럴듯했다.

### 놓쳤다면

**"노트북 한 대로는 딥러닝을 실시간으로 못 돌린다" 가 결론으로 남았을
것이다.** 실제로 그 표는 5 절에서 "남은 실질 위험" 을 좁히는 근거로 쓰였고,
모드 A 에 어떤 방법을 띄울 것인가가 그 숫자에 달려 있었다. 지금 브리지는
**고전 셋 + 딥러닝 둘을 1.6 코어**로 돌린다.

### 조치

`per_window_cost()` — **예열 3 회 뒤 7 회의 중앙값**을 쓴다. 평균이 아니라
중앙값인 이유는 다른 프로세스에 CPU 를 뺏긴 한 번이 평균을 끌어올리기
때문이다. 브리지 쪽은 **벽시계와 CPU 시간을 따로** 보고한다 — torch 가 코어를
여러 개 쓰므로 벽시계 RTF 0.44 가 CPU 0.87 코어일 수 있고, **노트북 한 대로
되는가는 CPU 쪽**이 정한다.

### 재현이 결함의 크기를 정확히 가둬 줬다 `[측정]`

다시 돌린 **24 행에서 dB 두 열(배관·파이프라인)이 전부 비트 단위로 같았다.**
이것이 중요한 이유는, 그렇지 않았다면 "측정을 다시 했더니 값이 달라졌다" 가
되어 **어느 부분이 틀렸는지 가릴 수 없었기** 때문이다. 두 열이 그대로라는 것은
**입력도 처리도 그대로였다**는 뜻이고, 따라서 **틀린 것은 CPU 열 하나**로
확정된다. 결함의 범위가 숫자로 닫혔다.

### 일반화

> **한 번 잰 값을 처리량으로 곱하지 않는다** — 곱셈은 오차도 함께 곱한다.
> 그리고 **같은 양이 문서 두 곳에 다른 값으로 있으면 둘 다 의심한다.**
> 이번에는 옆 절에 맞는 값이 이미 있었다.

## F-35. 채점 기준이 **후보 한 계열의 극한**이었다 — 참조를 바꾸니 순위가 뒤집혔다

### 발단

세 실시간 front-end 를 `total_db` 로 갈랐고 블록 영위상이 이겼다(F-33). 그런데
사용자가 화면을 보고 셋을 짚었다 `[대화]`.

1. «S 골 오차 4 %R» 이 S 골 깊이(10~14 %R)의 3 분의 1 인데 그림에는 안 보인다.
2. 영위상 출력의 T-P 가 회색선 아래인 것이 남은 변동인가 직류인가.
3. **참조가 `FE_off(clean)` = 오프라인 영위상이면, 블록 영위상은 같은 계열이라
   당연히 가깝다. 「더 낫다」가 아니라 「더 닮았다」를 재는 것 아닌가.**

### 먼저 의심한 것

1 번은 «지표는 맞고 그림이 작아서 안 보이는 것» 이라고 생각했다. **틀렸다.**

`s_depth` 는 «그 박동의 T-P 중앙값 − R+80 ms 최저점» 이라 **정의에 기준 준위가
끼어 있다.** 기준선이 필요 없는 `R−S 봉우리차`(R 꼭대기 − S 골, 두 점의 차)로
재면 `[측정]`:

| | R−S 봉우리차 [%R] | T-P 기준 S 깊이 [%R] |
|---|---|---|
| 오프라인 영위상 | 112.2 | 13.97 |
| 인과 o1 0.5 Hz | 113.0 | 19.63 |
| 블록 영위상 0.5 s | 112.6 | 13.98 |
| 중앙값 200+600 ms | 112.6 | **9.26** |

**S 골 자체는 아무도 안 깎는다**(폭 0.8 %R). 10 %R 벌어지는 것은 **QRS 옆의
기준 준위**다. 즉 지표 이름이 「S 골 오차」인 것이 잘못이었고, 재던 것은
**ST 구간의 이동**이다. **F-30 과 같은 계열** — 지표가 이름과 다른 것을 쟀다.

2 번도 절반 틀렸다. D1(기록 100)에서는 **영위상이 회색선 아래에 있지 않다**
(직류 +0.05 %R). 아래 있는 것은 입력(−27.8 %R, 기록 자신의 오프셋)이다.
D0 에서만 영위상이 −8.6 %R 인데, 원인은 D0 의 T 파가 43 %R 로 커서 «기록 전체
평균» 이 T-P 보다 위에 있기 때문이다 — **정보 없는 직류**다.

### 결정적 측정 — **참값이 있는 축에서 다시 잰다** `[측정]`

3 번은 잴 수 있다. 합성축에는 참값이 있다(D1 의 «clean» 은 자기 기저선 변동을
갖고 있어 참값이 못 된다). 세 방식이 **공유하는** 40 Hz 저역통과만 건 원본을
참값으로 삼았다 — 공통 부분은 아무에게도 안 물린다. 합성축 test 8 기록,
기저선 변동 50 %R 주입:

| | 참값 기준 [dB] | `FE_off` 기준 [dB] | ST 준위 오차 [%R] | 준위 산포 [%R] |
|---|---|---|---|---|
| 인과 o1 0.5 Hz | −22.67 | −23.80 | +0.87 | 21.56 |
| 블록 영위상 0.5 s | −29.78 | **−34.98** | **−0.20** | 11.18 |
| 중앙값 200+600 ms | **−30.56** | −28.93 | −2.20 | **4.58** |

**순위가 뒤집힌다.** `FE_off` 기준으로는 블록이 6.05 dB 우세하고 **8 기록 전부**
블록 승인데, 참값 기준으로는 중앙값이 0.78 dB 우세하고 8 중 4 에서 중앙값이
이긴다.

`total_db` 가 잰 것의 상당 부분은 «어느 쪽이 나은가» 가 아니라 **«어느 쪽이
오프라인 filtfilt 를 더 닮았는가»** 였다. 블록 영위상은 미리보기를 늘리면 그
참조로 **수렴하도록 정의된 방식**이므로, 유리한 것이 구조적으로 당연하다.

### 그럼 무엇으로 고르나 — ST 를 심어 본다 `[측정]`

준위 산포와 ST 준위 오차가 **반대 방향**을 가리킨다. 「평평할수록 좋다」로는
못 고른다 — D0 원본에서 **인과 방식의 산포가 오프라인보다 작다**(0.90 대 2.60).
가장 왜곡이 큰 방식이 평평함 1 위가 되는 것이다.

그래서 임상에서 실제로 읽는 양으로 갈랐다. **ST 편위는 그 박동 자신의 기준선에
대해 읽는다.** 합성축 8 기록에 **알고 있는 크기의 ST 상승 10 %R** 을 심었다:

| | 보존율 [%] |
|---|---|
| 오프라인 영위상 | 99.9 ± 0.4 |
| 인과 o1 0.5 Hz | 102.9 ± 3.4 |
| **블록 영위상 0.5 s** | **101.1 ± 2.1** |
| **중앙값 200+600 ms** | **84.1 ± 14.9** |

중앙값은 심은 것의 84 % 만 전달하고 **기록마다 ±15 % 로 들쭉날쭉하다.**
기제는 하나다 — 200 ms 창이 QRS 직후에 놓이면 창 안이 S·ST 로 눌려 있어
기저선 추정이 그쪽으로 끌린다. **평평해 보이는 이유와 ST 를 못 지키는 이유가
같은 것이다.**

### 놓쳤다면

**「숫자로 블록 영위상이 이겼다」로 D-20 을 확정했을 것이다.** 그 숫자는
진짜지만, 재던 것이 «오프라인 filtfilt 와의 닮음» 이었다. 그리고 사용자가
화면에서 본 «중앙값이 회색선에 붙는다» 는 관찰은 **옳았는데** 표가 그것을
반박하는 것처럼 보였다 — 표가 그 축을 안 재고 있었기 때문이다.

동시에, 감사가 없었다면 **중앙값 쪽으로 뒤집는 것도 성급했을 것이다.**
평평함만 보면 중앙값이 이기지만 ST 를 16 % 잃는다. **둘 다 재야 고를 수 있다.**

> **재사용할 것.** F-33 은 «참조가 후보와 **함께 움직인다**» 였고, 그것을
> 고정해서 `total_db` 를 만들었다. **고정하는 것만으로는 부족했다** — 고정한
> 그 참조가 **후보 한 계열의 극한**이었기 때문이다. 참조는 고정돼야 할 뿐
> 아니라 **후보 밖에 있어야** 한다.
>
> 그리고 **지표 이름은 주석이 아니라 인터페이스다.** 「S 골 오차」라고 부르는
> 동안 그것이 ST 이동이라는 것을 아무도 못 봤고, 그림과 표가 모순돼 보이는
> 이유도 못 찾았다. 이름을 고치자 «파형 미용» 이던 문제가 «ST 충실도» 라는
> **고를 값이 있는 축**이 됐다.

## F-34. FE 를 빼고 학습시켰더니 **졌다 — 내가 든 이유는 아니었다** `[측정]`

### 발단

「실시간에서 낼 수 있는 최선」을 물으려면 딥러닝에서 front-end 를 빼고
학습시켜 보는 것이 정당하다(docs/15 §7 목적 B). 그렇게 했다 —
`m06_l1_nofe`: 입력만 날것으로 주고 **목표는 `FE_off(clean)` 그대로** 뒀다.
목표까지 날것으로 두면 D1 의 참조가 「MIT-BIH 원본」이 되어 **F-12 를
재현**하므로 참조는 건드리지 않았다.

### 먼저 걸린 덫 — 학습 로그가 반대를 말한다

| | val `snr_imp` |
|---|---|
| FE 판 | +3.44 dB (ep 34) |
| **FE 없는 판** | **+9.56 dB** (ep 49) |

2.8 배 좋아 보인다. **그런데 분모가 다르다.** `snr_imp` 는 「그 학습이
받은 입력」 대비 개선인데, FE 판의 입력은 이미 기저선 변동이 빠진 것이고
nofe 판의 입력은 날것이라 **변동 제거분까지 자기 공로**가 된다. F-10 이
정확히 이 덫이었다 — 그때는 이것을 못 보고 표를 만들었다.

### 같은 분모로 재면 뒤집힌다

평가 세트가 이미 공정하다: 입력 `y = 원본+잡음`, 참조 `x = FE_off(clean)`,
FE 는 **방법 안쪽**. 22 기록 x 2 구간 x 6 동작점 (`results/d1/exp_nofe`):

| 입력 SNR | −5 | 0 | 5 | 10 | 15 | 20 |
|---|---|---|---|---|---|---|
| M06 (FE 판) | +18.97 | +16.74 | +14.33 | +12.61 | +11.83 | +11.72 |
| M06n (FE 없는 판) | +17.46 | +15.07 | +12.34 | +10.07 | +8.64 | +7.93 |
| 격차 | +1.5 | +1.7 | +2.0 | +2.5 | +3.2 | **+3.8** |

**모든 동작점에서 FE 판이 이긴다.** 그리고 격차가 **입력이 깨끗할수록
벌어진다** — 잡음을 못 지워서가 아니라 **체계적인 차**라는 신호다.

### 먼저 의심한 것

docs/15 §7 에 `[미측정]` 으로 이렇게 적어 뒀었다: *창 1024 표본 = 4.096 s
인데 기저선 변동은 주기 2~20 s 라, 절대 준위는 **원리적으로 관측 불가**다.*

재 보니 아니었다. T-P 준위 산포 [%R, 중앙값]: 입력 31.5 -> **nofe 판 3.6**,
FE 판 4.3, 참조 자신이 4.0. **nofe 판이 오히려 더 평평하다.** 창마다 자기
DC 를 빼고 겹침-합으로 이으면 결과적으로 평활 대역이 0 에 붙는다.

### 결정적 측정 — **용량이 나뉜다** `[측정]`

오차 `xhat − x` 의 파워를 대역별로 갈랐다 (`scripts/analyze_nofe.py`,
`results/d1/exp_nofe/mechanism.csv`). 이것이 원인을 가른 측정이다:

| | 오차 파워 [%R²] | <0.5 Hz | 0.5~40 Hz | 59~61 Hz | >61 Hz |
|---|---|---|---|---|---|
| M06 (FE 판) | 0.03 | 5 % | 75 % | 0.3 % | 5 % |
| M06n (FE 없는 판) | 0.07 | 4 % | 83 % | 0.5 % | 6 % |

오차 파워가 **2.2 배**(3.4 dB — 표의 격차와 맞는다)이고 초과분이 **신호
대역 안**에 있다. 기저선도 전원선도 아니다. 같은 97 만 파라미터로
**대역제한 + 노치 + 잡음 제거**를 한꺼번에 해야 하니 파형 재현이 나빠진다
(박동 상관 0.985 대 0.992, QRS 폭 오차 29.2 대 26.1 ms).

### 곁다리 — 지표가 «작다» 는 것과 눈에 «보인다» 는 것

전원선 잔여는 오차 에너지의 **0.5 %** 라 dB 를 거의 안 움직인다. 그런데
«PLI 있음» 판정(60 Hz 봉우리가 이웃 배경의 10 배 이상)에 걸리는 구간 비율은
**nofe 판 11~30 %**, FE 판 2.3 %, FE 만 걸어도 0 % 다. 22 기록 중 10 기록.

이것은 **평균으로도 중앙값으로도 안 보인다** — 평균은 소수의 큰 값에
끌려가고(최대 90), 중앙값은 그 소수를 통째로 숨긴다(약 2). 판정 비율로
봐야 보인다.

### 놓쳤다면

**FE 없는 판을 「+9.56 dB 대 +3.44 dB」로 보고 채택했을 것이다.** 학습 로그
두 줄만 보면 그렇게 읽히고, 그 숫자는 진짜다 — 다만 재는 대상이 다르다.
그러면 실시간 경로가 **모든 동작점에서 1.5~3.8 dB 나쁜 모델**로 바뀌고,
게다가 구간의 11~30 % 에 60 Hz 잔물결이 얹힌다. **표는 좋아지고 화면은
나빠지는** 조합이라, 실측 시연에서야 «왜 지저분하지» 로 발견됐을 것이다.

막은 것은 규약이다 — 「학습 로그로 비교하지 않는다, 평가 세트로 비교한다」.

> **재사용할 것.** 세 가지가 겹쳤다.
>
> 1. **학습 로그의 개선치는 학습 조건이 다르면 비교 불가다.** 분모를
>    맞추는 자리는 학습이 아니라 **평가 세트**다. 다행히 이 과제의 평가
>    세트는 처음부터 그렇게 설계돼 있었다 — 그래서 새 코드 없이 쟀다.
> 2. **가설이 틀려도 실험은 값을 낸다.** 「창이 짧아서」는 틀렸지만,
>    「용량이 나뉜다」는 더 일반적인 답이었다. 예측을 적어 두지 않았으면
>    무엇이 틀렸는지도 몰랐을 것이다.
> 3. **한 통계량만 보면 소수의 실패가 사라진다.** 평균·중앙값이 서로
>    반대 방향으로 속인다면, 답은 셋째 통계량(여기서는 임계 초과 비율)이다.

## F-33. 모드 비교를 `pipeline_db` 로 했다면 **가장 나쁜 front-end 를 골랐을 것이다**

### 발단

세 front-end 를 `verify_stream_processor.py` 로 재고 `pipeline_db`(그때까지
쓰던 열)를 보니 **d1 에서 인과 모드가 가장 좋았다** `[측정]`:

| d1 · 12:12 | `pipeline_db` |
|---|---|
| **인과 o1 0.5** | **+0.89** (`M06`) · +1.19 (`M06L6`) · +0.73 (`M04`) |
| 블록 영위상 0.5 s | −0.39 · +0.23 · −0.34 |
| 중앙값 200+600 | +0.76 · +0.99 · −0.12 |

그런데 `docs/13`·`docs/14` 의 파형 지표는 **정반대**를 말한다 — 인과 모드가
S 골을 5.7 %R 찌그러뜨리고 기저선을 20.8 %R 남긴다.

### 먼저 의심한 것

**dB 와 파형 지표가 다른 것을 재는 것**이라고 생각했다(그럴 수 있다). 그런데
`pipeline_db` 의 정의를 다시 보니 그게 아니었다:

```
pipeline_db = SNR(출력 vs FE_rt(clean))  −  SNR(오프라인 출력 vs clean)
                        ^^^^^^^^^^^^^ 참조가 **모드마다 다르다**
```

**참조가 후보와 함께 움직인다.** 인과 FE 의 참조 `FE_rt(clean)` 은 그 자신이
이미 찌그러진 목표이고, 방법이 그 찌그러짐을 충실히 재현하면 점수가 좋게 나온다.
**`docs/15` §3 에서 «참조를 후보 중 하나로 두면 순환이다» 라고 적어 둔 바로 그
형태를, 우리 산출물이 이미 갖고 있었다.**

### 결정적 측정

**고정된 오프라인 참조**로 재는 열(`total_db`)을 넣고 다시 쟀다 `[측정]`.
순위가 뒤집힌다:

| 12:12 · `total_db` | d1 `M06` | d1 `M06L6` | d1 `M04` | 6 칸 평균 |
|---|---|---|---|---|
| 인과 o1 0.5 | −6.06 | −5.69 | −5.46 | **−5.22** |
| **블록 영위상 0.5 s** | **−2.87** | **−3.44** | **−2.73** | **−3.08** |
| 중앙값 200+600 | −3.59 | −3.60 | −2.91 | −3.17 |

**인과 모드가 최고에서 최악으로 바뀐다** — d1 `M06` 에서 3.19 dB 차다.
그리고 `fe_share`(방법과 무관한 front-end 의 몫)가 그 이유를 그대로 말한다:
인과 13.9/14.2 dB, 블록 영위상 19.8/19.7, 중앙값 19.4/18.9 — **높을수록
오프라인 FE 에 가깝다.** 총손해의 지배항이 front-end 자신의 거리였다.

### 놓쳤다면

**세 모드 중 가장 나쁜 것을 골랐을 것이다.** 그것도 «dB 로 재봤다» 는 근거를
달고. 파형 지표(`docs/13`)와 dB 표가 정반대를 말하는 상태로 보고서에 실렸을
것이고, 둘 중 어느 쪽이 틀렸는지 판단할 방법이 표 안에 없었다.

### 일반화

> **후보와 함께 움직이는 참조로는 후보를 고를 수 없다.** `pipeline_db` 는
> «이 front-end 조건에서 방법이 얼마나 잘하나» 에는 옳은 열이다(그 안에서 FE 가
> 상쇄된다). **틀린 것은 그것으로 front-end 를 비교한 것**이다. 열 하나가 두
> 질문에 쓰이면 한쪽에서는 반드시 틀린다 — `docs/15` §5 의 분해(`fe_share` /
> `method_share` / `total`)를 넣은 이유가 이것이고, 이번엔 그 예측이 **실제로
> 순위를 뒤집는 것**으로 확인됐다.

## F-32. 이미 그려진 파형이 심박 주기로 들썩였다 — 스케일을 매 프레임 다시 잡았다

### 발단

사용자가 `live.html` 로 실측 모니터를 보다가 **"이미 출력된 파형이 주기적으로
흔들린다"** 고 했다 `[대화]`. 새로 들어오는 부분이 아니라 **과거 구간까지** 움직였다.

### 먼저 의심한 것

**데이터 쪽**을 의심했다 — 기저선 변동이나 정렬 오류로 값 자체가 바뀌는가.
그런데 값이 바뀌면 «흔들림» 이 파형 모양을 따라야 하는데, 관측된 것은
**화면 전체가 통째로** 위아래로 움직이는 것이었다. 그러면 값이 아니라
**축**이 움직이는 것이다.

### 결정적 측정 `[코드]`

`vscale()` 이 매 호출마다 보이는 구간 전체에서 중심 `m` 과 로버스트 폭 `s` 를
다시 계산했고, `frame()` 은 **매 프레임 버퍼에서 전부 다시 그린다.** 그러므로
`m`·`s` 가 조금만 달라져도 **이미 그려진 표본의 화면 좌표까지 전부 바뀐다.**

그리고 왜 **주기적**인가 — 20 s 창에 R 피크가 하나 들어오고 하나 나갈 때마다
`s`(평균 절대 편차)가 계단처럼 튄다. 그 사건의 간격이 곧 RR 이다.

### 조치

병원 모니터처럼 **이득을 단계로 고정**했다:

- 폭은 **1-2-5 사다리** 위에만 두고, 현재 값의 **+10 % / −45 %** 밖으로 나가야
  다시 잡는다
- 중심은 **폭의 1/4 격자**에 붙이고, 한 칸 안이면 안 움직인다
- 밴드 안에서는 **같은 객체를 그대로 반환**한다 — 1 픽셀도 안 움직인다

### 놓쳤다면

시연에서 **"신호가 불안정한가요" 를 들었을 것이다.** 실제로는 신호가 아니라
축이 움직인 것이고, 우리는 «자동 스케일이라 그렇다» 를 설명할 준비가 없었다.
그리고 이것은 **모든 방법에 똑같이 걸리므로 방법 비교로는 절대 안 보인다** —
화면을 오래 보는 사람만 발견한다.

### 일반화

> **매 프레임 전부 다시 그리는 화면에서 «자동 스케일» 은 과거를 바꾼다.**
> 그리기가 누적(append-only)이면 축이 변해도 과거는 그대로지만, 버퍼에서
> 재구성하면 축이 곧 과거다. 재구성형 화면의 스케일은 **양자화 + 히스테리시스**
> 가 기본이어야 한다.

## F-31. 실시간 브리지가 시간이 갈수록 느려졌다 — 정렬기 버퍼만 안 묶여 있었다

### 발단

사용자가 `--replay` 로 **10 분쯤** 돌려 보고 **"RTF 가 계속 올라가면서 처리
밀림 블록이 계속 늘어난다. 초반엔 아무 문제 없다"** 고 했다 `[대화]`.

### 먼저 의심한 것

**추론 비용**을 의심했다 — `M06` 이 21 회/s 라 CPU 가 빠듯하다고 생각했다.
그런데 그 가설은 «초반엔 멀쩡하다» 와 안 맞는다. **추론 비용은 시간이 가도
안 변한다.** 시간에 비례해 커지는 것이 어딘가 있어야 한다.

### 결정적 측정

`--diag` 를 넣어 30 초마다 버퍼 크기와 RSS 를 남겼다 `[측정]`:

| 신호 시간 | RTF | 큐드롭 | **정렬기 버퍼** | `raw` | RSS |
|---|---|---|---|---|---|
| 13.7 s | 0.32 | 454 | **13 784** | 3 581 | 673 MB |
| 43.8 s | 0.33 | 454 | **43 880** | 6 102 | 675 MB |
| 104.0 s | 0.32 | 454 | **104 072** | 6 138 | 678 MB |
| 164.2 s | 0.34 | 454 | **164 264** | 6 174 | 682 MB |
| 254.5 s | 0.33 | 454 | **254 552** | 3 702 | 687 MB |

**정렬기 버퍼가 신호 시간에 정확히 비례한다**(= 4 계열 × idx). `raw` 는
3.6 k~6.2 k 로 묶여 있다. 코드를 보면 이유가 한 줄이다 — `raw`·`rawok` 에는
트림이 있고(`if lo > 20 * FS`) **`Aligner.buf` 에는 없다.** `take()` 가
보낸 구간을 슬라이스해 주기만 하고 **버리지 않았다.**

왜 그것이 CPU 를 먹는가: **파이썬의 세대별 GC 는 추적 대상 컨테이너의 슬롯을
전부 훑는다.** 원소 수십만 개짜리 리스트가 넷 있으면 gen2 수집 한 번의 비용이
그 길이에 비례하고, 그 길이는 세션 시간에 비례한다. **초반엔 공짜고 시간이
갈수록 비싸진다** — 관측된 증상 그대로다. RSS 는 분당 약 3.6 MB 늘었다.

### 조치

`take()` 에서 보낸 만큼 `del self.buf[n][:k]` 하고 `origin[n]` 을 따라 올린다.
회귀 테스트 둘을 붙였다 — **버퍼가 묶여 있는지**, 그리고 **트림이 정렬 자체를
깨뜨리지 않는지**(늦게 시작하는 계열과의 공통 구간 계산이 유지되는지).

### 놓쳤다면

**시연 도중에 화면이 밀렸을 것이다.** 시연은 한 번에 수십 분 켜 두는 것이고,
우리 검증은 전부 **분 단위**였다 — R-3·R-4 의 측정도 40 초 구간이다.
**초 단위로 옳은 코드가 분 단위로 틀릴 수 있다는 것을 시험하는 장치가 없었다.**

### 일반화

> **«묶여 있는가» 는 버퍼마다 따로 확인해야 한다.** `raw` 를 묶을 때 같은
> 문제를 이미 알고 있었는데(주석에 «과거는 버린다 (메모리 상한)» 라고 적혀
> 있다) **바로 옆의 정렬기 버퍼는 그대로 뒀다.** 한 곳을 고칠 때 «같은 성질의
> 다른 곳» 을 세어 보는 습관이 없으면 이런 것이 남는다.
>
> 그리고 **오래 돌려 보는 시험이 따로 필요하다.** 짧은 검증은 이 계열의 버그를
> 구조적으로 못 잡는다.

## F-30. 새로 만든 평활도 지표가 **잡음을 재고 있었다** — 그림과 표가 반대를 말했다

### 발단

F-29 로 넣은 **(3) T-P 대역폭**(`tp_band`)으로 후보를 갈랐더니 d1 에서
중앙값 6.8 · 블록 영위상 7.2 %R 로 **거의 같았다.** 그래서 "합성에서는
중앙값이 훨씬 평평하지만 **실기록에서는 그 이점이 사라진다**" 고 적었다.

**사용자가 그 결론과 내가 같이 낸 그림이 모순된다고 지적했다** `[대화]`:
"네가 방금 준 «두 방식이 무엇을 빼는가» 리포트도 d1 100 기록으로 비교했는데
200+600ms 방식이 블록 영위상 0.5s 보다 중심선에 더 붙는다고 했잖아."

**같은 기록, 같은 두 방식인데 그림과 표가 반대를 말하고 있었다.**

### 먼저 의심한 것

**그림 쪽**을 의심했다 — 8 초 한 토막만 본 인상이고 30 초 통계와 다를 수
있다고 생각했다. 그래서 지표를 분해해 봤다 `[측정]`. `tp_band` 는
T-P 구간의 **표본을 전부 모아** p2.5~p97.5 폭을 잰다. 그 폭을 두 갈래로 나눴다:

- **박동별 준위의 산포** — 각 박동의 T-P 중앙값들이 얼마나 흩어지는가
- **구간 안 잡음** — 각 구간에서 자기 중앙값을 뺀 나머지의 폭

### 결정적 측정 `[측정]`

d1 기록 100, 기저선 변동 R 의 50 % 주입:

| 방식 | 옛 `tp_band` | **박동별 준위 산포** | 구간 안 잡음 |
|---|---|---|---|
| 인과 o1 0.5 | 25.9 | **23.3** | 8.1 |
| 블록 영위상 0.5 s | 12.3 | **8.2** | 7.3 |
| **중앙값 200+600** | 8.2 | **2.7** | 7.7 |
| 오프라인 영위상 | 9.7 | 6.2 | 6.1 |

**구간 안 잡음이 7~8 %R 로 네 방식 모두 거의 같다.** 그것이 `tp_band` 의
바닥을 만들어 진짜 차이(2.7 vs 8.2)를 덮고 있었다. **잡음은 front-end 가
갈라내는 대상이 아니다** — 그것은 뒤의 denoiser 몫이다. 평활도 지표에
그것이 들어가 있으면 **front-end 를 고르는 데 쓸 수 없다.**

박동별 준위로 다시 재면 **양축 모두에서 중앙값이 가장 평평하다** (변동 없는
원신호 기준: d0 0.5 · d1 1.0 %R, 오프라인 영위상 2.6 · 2.4 보다도 낮다).

### 놓쳤다면

**"실기록에서는 중앙값의 이점이 사라진다" 가 결론으로 남았을 것이다.**
그것을 근거로 후보 하나를 탈락시켰을 것이고, 근거는 **지표의 잡음 바닥**이었다.
그리고 사용자가 그림으로 반례를 이미 보고 있었으므로, **시연에서 "표와 화면이
다른데요" 를 들었을 것이다.**

### 왜 두 번 연속 같은 실수를 했나

F-29 도 «지표가 못 보던 것» 이었고 F-30 도 그렇다. 공통 원인이 있다 —
**두 번 다 「표본을 모아서 산포를 재는」 형태로 지표를 만들었다.** 그 형태는
편하지만 **서로 다른 원인의 변동을 한 숫자에 섞는다.** F-29 에서는 T-P 구간만
보느라 QRS 를 놓쳤고, F-30 에서는 구간 안 잡음과 박동 간 준위차를 섞었다.

> **재사용할 것.** 지표를 만들 때 «이 숫자를 키우는 원인이 몇 가지인가» 를
> 먼저 세어야 한다. **둘 이상이면 그 지표로는 원인을 고를 수 없다.**
> 이번 수정은 그것을 셋으로 쪼갠 것이다 — 준위 산포(3a) · 준위 이탈(3b) ·
> 구간 안 잡음(진단용). 셋째는 **front-end 로 안 갈린다는 것을 보이려고** 남겼다.

## F-29. 지표 넷이 전부 T-P 구간만 봐서, **눈에 보이는 왜곡을 구조적으로 못 봤다**

### 발단

D-19 로 인과 FE 를 order 1 로 바꾼 뒤, 화면을 본 사용자가 말했다 `[대화]`:
"o1 0.5 Hz 도 o1 0.05 랑 비교했을 때 **Q 나 S 파 근처가 찌그러지는 게 눈에
확실히 보일 정도**라 좀 마음에 안 드는데. (…) 측정 지표가 내가 중요하게
생각하는 부분을 잘 못 잡는 것 같아."

**우리 표에는 그 항목이 없었다.** D-19 는 두 지표로 결정했다 — (1) 박동당
기저선 이동, (2) 남은 기저선 변동. 둘 다 **T-P 구간**만 본다.

### 먼저 의심한 것

"지표가 부족한 게 아니라 사용자가 다른 것을 보는 것" 을 먼저 생각했다.
그런데 두 지표의 정의를 다시 읽어 보면 **정의상 못 잡는다** — (1) 은
`R+420 ms ~ 다음 R−280 ms` 창에 1 차 다항식을 맞춘다. QRS 는 그 창 **밖**이다.
(2) 는 0.5 Hz 이하 성분만 본다. S 골은 그 대역에 없다.

**지표가 안 잡은 게 아니라, 잡을 수 없는 자리를 보고 있었다.**

### 결정적 측정

지표 셋을 새로 넣고 후보 18 개를 같은 자에 올렸다 `[측정]`
(`scripts/explore_lookahead_fe.py` → `docs/13_lookahead_fe.md`):

- **(3) T-P 대역폭** — T-P 표본 전부를 모아 중앙값 제거 후 p2.5~p97.5 폭 [%R].
  박동 **안**의 기울기와 박동 **사이**의 어긋남을 하나로 잡는다.
- **(4) S 골 깊이 오차** — R+80 ms 최저점 깊이의 영위상 대비 차 [%R].
- **(5) T 진폭 오차** — R+150~400 ms 최고점 높이의 영위상 대비 차 [%R].

(4) 가 즉시 사용자가 본 것을 재현했다:

| | (4) S 골 오차 d0 | d1 |
|---|---|---|
| 영위상 (기준) | 0.0 | 0.0 |
| 인과 o4 · 0.5 Hz | 5.0 | **14.4** |
| **인과 o1 · 0.5 Hz (D-19 가 고른 것)** | **3.0** | **5.8** |
| 인과 o1 · 0.05 Hz | 0.4 | 1.2 |

**D-19 가 «고쳤다» 고 적은 설정이 이 축에서는 여전히 5.8 %R 이다.**
D-19 의 표에서 order 1 은 이동 23 %R 로 가장 좋은 축에 있었으므로,
(4) 가 없었다면 **«해결됐다» 로 닫혔을 것이다.**

### 그리고 (5) 가 곧바로 한 번 더 일했다 `[측정]`

새 후보 중 **중앙값 100+300 ms** 가 (3) 에서 압도적이었다 —
T-P 폭 **0.2 %R**, 영위상(6.6)보다도 평평하고 (4) 도 1.9 로 좋다.
지연도 296 ms 로 제일 짧다. **표의 앞 세 열만 보면 우승 후보다.**

(5) 를 재자 **T 진폭 오차 16.2 %R** 이 나왔다. 600 ms 가 아닌 300 ms 중앙값
창이 **T 파를 기저선으로 오인해 깎고 있었다.** 200+600 판은 1.3 %R 로 멀쩡하다.

**지표 하나가 없었으면 T 파를 16 % 깎는 방식을 추천했을 것이다.**

### 놓쳤다면

두 번 틀렸을 것이다. **(a)** D-19 를 «해결» 로 닫고 시연에 내보냈다가
현장에서 같은 질문을 받았을 것이다 — 심전도를 본 적 있는 사람에게 S 골
찌그러짐은 T-P 경사만큼 눈에 띈다. **(b)** 그 다음 개선으로 T 파를 깎는
방식을 골랐을 것이고, 그것은 **T 파 이상이 진단의 핵심인 신호에서
가장 나쁜 종류의 훼손**이다.

### 일반화

> **지표를 만든 시점의 문제만 잰다.** (1)(2) 는 «T-P 가 기울었다»(F-27)
> 라는 질문에 답하려고 만들었고, 그 질문에는 정확히 답했다. 문제는 그 뒤로
> **새 후보군을 그 지표로 계속 판정한 것**이다 — 형태가 다른 후보(중앙값,
> 블록 영위상, 아날로그단)를 들일 때 지표를 함께 늘렸어야 했다.
>
> 실무 규칙: **화면을 보고 나온 불만은 그때마다 지표를 하나 늘릴 기회다.**
> 이번 셋(3·4·5)은 전부 사용자가 «눈에 보인다» 고 말한 것에서 나왔다.

## F-28. 시연 카드 계획이 **축을 안 적고 인용해**, D0 에서만 나온 결과를 D1 카드로 만들 뻔했다

### 발단

`docs/99_status.md` §7.3.1 에 C5 카드 재설계 계획을 적으며 근거로
"`M05` 만 `V−N = −0.0645`, 나머지는 양수(보고서 5.5)" 를 인용했고,

### 놓쳤다면

낫다 — «`M05` 가 위험하다» 보다 **«합성에서만 보이던 위험이 실데이터에서
사라졌다, 그래서 축이 둘 필요했다»** 가 이 과제의 실제 결론이고, F-8 과
같은 이야기를 카드 한 장으로 말할 수 있다.

### 일반화

> **축을 안 적은 인용은 인용이 아니다.** 이 과제의 모든 수치는 D0 또는 D1
> 에 속하고 둘은 자주 다르다(F-14 · F-16 · F-18 · §5.8.4). "보고서 5.5" 처럼
> **절 번호만 적는 인용은 축을 잃는다** — 옮겨 적을 때 `d0`/`d1` 을 숫자에
> 붙여 적어야 한다.

## F-27. 실시간 화면의 T-P 구간이 기울어 있다 — **인과 front-end 의 시간축 얼굴**

### 발단

`--replay` 로 모드 A 화면을 띄우고 보니, **모든 방법에서** T 파와 다음 P 파
사이의 평탄해야 할 구간이 톱니처럼 기울어 있었다 `[대화]`. 모드 B(녹음본)의
같은 방법 출력에는 없던 것이다. "데이터가 달라서인가" 가 첫 질문이었다.

### 먼저 의심한 것

**데이터**를 의심했다 — 모드 A 는 `--replay synth`, 모드 B 는 은행에 담긴
mitdb 다. 그런데 **모든 방법이 똑같이** 기운다는 점이 그 가설과 안 맞는다.
방법마다 필터가 다른데 같은 모양으로 틀어질 이유가 없다. **모든 방법이
공유하는 것은 하나뿐이다 — 앞단의 front-end.**

### 결정적 측정

**(1) R 스파이크 하나만** 넣고 그 뒤를 봤다 `[측정]`:

| | 최저 | 1.5 s 뒤 값 |
|---|---|---|
| 영위상 FE | −0.029 | **+0.0035** (돌아왔다) |
| **인과 FE** | **−0.123** (4.3 배 깊다) | **−0.0095** (아직 회복 중) |

**QRS 하나가 필터 상태를 걷어차고, 그 회복이 RR 간격보다 느리다.** 그래서
다음 박동이 이전 발길질의 꼬리 위에 올라타고, 기저선이 영영 안 가라앉는다.

**(2) T-P 기울기를 직접 쟀다** (R+420 ms ~ 다음 R−280 ms, P 파를 확실히 뺀 창):

| | D0 합성 | D1 MIT-BIH |
|---|---|---|
| 원본 | 0.0 %/s | 19.6 %/s |
| **영위상 (모드 B)** | **0.3 %/s** | 20.5 %/s |
| **인과 (모드 A)** | **87.0 %/s** | 26.0 %/s |

D0 에서 **0.3 → 87 %/s**. 원인이 확정된다 — **필터를 어느 방향으로 도느냐**
하나다. 영위상은 앞뒤로 두 번 걸어 비대칭 처짐이 상쇄되고, 인과는 그럴 수 없다.

> **이것은 F-25 와 같은 사건의 다른 얼굴이다.** F-25 는 그 대가를 dB 로 쟀고
> (`M06-L1` −4.3 dB), 여기서는 **시간축에서 눈에 보이는 형태**로 나타났다.
> 관람객이 알아채는 쪽은 dB 가 아니라 이쪽이다.

### 고칠 수 있는가 — **공짜가 아니다** `[측정]`

| 인과 FE 설정 | T-P 기울기 (R 대비) | 0.05~0.5 Hz 잔여 |
|---|---|---|
| 영위상 (모드 B 기준) | 0.2 % | 0.0018 |
| **지금: order 4, 0.5 Hz** | **86.6 %** | 0.0036 |
| order 2, 0.5 Hz | 48.4 % | 0.0014 |
| order 1, 0.5 Hz | 30.5 % | 0.0022 |
| order 4, 0.05 Hz | 7.7 % | 0.0319 (**18 배**) |
| **order 1, 0.05 Hz** | **2.9 %** | 0.0096 (5 배) |

**차단 주파수가 차수보다 크게 작용한다** — 0.5 → 0.05 Hz 가 11 배를 줄인다.
진단용 심전도 표준이 0.05 Hz 를 요구하는 이유가 이것이고, 우리는 **잡음 제거를
위해 0.5 Hz 를 골랐다**(01_design 2.1). 대가는 기저선 변동이 5~18 배 남는 것이다.

**그리고 바꾸면 딥러닝이 다시 흔들린다.** 모델은 **0.5 Hz 영위상** FE 를 통과한
신호로 학습했다. F-25 가 인과 FE 로 바꾼 것만으로 `M06-L1` 이 −4.3 dB 를 잃는
것을 쟀는데, 차단까지 옮기면 학습 분포에서 더 멀어진다. **`verify_stream_processor.py`
를 대안 FE 로 다시 돌려 재기 전에는 바꾸면 안 된다.**

### 놓쳤다면

**시연에서 "이 시스템은 기저선을 못 잡는다" 로 읽혔을 것이다.** 심전도를 본
적 있는 사람에게 T-P 구간의 경사는 눈에 띄고, 우리는 그것을 설명할 말을 갖고
있지 않았을 것이다. 실제로 이 질문은 **화면을 만든 다음에야** 나왔다 —
dB 표만 봤을 때는 아무도 묻지 않았다.

### 조치

**재보고 나서 바꿨다.** 처음에는 "학습 분포에서 더 멀어질 테니 손해일 것"
이라고 적었는데, **재보니 정반대였다** — 차수만 4 → 1 로 낮추자 D1 에서
`M06` 이 −4.32 → **+0.89 dB** 로 돌아왔다. 손해의 원인이 «분포 이동» 이
아니라 **«필터가 파형을 망가뜨린 양»** 이었기 때문이다. 결정은 **D-19**.

차단(0.5 Hz)은 **건드리지 않았다.** 0.05 Hz 까지 내리면 T-P 기울기가 더
줄지만(2.9 %) D1 의 dB 이득이 없고 기저선 변동이 5 배 남는다.

화면에는 그대로 각주를 뒀다 — **실제 전극에서는 기울기의 상당 부분이 기록
자신의 것**이기 때문이다. MIT-BIH 원본이 이미 19.6 %/s 이고, 인과 FE(order 4)
가 35.6 %/s 로 만들던 것을 order 1 이 29.8 %/s 로 줄인다. **합성(D0)에서
0.3 → 87 %/s 로 극적이던 것이 실기록에서는 완만하다.**

### 일반화

> **주파수로만 고른 필터는 시간축에서 다른 얼굴을 갖는다.** 0.5 Hz 차단은
> 스펙트럼에서 보면 "0.5 Hz 아래를 지운다" 이지만, 시간축에서는 **"큰 편위마다
> 수 초짜리 처짐을 남긴다"** 이다. 둘 다 봐야 했고, 우리는 화면을 만들기
> 전까지 앞의 하나만 봤다.
