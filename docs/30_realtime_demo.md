# 30. 실시간 시연 설계 — 무엇을 만들고 무엇이 어려운가

> 이 문서는 **구현 전 설계 검토**다. 확정된 결정은 D 로, 실측은 산출물을
> 가리켜 적는다. 아직 안 정한 것은 **[미정]** 으로 남긴다 — 빈칸과 미정은
> 다르다(19_record_keeping 10절).

---

## 1. 요구 정리 — **두 모드는 요구가 완전히 다르다**

사용자가 강조할 것이 둘이라고 했고, 그 둘은 **서로 다른 것을 증명한다.**

| | **모드 A — 실측** | **모드 B — 기존 데이터** |
|---|---|---|
| 무엇을 보이나 | AFE 가 **실제 시연자의 심전도를 잡는가** | **방법 간 denoising 차이**가 드러나는가 |
| 입력 | Uno + AFE 실시간 | 합성 / mitdb / nstdb **녹음본** |
| 잡음 | 실제 환경 잡음 (통제 불가) | PLI · EM · MA 등을 **골라서 주입** |
| 정답(clean) | **없다** | **있다** |
| 실시간 제약 | **있다** (수십~100 ms) | **없다** |
| 과학적 주장 | 하드웨어가 된다 | **보고서의 결과 그대로** |

**이 구분이 설계의 전부다.** 모드 B 는 녹음본이라 **실시간 제약이 아예
없다** — 미리 계산해 둘 수도 있다. 모드 A 는 실시간이지만 **denoising 이
목적이 아니라 AFE 검증이 목적**이다.

> **둘을 한 화면에 섞으면 안 된다.** 모드 A 의 출력은 지연 제약 때문에
> 품질이 깎이고, 모드 B 는 안 깎인다. 구분 없이 나란히 두면 **같은 방법이
> 두 품질로 보이고** 보는 사람은 어느 쪽이 그 방법의 실력인지 알 수 없다.

## 2. 실시간 제약을 다시 봤다 — **window 길이는 지연이 아니다**

처음에 "`win=1024` = 4.096 s 이므로 4 초 지연" 이라고 말했는데 **틀렸다.**
window 는 *문맥* 이고, 버퍼가 한 번 차고 나면 매 hop 마다 새 출력이 나온다.

시각 `t` 에 가진 것은 `[t-W+1, t]` 다. 모델은 W 개 추정을 내지만 **끝에 가까운
샘플일수록 미래 문맥이 없다.** 샘플 `t-d` 를 내보내면

    출력 지연 = d / fs,   그 샘플이 가진 미래 문맥 = d 샘플

이 되고, `d` 는 우리가 고르는 값이다. **그러면 `d` 를 얼마로 해야 하는가** —
이것이 잴 수 있는 질문이고, **재학습 없이** 기존 체크포인트로 쟀다.

### 2.1 지연-품질 곡선 `[측정]`

`scripts/measure_stream_latency.py`, 산출물 `results/stream_latency.json`.
M06, seed 3 개, window 안 위치별 출력 SNR 을 중앙부 대비로 적었다.

| 끝에서 `d` | 지연 | **D1 (실데이터)** | **D0 (합성)** |
|---|---|---|---|
| 0 | 0 ms | −1.75 ± 0.58 dB | −4.45 ± 1.88 dB |
| 5 | 20 ms | −1.38 ± 0.26 | −3.47 ± 1.68 |
| **12** | **48 ms** | **−0.53 ± 0.47** | **−0.72 ± 0.65** |
| 25 | 100 ms | −0.78 ± 0.11 | −0.01 ± 0.33 |
| 50 | 200 ms | −0.05 ± 0.35 | −2.43 ± 0.72 |

**약 48 ms 지연이면 가장자리 손해가 사라진다.** 그 뒤로는 표준편차(0.3~1.9 dB)
안에서 오르내릴 뿐 추세가 없다 — D0 의 200 ms 값 −2.43 은 그 진동의 하단이지
"더 기다리면 나빠진다" 는 뜻이 아니다.

> 이 숫자에는 **공통 front-end 의 가장자리 효과(F-4)도 포함**돼 있다.
> 데이터셋이 window 마다 FE 를 적용하기 때문이다. 별도로 뺄 필요가 없다.

### 2.2 지연 예산 — 100 ms 안에 들어간다

| 항목 | 크기 | 근거 |
|---|---|---|
| ADC + 시리얼 | 1~5 ms | 1 kHz × 2 byte = 2 kB/s, 115200 baud 에 여유 |
| hop 버퍼링 | hop/2 평균 | hop 25 샘플(100 ms)이면 50 ms |
| **알고리즘 지연 `d`** | **48 ms** | **2.1 실측** |
| 추론 | 10 ms (M06, 데스크탑 1 thread) | 5.6 · 5.10.5 |
| 렌더링 | 16~33 ms | 60 / 30 fps |

**합계 약 80~130 ms.** 목표(수십~100 ms)에 걸치므로 **hop 을 12 샘플(48 ms)로
줄이면 여유가 생긴다** — 추론이 10 ms 라 hop 을 줄여도 부하는 감당된다.

**즉 모드 A 에서 지연 우회(별도 창에 n 초 지연)는 품질 때문에는 필요 없다.**
필요해지는 것은 **하드웨어가 못 따라올 때**뿐이고, 그것은 3 절의 문제다.

## 3. 처리 장치 — **노트북 하나로 끝내는 것을 권한다**

| | 역할 | 판단 |
|---|---|---|
| **Uno** | AFE + ADC + 시리얼 송신 | **수집 전용.** M06 가중치만 3.9 MB 라 애초에 불가 |
| Raspberry Pi 3 | 처리 | **넣지 않기를 권한다** — 아래 |
| **노트북** | 처리 + 표시 | **권장** |

**Pi 3 를 빼는 이유는 성능이 아니라 구조다.** 표시를 노트북에서 하기로 했으므로
Pi 를 넣으면 **시리얼 한 단과 네트워크 한 단이 늘어난다** — 시연 중 끊길 지점이
둘 늘어나는데 얻는 것이 없다. 사슬은 `Uno → USB 시리얼 → 노트북` 이 가장 짧다.

**Pi 3 의 실제 처리량은 [미정]** 이다. Cortex-A53 1.2 GHz 에 NEON 최적화된
PyTorch 가 기본으로 깔리지 않아 데스크탑 대비 10~30 배 느릴 것으로 보이지만
`[추론]`, **재보지 않았다.** Pi 를 꼭 써야 할 이유가 생기면 그때 재고, 그
전에는 추정으로 결론 내지 않는다.

## 4. 모드 B 설계 — 실시간이 아니라 **사전 계산**이 답이다

요구는 "데이터/잡음을 골라 방법별 결과 파형을 비교" 다. 이것은 **녹음본이므로
미리 다 계산해 둘 수 있다.** 그러면:

- 시연 중 **계산이 실패할 수 없다** (라이브 시연에서 가장 큰 위험)
- 선택이 **즉시** 반영된다 (기다림 없음)
- 파이썬 환경 없이 **브라우저만으로** 돌릴 수 있다

**규모 추정** `[추론]`: 기록 3 × 잡음 5 종 × SNR 3 단계 = 45 조합,
각 12 방법 × 10 s × 250 Hz. float16 으로 **약 2.7 MB** — 파일 하나에 들어간다.

> 조합을 다 만들지 말고 **골라야 한다.** 45 개도 시연에서 다 못 보여준다.
> 방법 간 차이가 가장 잘 드러나는 조합을 5.2(잡음별)·5.1(SNR별)에서 고른다 —
> 예: 임펄스 잡음(딥러닝이 크게 이김), PLI(front-end 가 이미 해결), 20 dB
> 저잡음(딥러닝이 짐). **세 장면이 보고서의 세 결론을 그대로 보인다.**

### 4.1 화면 구성

```
[ 실측 / 기존 데이터 ]  <- 먼저 고른다

기존 데이터일 때:
  기록  [ 합성 | mitdb 100 | nstdb ... ]
  잡음  [ PLI | EM | MA | 임펄스 | 혼합 ]   SNR [ 0 | 10 | 20 dB ]

  ┌──────────── 입력 (잡음 섞임) ────────────┐
  ├── M_FE ──┬── M01 ──┬── M04 ──┬── M06 ──┤   각 칸에 [?]
  └───────── 같은 시간축, 같은 y 스케일 ─────┘
```

**같은 y 스케일이 중요하다.** S4 를 만들 때 행마다 축이 달라 M08 이 좋아
보였던 일이 있다 — 축을 맞추자 차이가 정직해졌다.

`[?]` 는 방법·잡음마다 해설을 띄운다. 내용은 이미 있다 — `18_glossary.md`
와 보고서 5 장. **새로 쓰지 말고 그것을 가리키게 한다.**

## 5. 예상 난관과 대응

| # | 난관 | 왜 생기나 | 대응 | 상태 |
|---|---|---|---|---|
| 1 | window 가장자리 품질 저하 | 끝 샘플에 미래 문맥이 없다 | **`d = 12`(48 ms) 지연** | **해결, 실측(2.1)** |
| 2 | hop 마다 이음매가 튄다 | 연속한 두 window 가 같은 샘플에 **다른 추정**을 낸다 | 겹침 구간에서 **crossfade**, 또는 새 샘플만 내보내기 | 설계됨, 미측정 |
| 3 | 진폭이 계단처럼 뛴다 | 데이터셋이 window 마다 `robust_scale(y)` 로 정규화한다 | **느린 시정수의 러닝 스케일** — window 마다 다시 재지 않는다 | 설계됨, 미측정 |
| 4 | front-end 의 가장자리 전이 | `filtfilt` 는 비인과적이고 padding 에 민감하다(F-4, 11.9 dB) | 링버퍼 전체에 FE 적용 + `d` 지연이 이미 흡수 | 2.1 에 **포함돼 측정됨** |
| 5 | 60 Hz 전원선 잡음 | AFE 가 실환경에서 반드시 받는다 | `M01` 의 자동 notch. **시연에서는 오히려 볼거리** | 기존 구현 |
| 6 | 모드 A 에 정답이 없다 | 실측 신호는 clean 을 모른다 | **SNR 수치를 띄우지 않는다.** 파형만. 수치는 모드 B 에서 | 규칙 |
| 7 | 시연 중 크래시 | 라이브의 최대 위험 | 모드 B 사전 계산, 모드 A 는 **녹화본 대체 경로** | 설계됨 |
| 8 | Pi 3 처리량 | 미측정 | 노트북 단독 구성으로 회피(3절) | **[미정]** |

### 5.1 2 · 3 번은 함께 재야 한다

이음매와 진폭 계단은 **눈에 가장 잘 띄는 결함**이고, 둘 다 "정지 화면에서는
안 보이고 움직일 때 보인다". 그래서 **스트리밍 재생으로 재야 한다** —
녹음본을 스트리밍하듯 흘려보내고 **한 번에 처리한 결과와 비교**하면
이음매의 크기를 dB 로 잴 수 있다. 이것이 다음 측정 과제다.

## 6. 구현 절차 (제안)

**공통 원칙**: **모드 B 를 먼저 만든다.** 실시간 제약이 없어 위험이 낮고,
완성되면 그 자체로 발표에 쓸 수 있다. 모드 A 는 그 위에 입력만 바꿔 얹는다.

| 단계 | 무엇 | 산출물 | 선행 |
|---|---|---|---|
| **R-1** | 시연용 조합 선정 + 사전 계산 | (계획) `scripts/build_demo_bank.py` | 없음 |
| **R-2** | 모드 B 화면 (정적, 브라우저) | (계획) `demo/index.html` | R-1 |
| **R-3** | 스트리밍 이음매·진폭 측정 | (계획) `scripts/measure_stream_seam.py` | 없음 |
| **R-4** | 스트리밍 처리기 (`StreamProcessor`) | (계획) `ecgdn/realtime/stream.py` | R-3 |
| **R-5** | Uno 펌웨어 + 시리얼 브리지 | (계획) `scripts/serial_bridge.py` | 하드웨어 |
| **R-6** | 모드 A 를 R-2 화면에 연결 | WebSocket | R-4 · R-5 |

> 표의 `(계획)` 은 **아직 없는 파일**이라는 뜻이다. 만들고 나면 표식을
> 뗀다 — `tests/test_repo_integrity.py` 가 양방향으로 확인한다(없는데
> 표식이 없거나, 있는데 표식이 남아 있으면 실패).

**R-1 · R-2 · R-3 은 하드웨어 없이 지금 할 수 있다.** 아두이노 대기 중에
진행할 수 있는 것이 이 셋이다.

### 6.1 `StreamProcessor` 가 지켜야 하는 것

```
ring buffer (W 샘플)
  → front-end (버퍼 전체)
  → 방법별 추정
  → [t-d] 까지만 내보낸다        # d = 12 (48 ms)
  → 이전 출력과 crossfade         # 난관 2
  → 러닝 스케일로 역정규화        # 난관 3
```

**오프라인 경로와 같은 코드를 써야 한다.** 방법 구현을 따로 만들면 시연이
보고서와 다른 것을 보이게 되고, 그것을 알아챌 방법이 없다 — F-9 와 같은
계열이다. `ecgdn/methods/` 를 그대로 호출하고 **버퍼 관리만 새로 쓴다.**

## 7. 아직 정하지 않은 것 **[미정]**

1. **시연 조합 5 개** — 4 절의 세 장면 후보는 있으나 확정 아님
2. **Pi 3 를 쓸 것인가** — 노트북 단독을 권하나 사용자 판단
3. **모드 A 에서 어떤 방법을 보일 것인가** — 전부 보이면 화면이 좁다.
   `M_FE` · `M01` · `M04` · `M06` 넷 정도가 적당해 보이나 미확정
4. **해설 UI** — `[?]` 버튼인지 새 창인지
