# 37. 시연 화면의 디자인 시스템 — 재설계 계획 `[검토 중]`

> 이 문서는 **제작 전 단계**다 — `docs/34_visual_plan.md` 와 같은 성격이다.
> 합의된 뒤에 만들고, 만든 뒤에 결과를 여기 반영한다.
>
> 출처: 사용자가 다른 AI 와 한 대화(Figma MCP · Mobbin · shadcn · Storybook ·
> Playwright 로 UI 파이프라인을 짜는 안)를 가져왔고, 그것을 **우리 화면을 실제로
> 열어 본 결과**에 비춰 판정한다. `docs/31_demo_design_review.md` 가 외부 시안을
> 다룬 것과 같은 방식이다.

## 0. 한 줄 결론

**진단은 「설계가 없다」가 아니다.** `docs/33_card_design_samples.md` 의 색 대비
검증 · 레인 렌더러 · 직접 라벨은 이미 제품 수준의 작업이다. 실망스러운 이유는
셋이고, 전부 **적용과 검증**의 문제다.

| | 무엇 | 왜 안 드러났나 |
|---|---|---|
| **A** | 그 규칙이 **본 화면(`demo/index.html`)에 적용되지 않았다** | 시안(`mockup_expo`)과 카드만 다듬었다 |
| **B** | 규칙의 **단일 출처가 없다** — 같은 방법이 파일마다 다른 색 | 색이 네 파일에 각각 하드코딩돼 있다 |
| **C** | **화면을 여는 장치가 없다** | 그림은 `tests/test_figure_text.py` 가 보는데 HTML 은 아무도 안 본다 |

C 가 A·B 를 몇 달간 숨겼다. `docs/33` 이 이미 같은 종류를 겪었다 —
「**문서가 코드보다 앞서 있었고, 화면을 열지 않으면 드러나지 않는다**」
(B·C 안이 「실패」라고 적힌 첫 판 그대로였던 건).

## 1. 측정 — 화면 넷을 실제로 열어서 본 것 `[측정]`

headless Chromium 1440 폭, `demo/` 의 네 화면. 스크린샷은 세션 산출물이라
저장소에 없다 — **재현 방법을 5.2 에 절차로 남긴다.**

| # | 무엇 | 근거 |
|---|---|---|
| **U-1** | 본 화면에 **방법 색이 없다** — `M_FE`·`M01`·`M04`·`M06` 네 칸이 전부 같은 파랑 | `demo/index.html` 의 `COLOR` 에 `input`·`clean`·`B01` 만 있고 나머지는 기본값 `#184f95` 로 떨어진다 |
| **U-2** | **같은 방법이 파일마다 다른 색** (2 절) | `scripts/make_slides.py` · `scripts/build_metric_cards.py` · `demo/mockup_expo.html` |
| **U-3** | 파형이 가장 중요한데 **가장 작다** — 칸 높이 96 px 고정, 1440×1400 에서 아래 300 px 가 빈다 | `demo/index.html` 의 `canvas{height:96px}` |
| **U-4** | 컨트롤 **일곱 그룹이 같은 무게**로 상단 25 % 를 먹는다 — 데이터·잡음·SNR·방법·구간·표시·재생 | 위계가 없어서 「무엇부터 만지나」가 안 읽힌다 |
| **U-5** | 증거 수치(`dB`·`cc`)가 **12 px 회색 본문**에 흐른다 | 화면에서 가장 중요한 숫자가 시각 순위 최하위다 |
| **U-6** | **실패 상태 화면이 설계되지 않았다** — 연결이 끊긴 `live.html` 은 파형 영역이 통째로 비고 설명문만 남는다 | **D-18 이 「끊김이 시연에서 실제로 일어난다」고 적은 바로 그 상태다** |
| **U-7** | 시안·카드·본 화면이 **서로 다른 시각 언어** 세 벌이다 | 흰 바탕 시스템 폰트(`index`) / ECG 차트지 IBM Plex(`mockup_expo`) / 암전 형광(`cards/A`) |

**U-7 은 절반이 의도다.** 카드 A·B·C 가 갈린 것은 주제의식이 다르기 때문이고
(`docs/33`: 지나가는 사람 / 심사위원 / 다른 팀), 그건 옳다. 문제는 **본 화면
셋(`index` · `live` · `mockup_expo`)끼리도 다른 것**이다. 이 셋은 같은 사람이
같은 자리에서 연달아 본다.

## 2. 색 — **두 체계가 서로를 모른 채 병존한다** `[측정]`

| 방법 | `make_slides.py`·`build_metric_cards.py` | `demo/mockup_expo.html` | `demo/index.html` |
|---|---|---|---|
| `M_FE` | `#e87ba4` 마젠타 | `--classic` `#c07a1f` 황토 | `#184f95` |
| `M01` | `#2a78d6` 파랑 | `--classic` `#c07a1f` 황토 | `#184f95` |
| `M04` | `#eb6834` 주황 | `--classic` `#c07a1f` 황토 | `#184f95` |
| `M06` | `#184f95` 남색 | `--deep` `#184f95` 남색 | `#184f95` |
| `M08` | `#1baf7a` aqua | `--deep` `#184f95` 남색 | `#184f95` |
| `B01` | — | `--oracle` `#2f7d4f` 녹 | `#2f7d4f` 녹 |

**둘은 서로 다른 축을 인코딩한다.** 보고서·카드는 «방법 하나 = 색 하나»
(identity)고, 시연 시안은 «계열 하나 = 색 하나»(family: 고전·딥러닝·oracle)다.

**그리고 둘 다 근거가 있다.** `docs/33` 이 «색은 방법에 고정한다» 고 적은 것도,
`mockup_expo` 가 계열로 묶은 것도 같은 제약에서 나왔다 — 「**네 번째를 얹으면
정상시야 분리도가 무너진다**」. 카드는 방법을 셋으로 줄여 해결했고, 시연 화면은
여덟을 보여야 해서 계열로 묶을 수밖에 없었다.

> **즉 화면이 요구하는 방법 수가 색 체계를 강제한다.** 어느 한쪽이 틀린 게
> 아니라, **한 체계가 두 요구를 다 받도록 설계되지 않았다.**

### 2.1 제안 — 2 단 팔레트 (계열 = 색상, 방법 = 단계)

| 축 | 무엇이 정하나 |
|---|---|
| **색상(hue)** | **계열** — 입력 적갈 · 고전 황토 · 딥러닝 남색 · oracle 녹 · 참값 회색 |
| **단계(step)** | **계열 안의 방법** — `classic-1`=`M_FE`, `classic-2`=`M01`, `classic-3`=`M04` … |

셋만 그리면 단계가 충분히 벌어져 **방법색으로 읽히고**, 여덟을 그리면 계열이
먼저 읽힌다. **한 팔레트가 두 화면을 다 받는다.**

단계 값은 눈으로 고르지 않는다 — 2.2 의 검증기를 통과한 값만 쓴다.

### 2.2 `validate_palette.js` 가 **저장소에 없다** `[측정]`

`docs/33` 은 「`--pairs all` 로 검증했고」 「`validate_palette.js --mode light`
전 항목 PASS」라고 적는데, **그 파일이 저장소에 없다.** 다른 세션의 도구였고
사라졌다. 지금 팔레트를 바꾸면 **같은 자로 다시 잴 수가 없다.**

`docs/19_record_keeping.md` 6 절(측정 근거는 재현 가능하게)에 어긋난다. 그래서
**팔레트를 손대기 전에 검증기부터 저장소 안에 둔다** — 계획 1 단계의 첫 항목이다.

## 3. 외부안 판정 — 채택 · 변형 · 기각

외부 대화는 `Figma MCP → Codex → React/shadcn → Storybook → Playwright → CI`
파이프라인을 제안했다. **방향은 옳고, 그대로 옮기면 이 과제의 제약 둘을 깬다.**

| 제안 | 판정 | 근거 |
|---|---|---|
| **Figma 를 디자인 시스템의 집으로** | **채택 (범위 제한)** | 사용자 판단. 단 **진실의 출처는 저장소**다 — 4.0 |
| **디자인 토큰을 의미 이름으로** (`color.signal.clean`) | **채택** | 우리 문제(2 절)가 정확히 이것이다 |
| **ECG 전용 컴포넌트를 variant/state 로 정의** | **채택** | `card_core.js` 의 `drawLane()` 이 이미 그 모양이다 — 개념이 아니라 **정리**의 문제 |
| **상태별 갤러리로 컴포넌트를 따로 본다** (Storybook 의 핵심) | **채택, 구현은 변형** | U-6·U-7 을 잡는 장치가 이것이다. 다만 5.1 |
| **브라우저를 열어 자동 검증** (Playwright) | **채택, 구현은 변형** | U-1~U-7 전부 «화면을 열면 5 초에 보이는 것»이었다. 5.2 |
| **접근성 자동 검사** (axe) | **채택** | 이 과제엔 특히 맞는다 — 색각 이상에서 고전↔딥러닝이 안 갈리면 시연의 주장 자체가 안 전달된다 |
| **React + Vite 로 전면 전환** | **변형** | 3.1 |
| **shadcn 으로 부품 조달** | **보류** | 우리 화면의 부품은 칩·슬라이더·캔버스 셋이고 이미 있다. 우리가 못 만든 건 **ECG 파형 패널**인데 그건 registry 에 없다 |
| **Mobbin 으로 상용 UI 벤치마킹** | **기각 (유료 결제 불필요)** | 3.2 |

### 3.1 React 전환 — **시연용은 무빌드, 개발용은 빌드판** (사용자 확정)

`demo/index.html` 머리말이 설계 의도를 적어 뒀다 — 「**계산이 없다.** 시연 중에
실패할 계산이 없다는 것이 이 설계의 요점이다」, 「서버 없이 `file://` 로 열린다」.
**D-18** 도 같은 값을 골랐다(「시연 노트북에 `pip install` 을 하나라도 덜 하는
것이 실제 이득」).

전면 전환은 그 근거를 철회해야 하고, 박람회 당일에 **새 실패 지점**(빌드 산출물 ·
번들 경로 · 브라우저 호환)을 만든다. 그래서 **둘로 나눈다**:

| | 무엇 | 어디 |
|---|---|---|
| **시연 산출물** | 지금처럼 `file://` 로 열리는 단일 HTML | `demo/*.html` |
| **개발·검증판** | 갤러리 · 스크린샷 · 접근성 검사 | (계획) `demo/ui/` · `tests/` |

**대가를 적어 둔다**: 두 벌을 동기화해야 한다. 이건 `docs/33` 이 겪은 「문서가
코드보다 앞섰다」와 같은 종류의 위험이다. **그래서 5 절의 검사가 선택이 아니라
전제다** — 검사가 없으면 이 구성을 택하면 안 된다.

### 3.2 Mobbin 을 기각하는 이유 — 우리에겐 **더 가까운 레퍼런스**가 있다

Mobbin 은 모바일 앱 플로우 DB 다. 우리 화면은 1440 폭 데스크톱 계측 대시보드고
박람회 키오스크다. 그리고 우리가 흉내 내야 할 대상은 SaaS 대시보드가 아니라
**환자 감시장치와 ECG 차트지**인데, `mockup_expo.html` 이 이미 그 소재를 잡았다
(살몬 격자 · 스타일러스 먹색). **차용할 곳을 이미 옳게 골랐다** — 외부 DB 가
메울 빈자리가 아니다.

> 외부 대화 자신도 무료 대안 절에서 같은 결론에 도달했다. **결제하지 않는다.**

## 4. 진실의 출처 — 무엇이 무엇을 정하나

### 4.0 Figma 는 **시안과 구조**, 저장소는 **값**

사용자가 「디자인 시스템까지 Figma 로 구축」을 택했다. 그 위에 **한 줄을
덧붙인다**: 이 과제의 산출물은 **재현 가능한 저장소**이고, Figma 파일은 저장소
밖 계정에 있다. 값의 출처를 Figma 에 두면 **저장소가 자기 화면을 설명하지 못하게
된다** — `docs/19_record_keeping.md` 6 절에 어긋난다(2.2 가 이미 그 사례다).

| 무엇 | 출처 |
|---|---|
| 화면의 목적 · UX 원칙 | `docs/30_realtime_demo.md` · `docs/31_demo_design_review.md` · 이 문서 |
| **팔레트·간격·타이포의 값** | (계획) `demo/ui/palette.json` — **여기가 원본** |
| 컴포넌트 구조 · 레이아웃 시안 | **Figma** (여기서 탐색하고, 확정되면 값을 내려보낸다) |
| 실제 동작 | `demo/*.html` |
| 상태 목록(정상·로딩·빈·끊김·극단값) | (계획) `demo/ui/gallery.html` |
| 검증 | (계획) `tests/test_ui_tokens.py` · `tests/test_demo_screens.py` |
| 설계 결정의 이유 | `docs/21_decisions.md` (D-29) |

**Figma → 저장소 방향으로만 값이 흐른다.** Figma 에서 색을 고치면 사람이
`palette.json` 에 옮겨 적고 검증기를 돌린다. 반대 방향(저장소 → Figma)은 동기화
편의이지 권위가 아니다.

## 5. 계획 — 네 단계

각 단계는 **앞 단계의 검사가 초록일 때만** 시작한다.

### 5.1 1 단계 — 값을 한 곳으로 (코드 변경 없음에 가깝다)

| # | 무엇 | 산출물 |
|---|---|---|
| 1 | **색 검증기를 저장소 안에** — 2.2. all-pairs ΔE · 정상/색각 이상 · 라이트/다크 | (계획) `scripts/validate_palette.py` |
| 2 | **팔레트 단일 원본** — 2.1 의 2 단 체계. 기존 값을 먼저 그대로 옮겨 담고, 검증기로 현 상태의 실패를 **먼저 기록한다** | (계획) `demo/ui/palette.json` |
| 3 | 거기서 **CSS 와 Python 을 생성** — `make_slides.py`·`build_metric_cards.py` 가 상수 대신 이것을 읽는다 | (계획) `scripts/build_tokens.py` → (계획) `demo/ui/tokens.css` |
| 4 | 검사: 저장소 안의 **하드코딩된 색 리터럴이 팔레트에 있는 값인지** | (계획) `tests/test_ui_tokens.py` |

> 3 번이 U-2 를 구조적으로 끝낸다. **보고서 그림과 시연 화면이 같은 파일에서
> 색을 받으면 어긋날 수가 없다.**

### 5.2 2 단계 — 화면을 여는 장치 (**여기가 가장 값이 크다**)

| # | 무엇 | 산출물 |
|---|---|---|
| 1 | **상태 갤러리** — 각 컴포넌트의 정상·로딩·빈·**끊김**·극단값(SNR −5/25)·긴 라벨을 한 장에 | (계획) `demo/ui/gallery.html` |
| 2 | **스크린샷 절차** — headless Chromium 으로 갤러리와 화면 넷을 찍는다 (1 절에서 쓴 방법) | (계획) `scripts/shoot_screens.py` |
| 3 | **화면 검사** — DOM 을 열어 본다: 대비비, 캔버스가 0 픽셀인지, 글이 상자 밖으로 나갔는지, 색만으로 신원을 알리는 곳이 있는지 | (계획) `tests/test_demo_screens.py` |

**`docs/33` 의 결함 셋(글 깨짐 · 축 잘림 · 곡선이 상자 밖)은 전부 이 검사가 잡는
종류다.** 그때는 사람이 화면을 열어 찾았다.

### 5.3 3 단계 — 레이아웃 재설계 (U-3·U-4·U-5)

1 · 2 단계가 끝나야 **바꾼 것이 나아졌는지 잴 수 있다.** 목표는 셋:

- **파형이 첫 시선**이다 — 세로 공간의 다수를 가져간다. 1280×720 에서 칸 최소
  높이를 정하고 검사로 고정한다
- **컨트롤에 위계** — 항상 만지는 것(잡음 · SNR)과 가끔 만지는 것(축 · 표시 ·
  재생)을 갈라 놓는다
- **증거 수치를 격상** — `dB` 는 본문이 아니라 **수치 표시**다. `docs/32_metric_cards.md`
  가 카드에서 쓴 방식을 화면으로 가져온다

여기서 Figma 를 쓴다 — 레이아웃 대안 두셋을 빠르게 비교하는 자리가 이 단계다.

### 5.4 4 단계 — 실패 상태와 접근성 (U-6)

- **끊김·lead-off·처리 밀림**이 각각 어떤 화면인지 설계한다. D-18 이 실제로
  일어난다고 적었고, **박람회에서 그 화면이 우리 시연의 얼굴이 된다**
- 색각 이상에서 고전↔딥러닝이 갈리는지 검증기로 확인하고, 안 갈리면 **선 종류와
  직접 라벨**을 더한다 (`docs/33` 의 규칙을 본 화면까지 넓힌다)
