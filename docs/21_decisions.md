# 21. 설계 결정 (D) — 갈림길에서 무엇을 왜 골랐나

> 형식은 `docs/19_record_keeping.md` 를 따른다.
> **판별 질문**: "다르게 골랐다면 다른 결과가 나왔는가?"
>
> 결정은 발견이 아니다. 틀린 게 아니라 **고른 것**이고, 나중에 "왜 그렇게 했냐"
> 는 질문을 받는다. 그때 근거와 **검토했던 대안**이 남아 있어야 한다.

## D-1. 주 결과는 front-end 를 적용한 조건으로 한다

| | |
|---|---|
| 시점 | `cfb5d1a` (F-10 조치) |
| 상태 | 유효 |

### 갈림길
F-10 을 고칠 때 두 방향이 있었다. **딥러닝에도 front-end 를 주는 것**과
**모든 방법에서 front-end 를 빼고 알고리즘 자체만 비교하는 것.**

### 검토한 선택지
| | 의미 | 문제 |
|---|---|---|
| FE 적용 | 실사용 시나리오 | front-end 가 천장을 정한다(F-11) |
| FE 제거 | 알고리즘 본질 비교 | 실측 장비에서는 쓰지 않을 조건 |

### 고른 것과 근거
**FE 적용을 주 조건, FE 제거를 부록**(`exp_a_nofe.yaml`)으로 두었다.
실측 장비에서는 front-end 를 당연히 쓰므로, 그것을 뺀 비교는 이 과제의 질문
("우리 취득 시스템에 무엇이 적합한가")에 답하지 못한다.

### 되돌려야 하는 조건
과제의 질문이 "알고리즘 자체의 우열" 로 바뀌면. 또는 front-end 천장(34 dB)이
비교를 무의미하게 만들 만큼 낮아지면.

### 파생 결정
부록 조건에 딥러닝을 넣지 않았다(`dl_methods: {}`). FE 없이 학습한 체크포인트가
없어서, 넣으면 train/test 전처리 불일치가 된다.

## D-2. 데이터축은 명시 선택하고 산출물 경로를 분리한다

| | |
|---|---|
| 시점 | `824adc3` (P-1) |
| 상태 | 유효 |

### 갈림길
`source: auto` 는 `data/raw/mitdb` 에 파일이 생기는 순간 조용히 D0 → D1 로
바뀐다. 같은 커밋에 같은 config 로 같은 명령을 돌려도 다른 결과가 나온다.

### 검토한 선택지
1. **`auto` 를 금지**하고 명시를 강제 — 재현성은 최선이나 편의성을 잃는다
2. **`auto` 를 두되 해석 결과를 출력** + 산출물 경로에 축 태그
3. config 를 D0/D1 로 복제 — 중복이 늘고 두 벌이 어긋난다

### 고른 것과 근거
**2번.** `auto` 자체를 막지 않는 대신 **결과가 섞이지 않게** 했다
(`results/d0/`, `results/d1/`). 금지는 실수를 막지만 편의를 해치고,
경로 분리는 실수해도 **덮어쓰지 않는다.** 후자가 손실이 작다.

체크포인트 경로도 `results/{tag}/m06_l1/best.pt` 로 템플릿화해서,
D0 모델을 D1 평가에 먹이는 사고가 구조적으로 막히게 했다.

## D-3. D1 의 참조는 front-end 를 통과한 신호로 정의한다

| | |
|---|---|
| 시점 | `72fcc52` (F-12 조치) |
| 상태 | 유효 |
| 승인 | 사용자 확인 후 진행 |

### 갈림길
MIT-BIH 원본은 clean 이 아니다(F-12). 무엇을 '정답' 으로 둘 것인가.

### 검토한 선택지
| 안 | 내용 | 장 | 단 |
|---|---|---|---|
| **A** | 참조 = `FE(원본)` | 표준 관행, 코드 변경 최소 | 목표가 "원본 복원"이 아니게 됨 |
| B | front-end 를 파이프라인 밖 공통 전처리로 분리 | 가장 깨끗한 구조 | `M_FE` 기준선이 identity 가 되어 지금까지 쌓은 "front-end 기여분" 분석 틀이 사라짐. methods 계층 전면 수정 |
| C | D1 에서 front-end 컷오프 완화 | 변경이 작음 | 축마다 front-end 가 달라져 D0/D1 비교가 어려워지고, 문제를 줄일 뿐 없애지 못함 |

### 고른 것과 근거
**A.** 과제 목표를 **"0.5~100 Hz 대역의 ECG 를 복원한다"** 로 명시하는 것이
정직하고, ECG denoising 문헌의 표준 관행이며, 변경 범위가 가장 작다.
B 는 구조적으로 더 깨끗하지만 F-10/F-11 에서 얻은 분석 틀(`M_FE` 기준선)을
버려야 해서 순손실이다.

### 되돌려야 하는 조건
"원본 파형 그대로의 복원" 이 과제 목표가 되면. 또는 front-end 를 쓰지 않는
방법군이 비교에 들어오면.

## D-5. D0 를 완결한 뒤 D1 로 넘어간다

| | |
|---|---|
| 시점 | `29c3d80` (`99_status.md` P-1~P-9) |
| 상태 | 유효 |

### 갈림길
D1 데이터가 도착했을 때, 곧바로 D1 으로 갈 것인가 D0 를 마무리할 것인가.

### 검토한 선택지
| | 의미 | 문제 |
|---|---|---|
| D1 즉시 착수 | 최종 목표에 빨리 도달 | D0 결과 세트가 불일치인 채 남아 어떤 표도 못 만든다 |
| **D0 완결 후 D1** | 두 축의 비교 자체가 결과 | D1 착수가 늦어진다 |

### 고른 것과 근거
**D0 완결 우선.** 세 가지 이유다.
1. D0 결과 세트가 **내부적으로 불일치** 상태였다(일부만 FE 재학습). 이대로
   두면 어떤 표도 만들 수 없다.
2. D0 는 파이프라인 검증 역할이고, **D0/D1 비교 자체가 결과**가 된다
   (F-8 의 연장 — 합성 벤치마크가 무엇을 왜곡하는가).
3. 실제로 한 번 순서를 건너뛰어 무효 수치가 보고서에 경고 없이 남은 적이 있다.

`99_status.md` 에 **"P-5(결과 해석 보고)를 건너뛰고 P-7 로 가지 않는다"** 를
명시적으로 적어 두었다.

## D-6. oracle 의 family 라벨을 `bound` → `oracle` 로 바꾼다

| | |
|---|---|
| 시점 | `939b485` |
| 상태 | 유효 |

### 갈림길
`B01`/`B02` 를 표에서 어떻게 부를 것인가. 라벨 하나지만 독자의 해석을 좌우한다.

### 검토한 선택지
| | 문제 |
|---|---|
| `bound` 유지 | "모든 방법의 상한" 으로 읽힌다 |
| **`oracle` 로 변경** | 정확하지만 "그럼 상한은 무엇인가" 라는 질문이 남는다 |
| 표에서 제외 | 상한 없이 비교하면 "얼마나 더 갈 수 있는가" 를 알 수 없다 |

### 고른 것과 근거
**`oracle` 로 변경하고 label 에 계열을 명시**했다.

`family="bound"` 는 "모든 방법의 상한" 으로 읽힌다. 실제로는 각자 자기 계열의
상한일 뿐이고, `M07` 은 −5 dB 에서 `B01` 을 실제로 넘는다(18.54 vs 15.86).
**oracle 을 넘는다는 사실 자체가 그 oracle 이 그 방법의 상한이 아니라는 증거**다.

`oracle_gap` 지표의 적용 범위도 wavelet thresholding 계열로 한정한다고 명시했다.

## D-7. `Se`/`PPV` 를 주 지표로 승격한다

| | |
|---|---|
| 시점 | `cfb5d1a` 이후 |
| 상태 | 유효 |

### 갈림길
R-peak 관련 지표 중 무엇을 주 지표로 올릴 것인가.

### 검토한 선택지
| | 재는 것 | 한계 |
|---|---|---|
| `rpeak_mae_ms` (기존) | 매칭된 peak 의 타이밍 정확도 | **놓친 beat 를 못 본다** |
| **`Se`/`PPV` 추가** | 검출률과 오검출률 | 지표 수가 늘어 표가 커진다 |

### 고른 것과 근거
**`Se`/`PPV` 를 주 지표로 승격**하고 `rpeak_mae_ms` 는 유지했다.

`rpeak_mae_ms` 는 **매칭된 peak 만** 본다. 절반을 놓쳐도 남은 것의 타이밍이
정확하면 작게 나온다. 실측에서 전 방법이 8.6~8.8 ms 로 검출기 산포 안에 묻히는데,
`PPV` 는 0.977 → 0.996 으로 크게 갈렸다. **딥러닝은 오검출을 줄인다** 는 사실이
`rpeak_mae_ms` 만으로는 전혀 보이지 않는다.

## D-8. 학습 러너는 재개를 기본으로 켠다

| | |
|---|---|

| 상태 | 유효 |

### 갈림길
`--resume` 을 기본으로 켤 것인가 끌 것인가.

### 검토한 선택지
| | 위험 |
|---|---|
| 기본 끔 | 중단 복구 때마다 플래그를 기억해야 하고, 잊으면 처음부터 재학습 |
| **기본 켬** | 재학습하려 했는데 이어서 돌 수 있다 → `RESUME=0` 로 해제 가능하게 |

끝난 학습은 `train.py` 가 알아서 건너뛰므로, 재개를 기본으로 켜도 손해가 없다.
처음부터 다시 학습하려면 `RESUME=0`.

## D-9. SWT 파라미터는 축별 튜닝 결과를 자동으로 쓴다

| | |
|---|---|
| 시점 | P-7 이후 |
| 상태 | 유효 |

### 갈림길
D1 TRAIN split 재탐색 결과가 D0 와 크게 다르다.

| | sigma | mode | protect_qrs | k |
|---|---|---|---|---|
| D0 | `d2` | garrote | **True** | (2.5, 2.0, 0.6, 0.4, 0.3) |
| D1 | `d1` | hard | **False** | (0.6, 0.2, 0.1, 0.3, 0.3) |

D1 에서는 threshold 가 훨씬 낮고(k 0.6 vs 2.5) QRS 보호가 오히려 해롭다.
어느 파라미터로 D1 실험을 돌릴 것인가.

### 검토한 선택지
1. **D0 값 고정** — 두 축이 같은 설정이라 비교가 단순
2. **축별 튜닝 값** — 각 축에서 `M04` 가 최선을 다한 상태로 비교
3. 두 설정을 모두 평가에 넣어 별도 방법으로 취급

### 고른 것과 근거
**2번.** 설계 원칙 **"baseline 을 약하게 두지 않는다"** 가 직접 적용된다.
D0 파라미터로 D1 을 돌리면 `M04` 가 부당하게 약해지고, 그 상태로 "딥러닝이
낫다" 고 쓰는 것은 F-6 에서 이미 겪은 실수(약한 baseline 과의 비교)의 반복이다.

1번의 장점(비교 단순성)은 **`05_swt_tuning_{d0,d1}.md` 두 문서에 각 축의 최적점이
남으므로** 잃지 않는다. 오히려 "축마다 최적점이 다르다" 는 것 자체가 결과다.

3번은 표가 복잡해지고, 어느 쪽이 그 축의 `M04` 인지 독자가 판단해야 해서 기각.

### 구현
`results/{tag}/tune_swt/best.json` 이 있으면 `run_exp` 가 자동으로 읽어
`M04`/`M04np`/`B01` 에 주입한다. 없으면 `config.py` 의 기본값을 쓴다.
어떤 파라미터가 쓰였는지는 실행 로그와 `manifest.json` 에 남긴다.

### 되돌려야 하는 조건
축별 최적점 차이가 지표 분해능 안에 들어가면(그러면 굳이 나눌 이유가 없다).
또는 튜닝이 과적합을 보이면 — 현재 D1 은 holdout(12.58)이 tune(12.47)보다
높아 해당 없다.

## D-10. 실험 러너는 학습 완료를 확인한 뒤에만 시작한다

| | |
|---|---|
| 시점 | P-8 진행 중 (D1 학습 3/7 시점) |
| 상태 | 유효 |

### 갈림길
D1 학습이 도는 도중에 컨텍스트가 압축됐고, "학습이 끝나면 다음 단계로
넘어간다" 는 경로가 실제로 안전한지 점검하다가 두 개의 조용한 실패 경로를
찾았다. 둘 다 **에러 없이 그럴듯한 결과를 만들어 낸다.**

1. **체크포인트 없음** — `run_exp.py:103` 은 체크포인트가 없으면
   `[skip] {mid}: checkpoint not found` 한 줄을 찍고 그 방법을 뺀 채 계속
   간다. 실험 러너는 출력을 `tail -20` 으로만 남기므로 그 줄이 스크롤에
   묻힌다. 표는 정상적으로 생성되고, 다만 행이 하나 없다.
2. **학습 중인 체크포인트** — `best.pt` 는 epoch 마다 갱신되므로 학습
   도중에도 파일이 존재한다. 파일 존재만 확인하면 게이트를 통과하고,
   **덜 학습된 모델의 성능이 최종 표에 실린다.** 이때는 행조차 빠지지
   않으므로 표만 봐서는 알 방법이 없다. [코드]

두 경우 모두 F-9 와 같은 계열이다 — 산출물은 멀쩡하고 측정의 전제만 틀렸다.

### 검토한 선택지
1. **아무것도 안 한다** — 사람이 학습 완료를 확인하고 실험을 돌린다는 규율에
   의존. 이 프로젝트에서 학습은 이미 세 번 중단됐고(O-2), 재개 후 어디까지
   됐는지는 로그를 읽어야 안다. 규율에만 기대는 것이 실패한 전례가 있다.
2. **`run_exp.py` 가 `[skip]` 대신 죽게 한다** — 가장 직접적이지만, 의도적
   부분 실행(방법 하나만 빨리 확인)이 불가능해진다.
3. **실험 러너 앞에 게이트를 둔다** — 러너로 전체를 돌 때만 막고,
   `run_exp.py` 를 직접 부르는 경로는 그대로 둔다.

### 고른 것과 근거
**3번.** 사고가 실제로 일어나는 지점은 "전체 파이프라인을 한 번에 돌릴 때"
이지 개별 실험을 손으로 부를 때가 아니다. 게이트를 러너에 두면 그 경로만
막고 탐색적 실행의 자유는 남는다.

`scripts/check_ckpts.py` 가 `configs/*.yaml` 의 `dl_methods` 를 읽어 해당
데이터축에 필요한 체크포인트를 전부 확인하고, 하나라도 없으면 종료코드 2 로
러너를 중단시킨다. 학습 락(`results/.train.lock`)이 잡혀 있으면 파일이 있어도
막는다. 강행하려면 `--ignore-lock` 을 명시해야 한다.

락이 남았는데 학습 프로세스가 없으면 **"컨테이너 강제 종료로 락만 남은
상태"** 로 진단하고 해제 명령을 안내한다. 이 상태는 실제로 생길 수 있다 —
락 해제가 `trap ... EXIT` 에 걸려 있어 SIGKILL 에는 실행되지 않기 때문이다.

### 되돌려야 하는 조건
게이트가 정당한 부분 실행을 막아 `--ignore-lock` 이 습관적으로 붙기 시작하면.
그 시점에는 게이트가 방어가 아니라 통과 의식이 된 것이므로 다시 설계해야 한다.

### 남긴 검사
`tests/test_repo_integrity.py` 3건. 게이트 호출이 첫 실험보다 앞에 있는지,
게이트의 기본 config 목록이 러너가 실제로 도는 것을 전부 덮는지, 학습 락
검사가 남아 있는지. 특히 두 번째가 중요하다 — 실험을 추가하면서 게이트
목록을 안 고치면 그 실험만 조용히 검사 밖으로 빠진다.

## D-11. TCN 을 통째로 들이는 대신 "해상도" 하나만 남긴 판을 만든다

| | |
|---|---|
| 시점 | P-9 (사용자가 TCN 을 새 알고리즘 후보로 제시) |
| 상태 | 유효 — 결과는 F-20 |

### 갈림길
딥러닝 방법이 이미 셋(`M06`·`M07`·`M08`) 있는데 넷째를 넣을 것인가, 넣는다면
어떤 형태로 넣을 것인가.

TCN(temporal convolutional network)은 세 가지를 한꺼번에 바꾼다:
**(a) causal masking**(미래 샘플 차단), **(b) dilation 으로 수용영역 확장**,
**(c) downsampling 제거**. 우리 U-Net 3종과 다른 점이 여러 개다.

### 검토한 선택지

**1. 표준 TCN 을 그대로 추가** — 문헌 그대로라 인용이 쉽다. 그러나 결과가
나왔을 때 **셋 중 무엇 때문인지 말할 수 없다.** 이 프로젝트에서 이미 여러 번
겪은 실패 형태다(F-8·F-10·F-12) — 여러 요인이 섞인 채 측정하면 표는 나오는데
해석이 안 된다. 게다가 causal masking 은 **우리 설정에 맞지도 않는다**:
오프라인 후처리라 미래 샘플을 쓸 수 있고, 다른 방법(`M01` filtfilt,
`M04` SWT, `M06` U-Net)은 전부 비인과적이다. causal 로 묶으면 **해상도가
아니라 인과성을 재게 된다.**

**2. 아예 추가하지 않는다** — "구조는 이미 셋이고 손실 쪽이 효과가 크다"
는 것이 당시 판단이었다. 그러나 **U-Net 의 downsampling 이 QRS 를 뭉갠다**
는 가설은 그 자체로 그럴듯했고(QRS 폭 20~25 샘플 → 1/16 이면 1~2 샘플),
검증한 적이 없었다.

**3. 해상도 하나만 바꾼 대조군** — 선택.

### 고른 것과 근거
`M10` DilatedResNet1D 를 만들되 **`M06` 과 다른 것이 시간 해상도뿐이 되도록**
맞췄다 `[코드]`:

| | `M06` | `M10` | 차이 |
|---|---|---|---|
| params | 976,489 | 979,926 | +0.4 % |
| 수용영역(conv 경로) | 887 | 895 | +0.9 % |
| 손실 · 데이터 · 분할 · 일정 · 시드 | | 동일 | — |
| **시간 해상도** | 1/2 씩 4회 축소 후 복원 | **끝까지 유지** | **이것** |

causal masking 은 **일부러 뺐다.** 문헌의 TCN 과 다르다는 것을 모델
독스트링에 명시했다 — 숨기면 "TCN 을 구현했다" 는 오독을 부른다.

이렇게 하면 결과가 어느 쪽으로 나오든 **한 문장으로 말할 수 있다.**
나아지면 "해상도가 병목이었다", 안 나아지면 "해상도는 병목이 아니다".
실제로는 후자였고, 거기에 더해 **beat 형태가 나빠지는** 것까지 나왔다(F-20).

### 되돌려야 하는 조건
causal(실시간 스트리밍) 구성이 프로젝트 목표가 되면. 그때는 `M10` 이
답하지 못한 질문 — 인과 제약의 대가 — 이 새로 필요해지고, 표준 TCN 이
그 자리에 맞는다.

### 남긴 검사
`tests/test_dilated_resnet.py` 9건. params·수용영역이 `M06` 의 1 % 안인지,
길이가 보존되는지(축소 경로 부재), 초기화 시 항등인지, **비인과성이
의도된 것인지**(미래 샘플에 gradient 가 흐르는지 확인). 마지막 항목은
"실수로 causal 이 됐다" 와 "일부러 비인과다" 를 구분하기 위한 것이다.

## D-12. git LFS 로 옮기지 않는다 — 지금은 이득이 0 이다

| | |
|---|---|
| 시점 | P-9 (사용자 질문: "LFS 는 GB 단위 아니냐") |
| 상태 | 유효 — 재검토 조건은 아래 |

### 갈림길
O-13 을 고치면서 체크포인트·튜닝값·그림을 저장소에 올렸다. 저장소가 커졌으니
LFS 로 옮길 것인가.

### 검토한 선택지 — 실측부터

**저장소 실측** `[측정]`:

| 항목 | 값 | 대비 |
|---|---|---|
| `.git` (팩) | **163 MB** | GitHub 권장 상한 1 GB 의 **16 %** |
| 최대 단일 파일 | **3.9 MB** | 차단 100 MB 의 **3.8 %**, 경고 50 MB 의 7.8 % |
| 이력 blob 누적 | 201.7 MB | |

이력 구성:

| 무엇 | 크기 | 비중 | 성격 |
|---|---|---|---|
| MIT-BIH/NSTDB 원자료 | 119.9 MB | 59.5 % | **불변** — 한 번 올리고 안 는다 |
| 체크포인트 `.pt` | 60.6 MB | 30.0 % | 재학습마다 는다 |
| `.parquet` 지표표 | 9.2 MB | 4.6 % | |
| 그림 `.png` | 6.6 MB | 3.3 % | |
| 코드·문서·csv | 5.4 MB | 2.7 % | |

**결정적 수치**: 체크포인트 경로 16 개 중 **판이 2 개 이상인 것은 0 개**다.
즉 **이력에 낡은 판으로 남아 낭비되는 용량이 0.0 MB** 다 `[측정]`.

**LFS 의 이득은 바로 그 낭비를 없애는 것**이다. 큰 파일이 여러 판 쌓여 이력이
불어날 때 판마다의 실체를 저장소 밖에 두는 장치다. 지금은 없앨 낭비가 없다.
`clone` 이 받는 양도 어느 쪽이든 같다.

### 고른 것과 근거
**옮기지 않는다.** 이득이 0 인데 비용은 셋 다 실재한다.

**1. 이력을 통째로 다시 쓴다.** `git lfs migrate import` 는 69 개 커밋의
해시를 전부 바꾸고 force-push 를 요구한다. 이 프로젝트에서는 그 대가가
특히 크다 — **문서가 커밋 해시 19 개를 인용**하고 있고(`a893f2b`, `ebbe13f`,
`1416c86` …), 산출물의 `ckpt_git` 열에도 3 개가 박혀 있다 `[측정]`. 전부
가리키는 곳이 없어진다. **기록의 추적성이 이 프로젝트의 주 산출물인데
그것을 깨는 셈이다.**

**2. LFS 무료 한도는 저장이 아니라 대역폭에서 먼저 걸린다.** 무료 계정 기준
저장 1 GB · **월 대역폭 1 GB** 다. 바이너리가 180 MB 이므로 **월 5~6 번
clone 하면 소진**되고, 그 뒤로는 다음 달까지 clone 이 실패한다. 지금은
저장소가 커도 clone 이 **항상 된다.** 실패 양상이 더 나빠진다.
(과금 조건은 바뀌므로 착수 전 GitHub 문서 확인이 필요하다.)

**3. clone 하는 모든 기계에 `git lfs install` 이 필요해진다** — 앞으로 붙을
아두이노 쪽 작업 환경 포함.

### 되돌려야 하는 조건
아래 중 **하나라도** 걸리면 다시 따진다.

1. 단일 파일이 **50 MB** 에 접근 (지금 3.9 MB)
2. 같은 체크포인트 경로의 **낡은 판이 200 MB 이상** 쌓임 (지금 0 MB)
3. `.git` 이 **1 GB** 에 접근 (지금 163 MB — 지금 규모의 재학습을 **28 번**
   더 해야 닿는다)

2 번이 실질적인 방아쇠다. 그리고 그때도 LFS 보다 싼 수가 먼저 있다 —
**보고서가 인용하는 체크포인트만 남기고 나머지는 커밋하지 않는 것.**
`last.pt`(재개 전용, 182 MB)를 이미 그렇게 처리했다(O-13).

## D-13. 손실 확장 후보를 넷 기각하고 둘만 남겼다 (L5 · L6)

| | |
|---|---|
| 시점 | P-9 (사용자 요청: "다른 손실함수로 제안해볼 만한 게 있어?") |
| 상태 | 유효 — **결과 확정, 5.8.9** |

### 갈림길
구조 변경이 세 번 연속 기각됐고(F-20), 손실 변경만 양축에서 유의했다.
그러면 **어떤 손실 항을 더할 것인가.** 후보는 얼마든지 만들 수 있는데,
손실 하나당 학습 4회(모델 2 × 축 2) ≈ 2.5 시간이라 아무거나 못 넣는다.

### 검토한 선택지

**고르는 기준을 먼저 정했다**: (a) **이미 측정된 약점**을 겨냥할 것,
(b) 다른 항이 **하지 않는 일**일 것, (c) 지금 있는 지표로 **효과를 잴 수
있을 것**. (c) 가 특히 중요하다 — 잴 수 없는 것을 고치면 고쳤는지 모른다.

| 후보 | 판정 | 근거 |
|---|---|---|
| **`L6` clean 보존** | **채택** | EXP-C 가 **이미 재고 있는** 약점이다 — DL 이 깨끗한 신호를 SWT 보다 **17 dB 더 망가뜨린다**(22.22/23.51 vs 40.14). 기존 L1~L4 중 이것을 겨냥하는 항이 **하나도 없다.** residual 구조라 "입력이 깨끗하면 빼지 마라" 가 그대로 손실이 된다 |
| **`L5` SNR 층 균등** | **채택** | 딥러닝이 지는 곳이 고 SNR(교차점 13 dB, 5.8.2)인데 학습 손실은 저 SNR 로 쏠린다 — 실측 3.5~4.8 배 |
| SI-SDR (척도 불변) | 기각 | **이득 보존을 포기한다.** `gain_bias` 는 DL 이 `M_FE` 대비 **22 기록 전부**에서 이기는(r = 1.000) 몇 안 되는 항목이다. 척도 불변 손실은 그 강점을 겨냥해 깎는다 |
| 다해상도 STFT | 기각 | `L4` 의 subband 항이 **이미 웨이블릿 도메인 판**이고 D1 에서 L3 를 못 넘었다(+0.993 vs +1.032). 같은 자리에 도메인만 바꿔 다시 넣는 것이다 |
| 시간영역 QRS 가중 | 기각 | 같은 이유 — `L4` 가 QRS 대역(D3/D4)에 이미 2 배 가중을 줬다 |
| 적대적 / perceptual | 기각 | **방향이 반대다.** 안전성 프로브(EXP-E)에서 DL 이 가장 안전한 이유가 residual 구조인데, 생성적 압력은 없는 파형을 만들어내는 쪽으로 민다. RQ5 를 스스로 훼손한다 |
| **`diff_loss(order=2)`** | **기각** | 아래 별도 |

### `order=2` 를 기각한 근거 — 재고 나서 뺐다

처음에는 "곁들일 것" 으로 적어 뒀다. 1 차 차분(기울기) 대신 2 차(곡률)를
쓰면 과평활에 더 민감하리라는 것이었다. **실측 둘이 기각했다.**

**(1) 새 방향이 아니다.** 파라미터 gradient 의 코사인 유사도를 쟀다 `[측정]`:

| | D0 | D1 |
|---|---|---|
| `d1` vs `d2` | **+0.947** | **+0.993** |

거의 같은 방향이다. 즉 `order=2` 는 새 기제가 아니라 **차분항 가중치를
1.6~1.9 배 올린 것**과 사실상 같다. 그것은 새 손실이 아니라 가중치 sweep 이고,
"L1→L2→L3 처럼 한 번에 한 가지" 라는 ablation 규약(F-9)에 걸리지도 않는다.

**(2) 고치려는 기제 자체가 D1 에서 죽어 있다.** `L2 → L3`(= 차분항 추가)의
순효과 `[측정]`:

| | 전 구간 | 20 dB |
|---|---|---|
| D0 M06 | +0.223 (p = 0.083) | **+0.529 (p = 1.3e-03)** |
| D1 M06 | −0.018 (n.s.) | −0.117 (n.s.) |

**차분항의 고 SNR 이득은 D0 전용이다.** 이유도 같은 코사인 측정에 있다 —
차분항이 다른 항과 이루는 각이 축마다 다르다:

| `d1` gradient 와의 코사인 | D0 | D1 |
|---|---|---|
| vs MSE | **−0.069** (거의 직교) | **+0.826** (중복) |
| vs MAE | −0.294 | +0.640 |

**D0 에서는 MSE/MAE 가 못 보는 방향이라 값을 하고, D1 에서는 이미 하는
일이라 더할 게 없다.** 실기록은 beat 마다 형태가 달라 진폭 오차와 기울기
오차가 함께 움직이기 때문으로 보인다 `[추론]`.

**그러므로**: 이미 D1 에서 아무 일도 안 하는 항의 가중치를 1.7 배 올리는 데
학습 4 회를 쓰지 않는다.

### 고른 것과 근거
`L5` 와 `L6` 둘만 학습한다. 둘 다 **L3 에서 딱 한 가지만 바뀐다** —
`L5` 는 window 가중, `L6` 는 항 하나 추가. 그래야 결과를 한 문장으로 말할 수
있다(D-11 과 같은 원칙).

**결과를 보고 주 실험의 손실을 바꾸지 않는다.** TEST 를 보고 고르면 사후
선택이고, 그 순간 TEST 는 독립 평가가 아니게 된다(5.8.7). L5/L6 은 ablation
표에 실릴 뿐이다.

### 결과 (2026-08-29)

**두 후보 다 유의했고, `L6` 이 더 강했다** — 전문은 5.8.9.

| 기준 | 축 | `L6` | `L5` |
|---|---|---|---|
| `M06-L1` | D0 / D1 | **+2.426** / **+1.420** (둘 다 유의) | +1.694 / +0.853 (둘 다 유의) |
| `M08-L1` | D0 / D1 | +1.354 (유의) / +0.652 (n.s.) | +1.502 (유의) / −0.142 (n.s.) |

**고르는 기준 (c)("지금 지표로 효과를 잴 수 있을 것")가 값을 했다.** EXP-C 로
`L6` 의 기제를 직접 확인할 수 있었다 — D1 에서 `M06` 의 clean 통과 출력 SNR 이
**22.22 → 37.35 dB**, `M08` 이 **23.51 → 38.37 dB** 로 올라 SWT(40.14)와의
격차가 17 dB 에서 **1.7~2.4 dB** 로 줄었다 `[측정]`. 이득이 **의도한 기제를
통해** 왔음이 확인된 것이고, 기준 (c) 가 없었으면 "좋아졌는데 왜인지 모름"
으로 끝났을 것이다.

> **다만 그 도구가 겨냥돼 있지 않았다.** EXP-C 의 딥러닝 항목이 `L1`
> 체크포인트뿐이라 손실 변형을 잴 수 없었다. `configs/exp_c.yaml` 에 손실
> 변형을 넣고 다시 돌려서야 위 표가 나왔다. **실험이 이미 있다는 것과 그것이
> 이 질문을 향해 있다는 것은 다르다.**

### 되돌려야 하는 조건
- **SI-SDR**: 장비 신호에서 절대 이득이 어차피 보정된다는 것이 밝혀지면.
  그때는 이득 보존이 지킬 가치가 아니게 된다.
- **`order=2`**: 차분항이 D1 에서도 유의해지면(예: 손실 재조정 후). 지금은
  기제 자체가 없다.

### 남긴 검사
`tests/test_losses_l5_l6.py` 15 건. 특히 **L1~L3 가 부동소수점 단위로
보존되는지** — 공통 부품(`per_window_loss`)으로 갈아엎었으므로 기존 ablation
표를 다시 안 돌려도 된다는 것을 고정한다.

## D-14. window 실험은 fs 를 올리지 않고 시간 문맥만 늘린다 (win 4096, fs 250)

| | |
|---|---|
| 시점 | P-10 (사용자 제안: "window 1024 가 적절했는지 판단하는 용도") |
| 상태 | 유효 — **실험 착수 전에 기록** (19_record_keeping.md 5절) |

### 갈림길
`win = 1024` 는 프로젝트 초기에 정하고 **한 번도 재검토하지 않은 파라미터**다.
`M09`(CNN+Transformer)를 "구조 하나 더" 로 넣는 대신, **그 window 선택을
검증하는 도구**로 쓰기로 했다. 그러면 `win = 4096` 을 두 가지로 읽을 수 있다.

| | 무엇이 바뀌나 | 문맥 길이 |
|---|---|---|
| **(A) fs 250, win 4096** | **시간 문맥 4 배** | 4.096 s → **16.4 s** |
| (B) fs 1000, win 4096 | **시간 해상도 4 배** | 4.096 s 유지 |

(B) 는 사용자가 "아두이노 ADC 가 1 kHz 까지 된다" 는 것을 확인해 제안했다.

### 검토한 선택지 — (B) 를 기각한 이유

**지금 있는 데이터로는 (B) 를 잴 수 없다** `[측정]`:

| 원자료 | 실제 fs |
|---|---|
| MIT-BIH | **360 Hz** |
| NSTDB 잡음 | **360 Hz** |

fs 1000 으로 가려면 **360 → 1000 업샘플링**이 필요한데, 그것은 **보간일 뿐
새 정보가 아니다.** 원본의 Nyquist 가 180 Hz 이므로 그 위에는 아무것도 없다.
그 데이터로 "해상도를 올리니 좋아졌다" 가 나오면 **실제 1 kHz ADC 와 무관한
인공물**이고, 나오지 않아도 "1 kHz 가 쓸모없다" 는 근거가 되지 못한다.
**어느 쪽으로 나와도 해석할 수 없는 실험**이다.

D0(합성)만 1 kHz 로 생성하는 것은 가능하지만, D1 이 따라올 수 없어 양축
비교가 깨진다(F-9 계열).

**(B) 는 D3(아두이노) 축의 질문이다.** 거기서는 1 kHz 가 실제 표본이므로
같은 실험이 의미를 갖는다. **EXP-F 계획에 넣는다.**

### 고른 것과 근거 — (A), 그리고 2×2

`M06` 의 컨볼루션 수용영역은 **887 샘플(3.5 s)** 이라 window 를 늘려도 그
너머를 **볼 수가 없다.** `M09` 는 전역 attention 이라 쓸 수 있다. 그래서
"긴 window 가 좋은가" 와 "그것을 쓸 수 있는 구조라야 하는가" 를 갈라야 한다.

| | win 1024 (4.096 s) | win 4096 (16.4 s) |
|---|---|---|
| **`M06`** (RF 887, 국소) | 보유 | `m06_w4096` |
| **`M09`** (attention, 전역) | `m09_l1` | `m09_w4096` |

**행 효과** = window 를 늘리면 좋아지는가. **교호작용** = 구조가 필요한가.

**통제** — 두 가지를 맞추지 않으면 window 효과와 데이터량 효과가 섞인다:

| | win 1024 | win 4096 | 맞추는 것 |
|---|---|---|---|
| `max_per_record` | 160 | **40** | epoch 당 **총 샘플 수** |
| `batch_size` | 64 | **16** | step 당 샘플 수 (= epoch 당 step 수) |
| `hop` | 512 | 2048 | 겹침 50 % |

**할루시네이션은 EXP-E 가 이미 잰다.** `halluc_energy` 프로브가 "긴 문맥이
없는 파형을 지어낼 여지를 늘리는가" 에 직접 답한다 — 새 지표가 필요 없다.

**실행 가능성 확인** `[측정]`: 총 샘플 수를 맞춘 조건에서 `win 4096, batch 16`
이 `win 1024, batch 64` 보다 **오히려 조금 싸다**(M09 5.1 s vs 6.4 s/step).
attention 이 O(T²) 지만 T = 1024 토큰(win/4)에서는 지배적이지 않다. `M09` 의
`max_len = 4096` 이라 위치 임베딩이 **정확히 맞는다**(1024 ≤ 1025).

### 되돌려야 하는 조건
- 아두이노 실측이 들어오면 **(B) 를 D3 에서 다시 본다.** 그때는 1 kHz 가
  진짜 표본이다.
- 4096 에서 아무 효과가 없으면 그 사이(2048)를 보지 않는다 — 4 배로 안 되는
  것이 2 배로 될 이유가 없다.

### 남긴 검사
`tests/test_dl_wrapper.py` 3 건. **체크포인트의 학습 window 를 추론이
따르는지**다. `dl_wrapper` 는 window 를 기본값 1024 로 받고 있었고, 다른
길이로 학습한 모델을 넣으면 **에러 없이 어긋난 채** 표가 나왔다 —
`frontend` 와 같은 계열의 train/inference 불일치다(F-9). 이 실험의 전제
조건이라 먼저 고쳤다.

## D-15. 손실 ablation 은 `M06`·`M08` 두 backbone 으로만 한다 (`M07` 제외)

| | |
|---|---|
| 시점 | STEP 19 (결정 당시) / **기록은 P-10** — 사용자가 "M07 은 왜 표에 없나" 라고 물어서 |
| 상태 | 유효 |

> **이 항목은 `[재구성]` 이다.** 결정 당시에는 근거를 적지 않았고, 아래는
> 코드·결과에서 사후에 복원한 것이다. 19_record_keeping.md 5 절에
> "후보를 고른 순간" 트리거를 넣은 계기가 바로 이 누락이다.

### 갈림길
손실 ablation(L1~L6)을 **어느 모델로** 돌릴 것인가. 딥러닝 방법은 `M06`·
`M07`·`M08` 셋(뒤에 `M09`·`M10` 추가)인데, 손실 하나당 모델 하나 × 축 둘 =
학습 2 회다. 셋 다 하면 손실 6 종에 36 회가 된다.

### 검토한 선택지

| | 의미 | 판정 |
|---|---|---|
| 셋 다 | 완전한 격자 | 학습 36 회. 그리고 아래 (1) 때문에 정보가 늘지 않는다 |
| **`M06` + `M08`** | **backbone 두 종** | **선택** |
| `M06` 만 | 최소 | 손실 효과가 backbone 에 따라 다른지 못 본다 |

### 고른 것과 근거

**(1) `M07` 은 `M06` 과 backbone 이 같다** `[코드]`. `M07` = SWT 전처리 →
**같은 `ResUNet1D`**. 손실은 신경망 안에서 작동하므로, 앞단에 SWT 를 붙인 것이
손실 반응을 바꿀 이유가 약하다. 반면 `M08` 은 **입력 표현 자체가 subband** 라
손실이 다르게 걸린다 — 실제로 `L4`(subband 항)는 `M08` 에만 적용 가능하다.

**(2) `M07` 은 딥러닝 중 가장 나쁘다** `[측정]`. RQ4(5.4):

| 배치 | 방법 | 전체 평균 | 20 dB |
|---|---|---|---|
| 쓰지 않음 | `M06` | 11.43 | 3.86 |
| **전처리로** | **`M07`** | **10.46** | **1.91** |
| 표현공간으로 | `M08` | **11.97** | **5.51** |

`M06` 보다도 낮다. **가장 약한 방법에 학습 자원을 더 쓰는 것은 배분이 나쁘다.**

**(3) 사후 확인 — 이 선택이 옳았다는 근거가 결과에 있다** `[측정]`.
손실 반응이 backbone 마다 실제로 갈렸다(5.8.9):

| | D0 | D1 |
|---|---|---|
| `M06` L1→L3 | **+1.175 (유의)** | +0.869 (n.s.) |
| `M08` L1→L3 | +0.070 (n.s.) | **+1.032 (유의)** |

**두 backbone 이 반대로 반응한다.** `M06` 하나만 했으면 D1 에서 "손실은
효과 없다" 는 결론이 나왔을 것이다. 두 종을 고른 것이 값을 했다.

### 되돌려야 하는 조건
`M07` 계열(전처리 하이브리드)이 어떤 조건에서 최선이 되면. 지금은 양축에서
`M06`·`M08` 에 모두 뒤지므로 해당 없다.

### 남긴 검사
없음 — 이것은 자원 배분 판단이라 코드로 고정할 성질이 아니다. 대신
`check_records.py` 의 `check_design_choices_have_a_decision` 이 **모델과 손실
preset 이 D 기록에 이름을 갖도록** 강제한다(19_record_keeping.md 10 절).
