# 21. 설계 결정 (D) — 갈림길에서 무엇을 왜 골랐나

> 형식은 `docs/19_record_keeping.md` 를 따른다.
> **판별 질문**: "다르게 골랐다면 다른 결과가 나왔는가?"
>
> 결정은 발견이 아니다. 틀린 게 아니라 **고른 것**이고, 나중에 "왜 그렇게 했냐"
> 는 질문을 받는다. 그때 근거와 **검토했던 대안**이 남아 있어야 한다.

---

## D-1. 주 결과는 front-end 를 적용한 조건으로 한다

| | |
|---|---|
| 시점 | `cfb5d1a` (F-10 조치) |
| 상태 | 유효 |

### 갈림길
F-10 을 고칠 때 두 방향이 있었다. **딥러닝에도 front-end 를 주는 것**과
**모든 방법에서 front-end 를 빼고 알고리즘 자체만 비교하는 것.**

### 검토한 선택지
| | 의미 | 문제 |
|---|---|---|
| FE 적용 | 실사용 시나리오 | front-end 가 천장을 정한다(F-11) |
| FE 제거 | 알고리즘 본질 비교 | 실측 장비에서는 쓰지 않을 조건 |

### 고른 것과 근거
**FE 적용을 주 조건, FE 제거를 부록**(`exp_a_nofe.yaml`)으로 두었다.
실측 장비에서는 front-end 를 당연히 쓰므로, 그것을 뺀 비교는 이 과제의 질문
("우리 취득 시스템에 무엇이 적합한가")에 답하지 못한다.

### 되돌려야 하는 조건
과제의 질문이 "알고리즘 자체의 우열" 로 바뀌면. 또는 front-end 천장(34 dB)이
비교를 무의미하게 만들 만큼 낮아지면.

### 파생 결정
부록 조건에 딥러닝을 넣지 않았다(`dl_methods: {}`). FE 없이 학습한 체크포인트가
없어서, 넣으면 train/test 전처리 불일치가 된다.

## D-2. 데이터축은 명시 선택하고 산출물 경로를 분리한다

| | |
|---|---|
| 시점 | `824adc3` (P-1) |
| 상태 | 유효 |

### 갈림길
`source: auto` 는 `data/raw/mitdb` 에 파일이 생기는 순간 조용히 D0 → D1 로
바뀐다. 같은 커밋에 같은 config 로 같은 명령을 돌려도 다른 결과가 나온다.

### 검토한 선택지
1. **`auto` 를 금지**하고 명시를 강제 — 재현성은 최선이나 편의성을 잃는다
2. **`auto` 를 두되 해석 결과를 출력** + 산출물 경로에 축 태그
3. config 를 D0/D1 로 복제 — 중복이 늘고 두 벌이 어긋난다

### 고른 것과 근거
**2번.** `auto` 자체를 막지 않는 대신 **결과가 섞이지 않게** 했다
(`results/d0/`, `results/d1/`). 금지는 실수를 막지만 편의를 해치고,
경로 분리는 실수해도 **덮어쓰지 않는다.** 후자가 손실이 작다.

체크포인트 경로도 `results/{tag}/m06_l1/best.pt` 로 템플릿화해서,
D0 모델을 D1 평가에 먹이는 사고가 구조적으로 막히게 했다.

## D-3. D1 의 참조는 front-end 를 통과한 신호로 정의한다

| | |
|---|---|
| 시점 | `72fcc52` (F-12 조치) |
| 상태 | 유효 |
| 승인 | 사용자 확인 후 진행 |

### 갈림길
MIT-BIH 원본은 clean 이 아니다(F-12). 무엇을 '정답' 으로 둘 것인가.

### 검토한 선택지
| 안 | 내용 | 장 | 단 |
|---|---|---|---|
| **A** | 참조 = `FE(원본)` | 표준 관행, 코드 변경 최소 | 목표가 "원본 복원"이 아니게 됨 |
| B | front-end 를 파이프라인 밖 공통 전처리로 분리 | 가장 깨끗한 구조 | `M_FE` 기준선이 identity 가 되어 지금까지 쌓은 "front-end 기여분" 분석 틀이 사라짐. methods 계층 전면 수정 |
| C | D1 에서 front-end 컷오프 완화 | 변경이 작음 | 축마다 front-end 가 달라져 D0/D1 비교가 어려워지고, 문제를 줄일 뿐 없애지 못함 |

### 고른 것과 근거
**A.** 과제 목표를 **"0.5~100 Hz 대역의 ECG 를 복원한다"** 로 명시하는 것이
정직하고, ECG denoising 문헌의 표준 관행이며, 변경 범위가 가장 작다.
B 는 구조적으로 더 깨끗하지만 F-10/F-11 에서 얻은 분석 틀(`M_FE` 기준선)을
버려야 해서 순손실이다.

### 되돌려야 하는 조건
"원본 파형 그대로의 복원" 이 과제 목표가 되면. 또는 front-end 를 쓰지 않는
방법군이 비교에 들어오면.

## D-4. D0 는 참조 정의 변경에도 재실행하지 않는다

| | |
|---|---|
| 시점 | `72fcc52` |
| 상태 | 유효 |

### 갈림길
D-3 으로 참조 정의를 바꿨으니 D0 결과도 다시 재야 하는가(약 2시간).

### 근거 — 측정으로 결정했다
같은 비교를 D0 에서 하면 차이가 **0.02 dB 이하**다 (10 dB, 4 record):

| 방법 | 참조=raw | 참조=FE(raw) | 차이 |
|---|---|---|---|
| `M00` | 10.25 | 10.25 | −0.00 |
| `M_FE` | 16.04 | 16.05 | +0.01 |
| `M04` | 19.73 | 19.75 | +0.02 |

이유는 F-12 의 표에 있다 — D0 에서 front-end 는 53.24 dB 로 사실상 무해하다.

### 되돌려야 하는 조건
D0 결과에서 0.02 dB 수준의 차이가 결론을 가르는 비교가 나오면.
현재 주요 비교는 1 dB 이상이므로 해당 없다.

## D-5. D0 를 완결한 뒤 D1 로 넘어간다

| | |
|---|---|
| 시점 | `29c3d80` (`99_status.md` P-1~P-9) |
| 상태 | 유효 |

### 갈림길
D1 데이터가 도착했을 때, 곧바로 D1 으로 갈 것인가 D0 를 마무리할 것인가.

### 검토한 선택지
| | 의미 | 문제 |
|---|---|---|
| D1 즉시 착수 | 최종 목표에 빨리 도달 | D0 결과 세트가 불일치인 채 남아 어떤 표도 못 만든다 |
| **D0 완결 후 D1** | 두 축의 비교 자체가 결과 | D1 착수가 늦어진다 |

### 고른 것과 근거
**D0 완결 우선.** 세 가지 이유다.
1. D0 결과 세트가 **내부적으로 불일치** 상태였다(일부만 FE 재학습). 이대로
   두면 어떤 표도 만들 수 없다.
2. D0 는 파이프라인 검증 역할이고, **D0/D1 비교 자체가 결과**가 된다
   (F-8 의 연장 — 합성 벤치마크가 무엇을 왜곡하는가).
3. 실제로 한 번 순서를 건너뛰어 무효 수치가 보고서에 경고 없이 남은 적이 있다.

`99_status.md` 에 **"P-5(결과 해석 보고)를 건너뛰고 P-7 로 가지 않는다"** 를
명시적으로 적어 두었다.

## D-6. oracle 의 family 라벨을 `bound` → `oracle` 로 바꾼다

| | |
|---|---|
| 시점 | `939b485` |
| 상태 | 유효 |

### 갈림길
`B01`/`B02` 를 표에서 어떻게 부를 것인가. 라벨 하나지만 독자의 해석을 좌우한다.

### 검토한 선택지
| | 문제 |
|---|---|
| `bound` 유지 | "모든 방법의 상한" 으로 읽힌다 |
| **`oracle` 로 변경** | 정확하지만 "그럼 상한은 무엇인가" 라는 질문이 남는다 |
| 표에서 제외 | 상한 없이 비교하면 "얼마나 더 갈 수 있는가" 를 알 수 없다 |

### 고른 것과 근거
**`oracle` 로 변경하고 label 에 계열을 명시**했다.

`family="bound"` 는 "모든 방법의 상한" 으로 읽힌다. 실제로는 각자 자기 계열의
상한일 뿐이고, `M07` 은 −5 dB 에서 `B01` 을 실제로 넘는다(18.54 vs 15.86).
**oracle 을 넘는다는 사실 자체가 그 oracle 이 그 방법의 상한이 아니라는 증거**다.

`oracle_gap` 지표의 적용 범위도 wavelet thresholding 계열로 한정한다고 명시했다.

## D-7. `Se`/`PPV` 를 주 지표로 승격한다

| | |
|---|---|
| 시점 | `cfb5d1a` 이후 |
| 상태 | 유효 |

### 갈림길
R-peak 관련 지표 중 무엇을 주 지표로 올릴 것인가.

### 검토한 선택지
| | 재는 것 | 한계 |
|---|---|---|
| `rpeak_mae_ms` (기존) | 매칭된 peak 의 타이밍 정확도 | **놓친 beat 를 못 본다** |
| **`Se`/`PPV` 추가** | 검출률과 오검출률 | 지표 수가 늘어 표가 커진다 |

### 고른 것과 근거
**`Se`/`PPV` 를 주 지표로 승격**하고 `rpeak_mae_ms` 는 유지했다.

`rpeak_mae_ms` 는 **매칭된 peak 만** 본다. 절반을 놓쳐도 남은 것의 타이밍이
정확하면 작게 나온다. 실측에서 전 방법이 8.6~8.8 ms 로 검출기 산포 안에 묻히는데,
`PPV` 는 0.977 → 0.996 으로 크게 갈렸다. **딥러닝은 오검출을 줄인다** 는 사실이
`rpeak_mae_ms` 만으로는 전혀 보이지 않는다.

## D-8. 학습 러너는 재개를 기본으로 켠다

| | |
|---|---|
| 시점 | `bdc7b90` (P-2) |
| 상태 | 유효 |

### 갈림길
`--resume` 을 기본으로 켤 것인가 끌 것인가.

### 검토한 선택지
| | 위험 |
|---|---|
| 기본 끔 | 중단 복구 때마다 플래그를 기억해야 하고, 잊으면 처음부터 재학습 |
| **기본 켬** | 재학습하려 했는데 이어서 돌 수 있다 → `RESUME=0` 로 해제 가능하게 |

### 고른 것과 근거
**기본 켬.** 러너를 다시 돌리는 상황은 **대부분 중단 복구**다(O-1, O-2). 이미 목표 epoch 까지
끝난 학습은 `train.py` 가 알아서 건너뛰므로, 재개를 기본으로 켜도 손해가 없다.
처음부터 다시 학습하려면 `RESUME=0`.

## D-9. SWT 파라미터는 축별 튜닝 결과를 자동으로 쓴다

| | |
|---|---|
| 시점 | P-7 이후 |
| 상태 | 유효 |

### 갈림길
D1 TRAIN split 재탐색 결과가 D0 와 크게 다르다.

| | sigma | mode | protect_qrs | k |
|---|---|---|---|---|
| D0 | `d2` | garrote | **True** | (2.5, 2.0, 0.6, 0.4, 0.3) |
| D1 | `d1` | hard | **False** | (0.6, 0.2, 0.1, 0.3, 0.3) |

D1 에서는 threshold 가 훨씬 낮고(k 0.6 vs 2.5) QRS 보호가 오히려 해롭다.
어느 파라미터로 D1 실험을 돌릴 것인가.

### 검토한 선택지
1. **D0 값 고정** — 두 축이 같은 설정이라 비교가 단순
2. **축별 튜닝 값** — 각 축에서 `M04` 가 최선을 다한 상태로 비교
3. 두 설정을 모두 평가에 넣어 별도 방법으로 취급

### 고른 것과 근거
**2번.** 설계 원칙 **"baseline 을 약하게 두지 않는다"** 가 직접 적용된다.
D0 파라미터로 D1 을 돌리면 `M04` 가 부당하게 약해지고, 그 상태로 "딥러닝이
낫다" 고 쓰는 것은 F-6 에서 이미 겪은 실수(약한 baseline 과의 비교)의 반복이다.

1번의 장점(비교 단순성)은 **`05_swt_tuning_{d0,d1}.md` 두 문서에 각 축의 최적점이
남으므로** 잃지 않는다. 오히려 "축마다 최적점이 다르다" 는 것 자체가 결과다.

3번은 표가 복잡해지고, 어느 쪽이 그 축의 `M04` 인지 독자가 판단해야 해서 기각.

### 구현
`results/{tag}/tune_swt/best.json` 이 있으면 `run_exp` 가 자동으로 읽어
`M04`/`M04np`/`B01` 에 주입한다. 없으면 `config.py` 의 기본값을 쓴다.
어떤 파라미터가 쓰였는지는 실행 로그와 `manifest.json` 에 남긴다.

### 되돌려야 하는 조건
축별 최적점 차이가 지표 분해능 안에 들어가면(그러면 굳이 나눌 이유가 없다).
또는 튜닝이 과적합을 보이면 — 현재 D1 은 holdout(12.58)이 tune(12.47)보다
높아 해당 없다.
