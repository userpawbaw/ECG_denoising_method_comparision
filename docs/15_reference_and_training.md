# 15. 참조를 무엇으로 둘 것인가 · FE 없이 학습할 것인가

> 손으로 쓴 검토 문서다(생성물 아님). 인용한 숫자는 전부
> `docs/13_lookahead_fe.md` · `docs/14_median_vs_zerophase.md` 에서 온 것이고,
> 그 둘은 스크립트가 생성한다.

실시간 front-end 가 **자기 왜곡을 갖는다**는 것이 드러나자(F-27 · F-29 · F-30)
평가 기준이 흔들리는 것 아니냐는 질문이 나왔다. 이 문서가 그 질문을 정리한다.

---

## 1. 먼저 — 참조가 흔들리는 곳은 **한 군데뿐**이다

우리 평가는 참조를 `FE(clean)` 으로 둔다(**D-3** · **F-12**). 그런데 이 정의가
쓰이는 자리는 둘이고, **둘의 성질이 다르다.**

| | 어디 | front-end 가 어떻게 들어가나 |
|---|---|---|
| **E1 오프라인 비교** | EXP-A~G, 보고서 5장 | 방법 쪽도 참조 쪽도 **같은 오프라인 FE** 다 → **상쇄된다.** FE 는 오차에 한 푼도 안 보탠다 |
| **E2 실시간 검증** | `verify_stream_processor.py`, R-3·R-4 | 방법 쪽은 **실시간 FE**, 참조 쪽은 **오프라인 FE** → **안 상쇄된다** |

**그러므로 이 논의는 E2 에만 해당한다.** 보고서 5장의 결론은 이 문제와 무관하다 —
거기서는 양쪽이 같은 필터를 쓴다.

## 2. E2 에서 «안 상쇄되는 것» 이 정말 문제인가 — 묻는 질문에 따라 다르다

E2 의 오차에는 두 가지가 섞여 있다:

```
출력 − FE_off(clean)  =  [ 출력 − FE_rt(clean) ]  +  [ FE_rt(clean) − FE_off(clean) ]
                            ^^^ 방법의 몫              ^^^ front-end 의 몫
```

| 묻는 것 | 섞여 있어도 되나 |
|---|---|
| **Q1 «실시간으로 옮기면 얼마를 잃는가»** | **된다.** front-end 를 바꿔야 하는 것 자체가 실시간의 비용이다. R-3·R-4 가 «배관 손해» 로 부른 것이 이것이다 |
| **Q2 «실시간 조건에서 어느 방법이 가장 좋은가»** | **순위는 안 바뀐다.** front-end 의 몫은 **모든 방법에 공통**이라 전부 같은 만큼 깎인다. 다만 절대 dB 는 비관적으로 나온다 |
| **Q3 «어느 front-end 가 가장 좋은가»** | **된다.** 그 항이 바로 재려는 것이다 |

**즉 «틀린 결론이 나오는» 상황은 아니다.** 다만 Q2 의 절대값이 front-end 몫만큼
눌려 있고, 그것을 **읽는 사람이 알 수 없다.**

## 3. 제안 (a) — «가장 오차가 낮은 방식의 FE 를 기준으로» 는 **안 된다**

세 가지 이유로, 그리고 셋 다 이 과제가 이미 한 번씩 밟은 지뢰다.

| | 왜 안 되나 |
|---|---|
| **순환** | 참조가 **후보 중 하나**가 된다. 후보를 하나 더 넣으면 참조가 바뀌고 **기존 후보들의 점수가 전부 달라진다.** 재현성이 깨진다 |
| **우승자가 0 을 받는다** | 기준이 된 방식은 front-end 몫이 **정의상 0** 이다. 자기가 자기 시험지를 채점한다 |
| **F-12 와 같은 형태** | F-12 는 «MIT-BIH 원본을 정답으로 두면 front-end 를 쓰는 모든 방법이 부당하게 진다» 였다. 참조를 **한 후보의 출력**으로 두면 같은 종류의 부당함이 반대 방향으로 생긴다 |

## 4. 제안 (b) — «오프라인 FE 를 기준으로만» 은 **이미 그렇게 하고 있다**

`verify_stream_processor.py` 의 참조가 바로 `FE_off(clean)` 이다. 그러니 이
제안은 현상 유지이고, **직관이 맞는 곳에 닿았다.** 참조가 갖춰야 할 두 조건을
그것만 만족한다:

1. **후보와 무관할 것** — 후보를 더해도 안 바뀐다
2. **도달 목표일 것** — «오프라인에서 할 수 있었던 것» 이 곧 실시간이 좇는 상한이다

## 5. 그래서 권하는 것 — **참조는 그대로, 오차를 쪼갠다**

참조를 바꾸는 대신 §2 의 항등식을 **그대로 두 숫자로 보고**한다:

| 보고할 것 | 무엇에 쓰나 | 후보 의존성 |
|---|---|---|
| **`fe_share`** = `FE_rt(clean)` vs `FE_off(clean)` | front-end 고르기 (Q3) | 방법과 무관 |
| **`method_share`** = 출력 vs `FE_rt(clean)` | 방법 비교 (Q2). **front-end 가 상쇄된다** | FE 는 선언된 조건이지 경쟁자가 아니다 |
| **`total`** = 출력 vs `FE_off(clean)` | 실시간 전체 손해 (Q1). **지금 쓰는 것** | 그대로 |

`method_share` 의 참조 `FE_rt(clean)` 은 **후보 방법과 독립**이다 — front-end 는
실험 조건으로 **선언**된 것이고, 그 조건에서 방법이 낼 수 있는 최선이
«깨끗한 입력을 그 front-end 에 통과시킨 것» 이다. D-3 이 오프라인에서 한 논리를
실시간 조건에 그대로 옮긴 것뿐이다.

**세 숫자 다 지금 코드로 잴 수 있다.** 참조 정의를 바꾸는 것이 아니라 **한 개
쓰던 자리에 세 개를 적는** 것이므로, 기존 산출물의 값도 그대로 남는다(`total`).

## 6. 그런데 **비선형 front-end 는 이 분해 자체를 흔든다**

§5 는 `FE_rt(clean)` 이 «신호 성분이 front-end 를 통과한 결과» 라는 것을 전제한다.
**선형 필터에서만 참이다.** 비선형이면 잡음이 신호가 받는 처리를 바꾼다:

| | `FE(x+n) − FE(x)` 와 `FE(n)` 의 차 |
|---|---|
| 블록 영위상 0.5 s | **−257 dB** (정확히 선형) |
| 인과 o1 0.5 Hz | 선형 (같은 부류) |
| **중앙값 200+600 ms** | **−17.6 dB** (d0) · −22.5 dB (d1) |

**중앙값 front-end 는 «비선형이라 마음에 걸린다» 수준이 아니라, 우리 참조
정의가 서 있는 가정을 직접 깬다.** 평활도(준위 산포 d1 1.0 %R)가 가장 좋은
것은 사실이고 그래서 화면 선택지에 남겼지만, **그 모드로 잰 dB 는 다른 두 모드의
dB 와 같은 자에 놓을 수 없다.** 화면에는 두고 표에서는 빼는 것이 맞다.

## 7. FE 없이 딥러닝을 다시 학습할 것인가 — **목적이 갈린다**

### 목적 A — «실시간에서 어느 방법이 우월한가» (비교)

**FE 는 필수다.** 공정성 규약(§4.2)의 첫 항이 «모든 방법이 같은 입력에서
출발한다» 이고, 이것이 없으면 재는 것이 **방법의 차이가 아니라 «누가 대역제한을
더 잘 챙겼는가»** 가 된다. F-10 이 정확히 그 사건이었다 — «모든 방법에 동일
조건» 이 선언에만 있고 코드에는 없었다.

딥러닝만 자기 front-end 를 갖게 하면 «`M06` + 학습된 FE» 대 «`M04` + 우리 FE» 를
비교하게 되고, 이 과제의 연구 질문(RQ1~RQ5)에 답하지 못한다.

### 목적 B — «실시간에서 낼 수 있는 최선은 무엇인가» (성능)

**FE 없는 학습이 정당하고, 매력도 있다.**

| 이점 | |
|---|---|
| 위상 왜곡이 사슬에서 **사라진다** | 필터를 안 거니 F-27 의 문제가 원천적으로 없다 |
| **F-25 · D-19 의 취약성이 사라진다** | 「front-end 를 어느 방향으로 도느냐」로 `M06` 이 4.3 dB 움직이던 것이 없어진다 |
| 자기 디코더에 맞는 앞단을 학습한다 | 손으로 고른 0.5 Hz·4 차가 최적이라는 근거는 없다 |

| 위험 | |
|---|---|
| **창이 기저선 주기보다 짧다** | 창 1024 표본 = **4.096 s**. 기저선 변동 0.05~0.5 Hz 는 주기 **2~20 s** 다. 0.05 Hz 성분은 창 안에서 **DC + 직선**으로만 보이고 절대 준위는 **원리적으로 관측 불가**다. residual 구조라 창 안 기울기는 뺄 수 있지만 **재봐야 안다** `[미측정]` |
| 체크포인트가 전부 무효 | **F-9** — 앞단을 고치면 뒤의 모든 학습이 동시에 무효가 된다 |
| oracle 과 비교 불가 | `B01`·`B02` 는 FE 통과 참조 기준으로 정의돼 있다 |

**권고**: 목적 A(이 과제의 본체)는 **FE 를 유지한다.** 목적 B 는 별도 실험으로
분리하고, 하려면 **`M06` 한 모델 · `d1` 한 축**으로 좁혀 질문에만 답한다.
지금 일정(보드 연결, 시연)에서 우선순위는 낮다.

## 8. 아무도 안 꺼낸 세 번째 선택지 — **실시간 FE 출력으로 학습**

목적 A 를 지키면서 F-25 의 불일치를 없애는 길이 하나 더 있다.
지금 모델은 `FE_off(noisy)` 로 학습하고 시연에서는 `FE_rt(noisy)` 를 본다.
**그 불일치가 F-25 의 −4.3 dB 였다.** 학습을 `FE_rt` 로 옮기면 불일치가 0 이 된다.

**그런데 블록 영위상을 쓰면 이 작업이 애초에 필요 없다.** 오프라인 FE 와의 차가
가장 작기 때문이다 (`docs/13` 「영위상과의 차」 열):

| 실시간 FE | 오프라인 FE 와의 차 d1 | d0 |
|---|---|---|
| **블록 영위상 0.5 s** | **4.8 %R** | **6.9 %R** |
| 인과 o1 0.5 Hz (지금) | 6.0 | 10.1 |
| 중앙값 200+600 ms | 6.4 | 13.7 |

**블록 영위상은 모델이 학습한 것과 가장 가까운 신호를 준다** — 재학습 없이
학습/시연 불일치가 가장 작은 선택이다. §6 의 선형성까지 합치면, 이 모드는
**평가 틀을 하나도 안 건드리고** 들어온다.

> 다만 이 %R 은 **파형 거리**이지 dB 가 아니다. **dB 로도 재봤고 같은
> 방향이었다** — 다음 절.

## 8.5 예측이 맞았다 — **그리고 순위를 뒤집었다** `[측정]`

§5 는 «열 하나가 두 질문에 쓰이면 한쪽에서는 틀린다» 를 예측만 했다.
세 모드를 실제로 재니 **그 일이 이미 일어나 있었다**(**F-33**).

`verify_stream_processor.py --fe-mode {causal,zerophase,median}`,
데모 동작점 `d=12 hop=12`(추가 지연 96 ms):

| | d0 `M06` | d0 `M06L6` | d0 `M04` | d1 `M06` | d1 `M06L6` | d1 `M04` | **평균** |
|---|---|---|---|---|---|---|---|
| **`pipeline_db`** — 참조가 모드마다 다르다 (비교 불가) | | | | | | | |
| 인과 o1 0.5 | −1.06 | −4.80 | +3.09 | **+0.89** | **+1.19** | **+0.73** | **−0.00** |
| 블록 영위상 0.5 s | −3.39 | −3.83 | −0.08 | −0.39 | +0.23 | −0.34 | −1.30 |
| 중앙값 200+600 | −2.03 | −0.56 | +0.28 | +0.76 | +0.99 | −0.12 | −0.11 |
| **`total_db`** — 참조가 고정된 오프라인 FE (**비교 가능**) | | | | | | | |
| 인과 o1 0.5 | −5.72 | −6.05 | −2.35 | −6.06 | −5.69 | −5.46 | **−5.22** |
| **블록 영위상 0.5 s** | **−3.49** | **−4.00** | −1.96 | **−2.87** | **−3.44** | **−2.73** | **−3.08** |
| 중앙값 200+600 | −3.28 | −3.86 | **−1.75** | −3.59 | −3.60 | −2.91 | −3.17 |

**`pipeline_db` 로 보면 인과가 1 위이고, `total_db` 로 보면 꼴찌다.**
d1 `M06` 에서 −6.06 → −2.87, **3.19 dB** 차다.

이유는 §5 가 적어 둔 그대로다. `pipeline_db` 의 참조 `FE_rt(clean)` 은
**모드와 함께 움직인다** — 인과 FE 의 참조는 그 자신이 이미 찌그러진 목표이고,
방법이 그 찌그러짐을 충실히 재현하면 점수가 좋게 나온다. `fe_share` 가 그
거리를 방법과 무관하게 잰다:

| `fe_share` (오프라인 FE 대비, 높을수록 가깝다) | d0 | d1 |
|---|---|---|
| 인과 o1 0.5 | 13.88 dB | 14.17 dB |
| **블록 영위상 0.5 s** | **19.84** | **19.71** |
| 중앙값 200+600 | 19.38 | 18.93 |

**총손해의 지배항이 front-end 자신의 거리다.** 그래서 `pipeline_db` 만 보면
그 항이 참조 쪽으로 숨는다.

> **규약**: front-end 를 비교할 때는 **`total_db` 또는 `fe_share`** 를 본다.
> `pipeline_db` 는 **front-end 를 고정한 뒤 방법을 비교할 때만** 쓴다.

### 동작점 하나의 우연이 아니다

그리고 이것은 **동작점 하나의 우연이 아니다.** 지연 격자 넷 전부에서 같다
(각 칸은 축 2 × 방법 3 의 `total_db` 평균):

| 추가 지연 | 인과 o1 0.5 | **블록 영위상 0.5 s** | 중앙값 200+600 |
|---|---|---|---|
| 96 ms `12:12` | −5.22 | **−3.08** | −3.17 |
| 148 ms `12:25` | −5.25 | **−2.31** | −3.18 |
| 304 ms `12:64` | −5.24 | **−1.99** | −3.18 |
| 712 ms `50:128` | −5.05 | **−2.92** | −3.00 |
| **24 칸 전체** | **−5.19** | **−2.57** | −3.13 |

인과와 중앙값은 지연을 늘려도 거의 안 변하는데(−5.2 · −3.1 고정),
**블록 영위상만 지연을 주면 좋아진다**(−3.08 → −1.99). 방법 쪽 문맥이 늘어난
이득을 front-end 가 안 깎아먹기 때문이다 — 나머지 둘은 자기 왜곡이 바닥을
만들어 그 이득이 묻힌다.


## 9. 정리

| 제안 | 판정 |
|---|---|
| FE 3 종을 화면에서 고르게 하기 | **맞다. 넣었다** (`--fe`, `POST /fe`). 위상 왜곡과 평활도는 같이 못 가므로 **보는 사람이 고를 문제**다 |
| «가장 오차 낮은 FE» 를 참조로 | **안 된다** — 순환이고 F-12 와 같은 형태다 |
| 오프라인 FE 만 참조로 | **이미 그렇게 한다.** 직관이 맞다 |
| (추가) 오차를 FE 몫 / 방법 몫으로 쪼개기 | **권한다** — 참조를 안 바꾸고 Q1·Q2·Q3 에 각각 답한다 |
| FE 없이 재학습 | **목적 A 는 안 된다**(공정성 규약), **목적 B 는 정당**하나 지금 우선순위가 낮다 |
| (추가) 실시간 FE 로 재학습 | **블록 영위상을 고르면 필요 없다** — 오프라인 FE 와 가장 가깝다 |
| **어느 모드를 쓸 것인가** | **블록 영위상 0.5 s.** `total_db` 6 칸 평균 −3.08 dB (인과 −5.22, 중앙값 −3.17)이고 **d1 세 방법 전부에서 1 위**다. 파형 지표·선형성·학습 분포까지 같은 방향을 가리킨다 (§8.5) |
