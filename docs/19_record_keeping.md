# 19. 기록 규약 — 보고서를 나중에 쓰기 위해 지금 무엇을 남길 것인가

> **이 문서가 필요한 이유.** 이 과제에서 가장 값진 산출물은 결과표가 아니라
> **"그럴듯한 결과표가 틀렸다는 것을 어떻게 알아챘는가"** 다. F-8, F-10, F-11,
> F-12 는 넷 다 방법이 아니라 **측정 틀**이 틀린 경우였고, 넷 다 표만 봐서는
> 드러나지 않았다. 그런데 그 판단 과정은 대부분 커밋 메시지와 세션 대화에만
> 남아 있어서, 시간이 지나면 결론만 남고 **왜 그렇게 판단했는지가 사라진다.**
>
> 결론만 남은 기록으로 보고서를 쓰면 "우리는 X를 발견했다" 수준의 나열이 된다.
> 평가자가 알고 싶은 것은 그게 아니라 **"무엇이 이상해 보였고, 무엇을 먼저
> 의심했고, 그 의심이 어떻게 틀렸고, 결국 어떤 측정이 결판을 냈는가"** 다.

---

## 1. 세 종류의 기록을 분리한다

같은 파일에 섞으면 성격이 다른 것들이 서로를 묻는다.

| 종류 | 파일 | 담는 것 | 판별 질문 |
|---|---|---|---|
| **F — 발견** | `20_findings.md` | 결과의 해석을 바꾼 것 | "이걸 몰랐다면 보고서에 틀린 결론이 실렸는가?" |
| **D — 결정** | `21_decisions.md` | 갈림길에서 고른 것 | "다르게 골랐다면 다른 결과가 나왔는가?" |
| **O — 사고** | `22_incidents.md` | 결과는 안 바꾸지만 재현·신뢰성에 영향 | "같은 일이 또 나면 시간을 또 잃는가?" |

**F 와 O 의 경계**: 잘못된 숫자가 보고서에 실릴 뻔했으면 F, 시간만 잃었으면 O.
학습이 두 번 죽은 것은 O(결과는 같다), front-end 비대칭은 F(결론이 뒤집혔다).

**D 를 따로 두는 이유**: 결정은 발견이 아니다. "MIT-BIH 를 정답으로 쓸 것인가"
같은 것은 틀린 게 아니라 **고른 것**이고, 나중에 "왜 그렇게 했냐" 는 질문을
받는다. 그때 근거와 함께 검토했던 대안이 남아 있어야 한다.

---

## 2. F 항목 템플릿 — 결론이 아니라 **판단 과정**을 남긴다

```markdown
## F-nn. 한 줄 요약 (무엇이 틀렸는가)

| | |
|---|---|
| 상태 | 확정 / 잠정 / **철회** |
| 발견 | 커밋 해시, 어느 단계에서 |
| 영향 | 어떤 결론이 어떻게 바뀌었는가 |

### 발단 — 무엇이 이상해 보였나
그냥 "발견했다" 가 아니라, **어떤 숫자가 어떻게 이상했는지**. 이상하다고
느낀 근거가 무엇이었는지. 이 항목이 보고서에서 가장 인용 가치가 높다.

### 먼저 의심한 것과 그것을 배제한 방법
틀린 가설도 반드시 적는다. **"파라미터가 나쁜 줄 알았다"** 가 F-12 의 핵심이다.
배제 근거(측정/코드 확인)를 함께 남긴다.

### 결정적 측정
표 또는 명령. **재현 가능해야 한다.** 이 측정 하나로 판이 갈렸다는 것이
보이도록.

### 조치와 검토한 대안
왜 그 수정을 골랐는지. 다른 선택지가 있었다면 왜 안 골랐는지.

### 비용
재학습/재실행 범위, 무효가 된 산출물, 소요 시간.

### 놓쳤다면
이 결함이 남았다면 보고서에 무엇이 실렸을지. **한 문장으로.**

### 일반화
다른 과제에도 옮길 수 있는 교훈.
```

**필수는 "발단 / 먼저 의심한 것 / 결정적 측정 / 놓쳤다면" 네 개다.**
나머지는 해당 사항이 있을 때만 쓴다. 억지로 채우지 않는다.

## 3. D 항목 템플릿

```markdown
## D-nn. 무엇을 정했나

| | | 
|---|---|
| 시점 | 커밋 |
| 상태 | 유효 / 번복됨(→ D-mm) |

### 갈림길 — 무엇을 정해야 했나
### 검토한 선택지 (각각의 장단)
### 고른 것과 근거
### 되돌려야 하는 조건
```

마지막 항목이 중요하다. **"이 조건이 성립하면 이 결정은 틀린 것"** 을 미리
적어두면, 나중에 그 조건이 관측됐을 때 결정을 다시 볼 수 있다.

---

## 4. O 항목 템플릿

```markdown
## O-nn. 무엇이 일어났나
| 시점 | 잃은 것 | 재발 방지 |
### 증상 → 원인 → 조치
```

짧게. O 는 상세할 필요가 없고 **재발 방지책이 코드/테스트로 남았는지**가 핵심이다.

## 5. 기록 시점 규약

| 언제 | 무엇을 |
|---|---|
| **이상한 숫자를 본 순간** | 그 숫자와 "왜 이상한가" 를 먼저 적는다. 원인을 알기 **전에** 적어야 발단이 왜곡되지 않는다 |
| 가설을 배제했을 때 | 배제 근거와 함께. 틀린 가설이 사라지면 판단 과정이 사라진다 |
| 수정을 커밋할 때 | F/D/O 번호를 커밋 메시지에 넣는다. 역추적 경로가 된다 |
| 결론이 바뀌었을 때 | 이전 결론을 **지우지 않고 철회 표시**한다. 무엇이 왜 바뀌었는지가 결과다 |

**절대 하지 않는 것**: 틀린 초기 판단을 조용히 고쳐 쓰는 것. 이 프로젝트의
가치 상당 부분이 "틀렸다가 고친 과정" 에 있다.

---

## 6. 측정 근거는 재현 가능하게

F 의 표에 실린 숫자는 **어떤 명령으로 나왔는지** 함께 적는다.
자동 생성 문서(`90_results_*.md`, `03_metric_floor*.md` 등)에 있는 값이면
그 파일을 가리키고, 일회성 측정이면 스크립트를 `scripts/` 에 남기거나
F 항목 안에 코드를 붙인다.

## 7. 보고서를 쓸 때 이 기록을 어떻게 쓰는가

`91_report.md` 6장("개발 과정에서 발견한 것")은 **F 항목의 요약본**이다.
전문은 `20_findings.md` 에 두고 6장에서는 각 F 의
**발단 → 결정적 측정 → 놓쳤다면** 세 줄만 옮긴다.

평가자가 "이 팀은 자기 결과를 의심할 줄 안다" 고 판단하게 만드는 것이
6장의 목적이고, 그러려면 **틀렸던 과정이 보여야 한다.**

## 8. 근거 등급 — 지어내지 않기 위한 장치

필수 4요소를 **억지로 채우면 없던 정보를 만들어낸다.** 실제로 이 규약을 만든
직후 F-1~F-9 를 보완하면서, 당시 기록이 없는 판단 과정을 그럴듯하게 재구성해
넣은 일이 있었다. 그럴듯해서 더 위험하다 — 나중에 보고서에 "우리는 X를
의심했다" 고 쓰면 그건 **사실 주장**이 된다.

그래서 모든 서술에 근거 등급을 붙인다.

| 태그 | 뜻 | 보고서에서 |
|---|---|---|
| `[측정]` | 산출물(`results/`)에 수치가 남아 있다 | 그대로 인용 가능 |
| `[로그]` | 실행 로그·에러 메시지에 남아 있다 | 그대로 인용 가능 |
| `[커밋]` | 커밋 메시지·diff 에 남아 있다 | 그대로 인용 가능 |
| `[대화]` | 세션 기록에 그 판단이 적혀 있다 | 그대로 인용 가능 |
| **`[재구성]`** | **당시 기록이 없고 사후에 복원한 것** | **"추정" 으로 쓴다** |

**`[재구성]` 을 숨기지 않는다.** 재구성 자체는 유용하다 — 코드와 결과를 보면
당시 어떤 순서로 판단했을지 상당 부분 복원할 수 있다. 문제는 그것을 **관측인 것처럼**
쓰는 것이다.

### 빈칸을 두는 기준

다음이면 **채우지 말고 `기록 없음` 이라고 적는다.**

- 근거가 `[재구성]` 인데 **코드나 결과로도 뒷받침되지 않을 때**
  (예: "무엇을 먼저 의심했는가" 는 코드에 흔적이 남지 않는다)
- 여러 해석이 다 그럴듯해서 하나를 고를 근거가 없을 때
- 그 항목이 애초에 해당 사항이 없을 때
  (예: F-7 은 사고 전에 막은 것이라 '틀린 값' 이 없다)

**빈칸이 허위보다 낫다.** 자동 점검(`scripts/check_records.py`)은
`기록 없음` 을 충족으로 인정한다.

### 수치 검증

문서에 인용된 숫자는 `scripts/check_records.py` 가 `results/` 의 실제 값과
대조한다. 불일치하면 실패한다. **인용을 지어내면 테스트가 잡는다.**

## 9. 해설 수준 — 누구를 위해 쓰는가

이 문서들은 **복기 노트가 아니라 해설서**다. 독자는 셋이다.

| 독자 | 필요한 것 |
|---|---|
| 미래의 설계자 | 논리를 잊었을 때 되살릴 수 있는 근거 |
| **심사위원·제3자** | **배경지식 없이도 판단 과정을 따라갈 수 있는 설명** |
| 보고서 작성자 | 그대로 옮길 수 있는 문장 |

두 번째가 기준선이다. 다음을 지킨다.

1. **지표·개념이 그 문서에서 처음 나오면 정의를 함께 준다.**
   수식이 필요하면 수식을, 아니면 한 문장 정의를. 상세 정의는
   **`docs/18_glossary.md`** 에 두고 링크한다. **다른 문서를 찾아봐야 하는
   상황을 만들지 않는다.**
2. **"A 이므로 B" 라고 쓸 때, A 에서 B 가 왜 따라오는지 한 단계 풀어 쓴다.**
   나쁜 예: "과적합이면 tune 만 좋고 holdout 이 나빠야 하는데 둘 다 음수였다."
   좋은 예: 위 문장 + "tune 은 파라미터를 고르는 데 쓴 데이터라 그 데이터에
   맞춰진 파라미터는 tune 에서만 좋다. holdout 은 고르는 데 쓰지 않았으므로
   과적합이면 거기서 성능이 떨어진다. 그런데 둘 다 똑같이 나쁘다는 것은
   '파라미터가 tune 에 맞춰졌다' 로 설명되지 않는다는 뜻이다."
3. **"불가능하다", "말이 안 된다" 같은 판단에는 근거를 붙인다.**
   무엇에 비추어 불가능한지 — 지표 정의상인지, 측정 맥락상인지.
4. 같은 문서 안에서 두 번째 등장부터는 반복하지 않는다.
